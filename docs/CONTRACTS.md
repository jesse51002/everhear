# Everhear contracts

_The contract the parts were built to (draft, 2026-10-07; the dispatcher, §14, 2026-10-09; actions, §1, §8, §10 and §14, 2026-10-10; incantations, §2, §4, §7, §8 and §10, 2026-10-10; the brain, which replaces the conversation, the orchestrator and the dispatcher, §1, §4, §5, §7, §8, §9, §12 and §14, 2026-10-10; the Jev routing, §5 and §7, 2026-10-11; named tasks, a name and a `tasks` row for each implementer's task, and the brain's orchestrator call, §1, §4, §7, §8, §9, §10, §12, §13 and §14, 2026-10-11; one-word incantations, §2 and §10, 2026-10-11; the brain loop, a loop of steps per event and one turn per player, into which the orchestrator call and the retry planner fold, §1, §4, §5, §7, §9, §10, §13 and §14, 2026-10-11). Code comments cite it as "Contracts §N". Where the code has moved on — model choices — the code and the part's README are current._

**What every part of the prototype takes in and puts out, so each part can be built from its own spec in one prompt and still fit the others.** A part's spec may decide anything inside the part; it may not change anything here. Where a part needs this page to change, the change is made here first.

**The pattern is the one that already worked**: an SSH `tail -F` of a file on the EC2 box, RCON over SSH to act, `tellraw` to answer. One feed file carries everything the brain should hear — kept speech, watched game events — and what the brain itself did, so there is one stream, and it is the shared context.

## 1. Where things run

- **EC2** (one Amazon Linux 2023 instance): the Minecraft Java server, vanilla 26.3, in `/opt/mc`, systemd unit `minecraft`, its console written to `/opt/mc/console.log`; the **bridge** (`vfg-bridge`) and the **Jev filter** (`vfg-jev`) in `/opt/vfg`; the database `/opt/vfg/vfg.db`, the transcript history and the brain's tasks (§4); the feed `/opt/vfg/feed.log`; deployed scripts in `/opt/vfg/scripts/`, with `_lib/` (the kit, `mc.py`, `instances.py`, `places.py`, `commands.py`); each running copy's files in `/opt/vfg/run/` (§10). Open to the internet: Minecraft `25565` and the bridge's speech port `8787`. SSH only from the owner's IP. RCON `25575` is never reachable from outside — vanilla binds every interface, so the security group and a host firewall rule keep it in. Every unit runs as `ec2-user`, which owns `/opt/mc` and `/opt/vfg` (the database and its `-wal` and `-shm` files included) and has passwordless `sudo` for `systemctl` and `journalctl`, as Amazon Linux 2023 sets it up.
- **Players' PCs**: Minecraft Java 26.3 with Fabric and the **client mod**.
- **The owner's PC**: this repo; the **`vfg` toolkit**; the **brain** (§9), **Respond**, and the **implementers** the brain starts; the **actions** `actions/`, and `made/<server>/actions/` for what implementers made; the **scripts folder** `scripts/` (and `made/<server>/scripts/`). It reaches EC2 only over SSH; the brain also calls OpenRouter.

Every timestamp is ISO-8601 UTC with milliseconds (`2026-10-07T18:22:31.412Z`). Every id is a ULID unless stated.

**The units** start the server jar in `/opt/mc` (`minecraft`), `/opt/vfg/python/bin/python3 -m vfg_bridge` (`vfg-bridge`) and `/opt/vfg/python/bin/python3 -u /opt/vfg/jev/jev_filter.py` (`vfg-jev`).

**Python on the box** is 3.12, the PC's version: uv, installed into `/opt/vfg/uv/` as a step of the box's setup (`deploy.sh provision` runs `bridge/deploy/python.sh`), installs CPython 3.12 there, and `/opt/vfg/python` links to it. `/opt/vfg/python/bin/python3` runs the units, the scripts and every `vfg` remote program; Amazon Linux's own `python3` (3.9) is left to the host's tools.

**The code** is one repo, a folder per part: `client-mod/`, `bridge/`, `jev/`, `toolkit/`, `brain/` (the brain's loop, Respond and the implementers), `actions/`, `lib/py/` (`structured()`, every model call that wants a structure back; `vfg_actions`, the one loader of the actions), `scripts/`. What runs on EC2 is deployed to `/opt/vfg/`; `vfg action run` deploys a copy's script and `scripts/_lib/` when the box does not have them as the PC does: each deployed folder keeps the stamp, a hash of its files, it was sent with (`.vfg-stamp`), and a run sends the stamps first. An action never leaves the PC: it is a class that names a script and checks its values (§10).

## 2. Speech in — client mod → bridge

`POST {VFG_BRIDGE_URL}/v1/lines`, header `Authorization: Bearer {VFG_CLIENT_TOKEN}`, body:

```json
{ "client_line_id": "uuid-v4", "player_uuid": "…", "player_name": "Steve",
  "text": "build me a castle",
  "started_at": "2026-10-07T18:22:29.100Z", "ended_at": "2026-10-07T18:22:31.400Z",
  "peak_dbfs": -8.2, "mean_dbfs": -23.5 }
```

- `202 {"id": "<line id>"}` stored; `400` bad body; `401` bad token. The token is checked before the body, so an empty `{}` with a good token gets `400` — the mod's connection test relies on it. Repeating a `client_line_id` returns the first id and stores nothing. An empty `player_uuid` is stored as NULL, the same as an AI line.
- Plain HTTP is accepted for the prototype: the token only lets someone post lines.
- **Incantations** — a word or a phrase, bound for a player to an action with its values, fires that action the moment that player says it, with no model on its path. The mod's keyword spotter hears it and posts a **cast**, its own request, beside the line pipeline: neither waits on the other.
  - `POST {VFG_BRIDGE_URL}/v1/casts`, the same token, body `{"client_cast_id": "uuid-v4", "player_uuid", "player_name", "phrase": "fire ball", "heard"?: "fireball", "started_at", "ended_at"}`: the incantation's own phrase (the mod maps a matched alias back to it), and the phrase's window on the mod's audio clock, the clock a line's times use. `202 {"id", "status": "fired"|"cooldown"|"duplicate"|"failed"|"stale", "copy"?, "error"?}` as soon as the copy is spawned; `404` when the player has no such incantation (their own or `@a`); `400`, `401`; `503` when the kit is not on the box. Repeating a `client_cast_id` answers what the first did.
  - The bridge starts the bound action's copy on the box itself (`scripts/_lib/instances.py`, from the entry in `/opt/vfg/incantations.json`, §10), with every caster field set to whoever cast. A cast of an incantation whose window, widened by `VFG_CAST_SLACK_S` (0.3 s) each side, overlaps one of that player's that fired is `duplicate`; within its own `cooldown_s` of its last fired cast, or within `VFG_CAST_GAP_S` (1 s) of any of that player's, it is `cooldown`. Cooldowns are on the bridge's clock.
  - The mod's settings: `incantations` (on), `incantation_threshold` (0.25) and `incantation_boost` (1.5), the spotter's; `heard` is the keyword it matched, normalised (`fireball`). It spots only while it listens, and only that player's own incantations, `@a` ones included; no audio leaves the PC, only the phrase.
  - `GET {VFG_BRIDGE_URL}/v1/incantations?player=Steve&after=<version>&wait=<s>`: `200 {"version", "player", "incantations": [{"phrase", "aliases", "cooldown_s"}]}`, the incantations that apply to that player, `@a` ones included; with `after` the current version it is held until the version changes or `wait` (default 25, at most 30) seconds pass, then `304`. The mod long-polls it while connected.
  - **Layer 2 and the drop rule, on `/v1/lines`.** For a voice line from a player with incantations, a phoneme match of the transcript against their phrases and aliases (`VFG_INCANT_ALLOWANCE`, 0.25) fires a cast through the same path, layer `transcript`, with the line's window; a one-word phrase's phrase and aliases match only from the start of a word of the line, and one of fewer than 6 speech sounds only as it is said, its mishearings left to its aliases. Then a line that overlaps one of that player's casts and has at most one word left once the phrase is taken out (fillers not counted) is stored with `dropped = 'cast'` and never judged or fed (§5); a kept one gets `cast_id`.
- The mod captures only while connected to the server whose address matches its configured `server_address`; a line captured then is still delivered after the player leaves, within its 60 s. A line is speech ended when the mod's turn model hears it finished, or by **`silence_seconds` of silence** (default 3). `text` is 1–2000 characters after trimming. On failure it retries with backoff for up to 60 s, then drops the line.

## 3. Chat and game events — Minecraft server → bridge

The bridge tails `/opt/mc/console.log` and parses it.

- **Chat** `<Name> message` becomes a line with `source = chat`, in the same table as speech, and goes through Jev the same way.
- **Events**, kinds `join`, `leave`, `death`, `advancement`, `server` (start or stop), always go into `events`, and into the feed only if watched (§6).
- RCON echoes, `Played sound`, `Set spawn point` and other noise are ignored.

## 4. Transcript history — `/opt/vfg/vfg.db` (SQLite, WAL)

The bridge creates the schema. The Jev filter writes only the `jev_*` and `fed_at` columns and `usage` rows.

```sql
CREATE TABLE lines (id TEXT PRIMARY KEY, at TEXT NOT NULL, ended_at TEXT,
  player_uuid TEXT, player_name TEXT NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('voice','chat','ai')), text TEXT NOT NULL,
  peak_dbfs REAL, mean_dbfs REAL, client_line_id TEXT UNIQUE,
  jev_class TEXT CHECK (jev_class IN ('action_oriented','conversational','context','not_relevant')),
  jev_confidence REAL, jev_judged_at TEXT, fed_at TEXT);
CREATE INDEX lines_at ON lines(at);
CREATE INDEX lines_player_at ON lines(player_name, at);
CREATE TABLE events (id TEXT PRIMARY KEY, at TEXT NOT NULL, kind TEXT NOT NULL,
  player_name TEXT, text TEXT NOT NULL);
CREATE INDEX events_at ON events(at);
CREATE TABLE feed (seq INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL, line TEXT NOT NULL);  -- line: the whole line, exactly as in feed.log
CREATE TABLE usage (id INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL,
  component TEXT NOT NULL CHECK (component IN ('jev','conversation','orchestrator','implementer','brain','respond','planner','alias')),
  model TEXT, input_tokens INTEGER, output_tokens INTEGER, cost_usd REAL, ref TEXT);
```

- **Incantations** (§2): `lines.dropped` (`'cast'`: only an incantation, never judged or fed) and `lines.cast_id` (the cast the line's speech overlapped), and the bridge's own table `casts (id, at, started_at, ended_at, player_name, phrase, heard, layer 'spotter'|'transcript', incantation_id, action, copy, status 'fired'|'cooldown'|'duplicate'|'failed'|'stale', error, line_id, client_cast_id UNIQUE)`. A fired or failed cast is also an `events` row of kind `cast`.
- It is queried by date with `vfg history` (§8).
- **The AI's own messages are lines too**: every `vfg say` is stored with `source = 'ai'`, `player_name = 'AI'`, no uuid, and the text without the prefix. A whisper is stored as `(to <player>) <text>`. They give Jev the other half of the conversation, and are never judged; `vfg say` feeds each as an `AI say` line itself (§7).
- **The shared context is the `feed` table** (§9): every kept line, every fed game event and everything the brain recorded, in `seq` order, each with its `processed_at` mark: a column added after this DDL, by `ALTER TABLE` on the bridge's start, as are `usage`'s `cache_read_tokens`, `cache_write_tokens`, `ok`, `error` and `ms`. A database built before the four classes is rebuilt on the bridge's start: `direct_ask` becomes `action_oriented`, `not_useful` becomes `not_relevant`; one built before `planner` and `alias` gets its `usage` CHECK rebuilt the same way, every row kept. `conversation`, `orchestrator` and `planner` stay valid components only for old rows: the orchestrator call and the retry planner are folded into the brain's loop, whose steps write `brain` rows (§9).
- **`usage` is the one log of every model call.** Every `structured()` call (`lib/py/vfg_llm.py`, §1) records its own row, whatever happens: its `component` (one of `vfg_llm.Component`, the CHECK's list: `brain`, a step of the brain's loop, and `respond` are the brain's, `alias` the incantation alias call's; `orchestrator`, `planner` and `conversation` only old rows have), `ref` its `call_id` (at most 64 characters), its tokens and cost summed over every attempt, `ms`, and `ok` 1, or 0 with `error`, the reason, one line of at most 300 characters. A failed call is a row with what it cost; one that timed out or was cancelled with an attempt in flight, which OpenRouter bills at a price it never told, has `cost_usd` NULL, and its `error` says what the attempts that came back cost. The row is appended to `usage.pending.jsonl` on the PC, under `usage.pending.lock`, in the folder `VFG_USAGE_QUEUE` names in the environment (default `$VFG_HOME`; the replays point it at their own output, so their rows reach the box only when sent on purpose), and `vfg usage flush` (or the next `vfg usage add`) with the same `VFG_USAGE_QUEUE` sends it (§8); recording never fails a call, never waits on the box and never holds up the caller's event loop. Jev's filter writes its rows itself, and the implementers theirs through `vfg usage add`; those leave `ok`, `error` and `ms` NULL.
- **The brain's tasks** (§9) are the `tasks` table, one row per implementer task, keyed by its name. The bridge creates it after this DDL, as it does `casts`, on every start and every `--init-db`, so an older history gains it and nothing else changes (`PRAGMA user_version` 4); it never writes it. Only the brain writes it, through `vfg task set` (§8):

  ```sql
  CREATE TABLE IF NOT EXISTS tasks (name TEXT PRIMARY KEY, description TEXT NOT NULL, player TEXT,
    status TEXT NOT NULL CHECK (status IN ('open','done','failed')), line TEXT, brief TEXT,
    made TEXT, variables TEXT, session TEXT, result TEXT, created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL, closed_at TEXT);
  ```

  `name` matches `^[a-z][a-z0-9_]{1,31}$` (`galick_gun_styrk`), is never a library action's name or `cast` (the bridge's task for an incantation's copies), and is kept for life. `description` is what the thing is now and for whom, `line` the player's words that started it, `brief` the latest brief its implementer got (a hand-off's, rendered in parts under headings; a follow-up's; or the cancel words, §9), `session` its implementer's session, `result` the brain's last record of it. `made` is JSON, `{"scripts", "actions", "presets", "copies"}`, each a list of names; `variables` is JSON, the fields of the task's action as `vfg_actions.variables()` reads them (`{"name", "type", "default", "ge", "le", "choices", "live", "fixed", "description"}` each), or null until read. `closed_at` is set as the status leaves `open`, and cleared when it opens again.

## 5. Jev — the Jev filter

- Takes lines with `jev_class IS NULL` and `source` other than `ai`, in `at` order, polling every 250 ms or less.
- Calls Jev — `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, key `TYPESAFE_API_KEY` — once per new line, the routing call. The state is the fixed rules (the setting and how to read the state; they define no class), then `/opt/vfg/lookout.md` (what to look out for), then a block of invented examples under what should become of each, then `/opt/vfg/menu.md` (the brain's actions, one `name — what it does` line each, which `vfg jev menu set` writes), then history: recent lines, the AI's included, and the brain's records of its loops, the tasks it opened and followed up and their results (`AI action`, `task` and `result` feed lines), so a follow-up to an earlier ask reads as one — as much as fits in `VFG_JEV_STATE_TOKENS` (default 8,000). The line is marked `[1]` in the history and gets two `choice` questions, D2's: what should happen with it (`d_what`: the AI must act, the AI should answer in chat, remember it, ignore it), and how the speaker would feel if the AI only replied in chat (`d_feel`: fine, let down, they wouldn't notice). The answers walk onto four classes, with `d_what`'s confidence:
  - `action_oriented` — act, and let down: the brain;
  - `conversational` — answer, or act with `d_feel` anything else or missing: Respond;
  - `context` — remember: kept, and shown to no model (§9);
  - `not_relevant` — ignore: never fed.

  A missing or malformed `d_what` is Jev failing. Each line is judged once: nothing is asked again.
- Writes the verdict to the line, and a `usage` row with `component = jev`.
- **The gather call.** A line classed `action_oriented` or `conversational` gets one more call before it is fed, over its speaker's lines that Jev classed `context` or `not_relevant` with a confidence (never a line passed as `context` while Jev failed open or after it refused the line twice), judged after that speaker's last `action_oriented` or `conversational` line was judged, said before the line and at most 180 s before it, not blank and not dropped — the newest 10. Judge order, not the order said, because a voice line is stored once its speech is text, after a line typed later may have been judged: each line is offered to the speaker's next line to the AI judged after it, and to no other. When there are none, no call is made. The state is built the same way, with the gather call's own rules and history heading, the line marked `[ask]` and those lines `[1]` … `[n]`, and each of them gets one `choice` question: is it part of the ask (`part_of_the_ask`, `not_part_of_it`); a missing answer is a no. The yes lines go with the ask as one `LINE` (§7): their texts and then the ask's, in the order said, joined with ` … `, the oldest dropped first when that is over 500 characters, under the ask's fields and time. A gathered line keeps its own class and is fed, or not, as before. A gather call that fails feeds the ask alone, and does not count towards failing open. It writes a `usage` row with `ref = gather:<ask id>`, and one `gather` line to the journal. The filter holds a group in memory until the ask is fed, so an ask caught by a crash in between is fed alone.
- **Feeds what it keeps** (`action_oriented`, `conversational`, `context`) in batches. An `action_oriented` or `conversational` line flushes the batch at once, with whatever context is waiting: both get a live answer. Otherwise a batch flushes `VFG_BATCH_SECONDS` (default 5) after its first line.
- If Jev fails for 10 s it **fails open**: every line passes as `context` with no confidence, and one `SYS` line says so. No model is shown a `context` line (§9), so while Jev fails open the brain answers none of them. Another `SYS` line says when Jev is back.

## 6. Game watchers — `/opt/vfg/watch.json`

```json
{ "events": ["join","leave","death","advancement","server"], "players": [], "contains": [] }
```

- `events` are the kinds to feed. `players` limits them to those players; empty means everyone. `contains` holds extra regexes on raw console lines, fed as `GAME raw`.
- Every kind is on by default. The bridge rereads the file when it changes. The brain sets it with `vfg watchers set` as it starts.

## 7. The feed — `/opt/vfg/feed.log`

**The one stream the brain follows, and the shared context.** It is append-only, one event per line, and mirrored in the `feed` table. The bridge and the Jev filter write it through one locked writer that assigns `seq`. The owner's PC writes it only through `vfg say` and `vfg feed post`, and only the brain does.

```text
LINE#812 18:22:31 Steve voice action_oriented 0.93 -8dB | build me a castle
LINE#813 18:22:33 Alex chat context 0.71 - | that cave by spawn
AI#814 18:22:35 task castle_steve | new: A castle for Steve at spawn, about 40x40, stone and oak
AI#815 18:22:35 say castle_steve | on it, castle coming up
GAME#816 18:22:40 death Steve | Steve was slain by Zombie
AI#817 18:24:02 result castle_steve | castle_steve done: castle built at spawn, 40x40
SYS#818 18:25:00 | jev unavailable — passing every line as context
LINE#819 18:26:04 Alex voice action_oriented 0.91 -11dB | fire aspect 5 on my axe
AI#820 18:26:09 say - | your axe burns now
AI#821 18:26:09 action - | gave Alex's axe Fire Aspect 5 by item modifier; /enchant refuses a level over the maximum
```

- The grammar is `TYPE#seq HH:MM:SS fields | text`. `TYPE` is `LINE`, `GAME`, `AI` or `SYS`. The time is UTC. The fields, separated by single spaces, with `-` for anything missing:
  - `LINE`: `<player> <voice|chat> <action_oriented|conversational|context> <confidence|-> <NdB|->`. The confidence has two decimals and is `-` when Jev fails open; dB is the line's peak, rounded, and `-` for typed chat. A line fed before the Jev routing may end with ` was=not_relevant`, from the re-ask that is gone; the writer still accepts it, and nothing writes it now. The text may hold a group (§5): the lines Jev gathered into an ask, then the ask, in the order said, joined with ` … ` — `the castle by the river … the big one … make it bigger`.
  - `GAME`: `<kind> <player|->`, any kind the bridge feeds.
  - `AI`: `<say|action|task|result|note> <name|->` — what the brain did, which only it writes. The second field is a task's name (`[a-z][a-z0-9_]{1,31}`, §4), or `-` where no task applies, and never a copy's name or a `#seq`: `say`, a chat line it sent (as the `lines` table keeps it, a whisper as `(to <player>) <text>`), under the task it is about (the reported one, else the first its loop opened, else the first it followed up); `action`, the one record a loop of a line leaves (§9): what was done, and what failed and why, at most one per loop and always `action -`; `task`, a task a loop opened (`new: <description>`) or followed up (`follow-up: <what to change, cut to 160>`, or `follow-up: never mind — put back what its last run built` for a cancel); `result`, a task's result, one short line (`<name> done: …`, `<name> failed: …`), which a report's loop leaves as its record. The brain writes no `note` now, and no row per action: older rows hold one `action -` per action run and `note` rows for a copy changed or stopped (`edited <copy>: k=v …`, `stopped <copy>`), and still read. Nothing an implementer writes is ever fed. Rows written before named tasks carry the old `T<n>` ids and still read: only a write is checked.
  - `SYS`: no fields.
- The `ORCH` type of the orchestrator is retired.
- Text has newlines replaced by spaces and is cut at 500 characters with `…`.
- A batch is written in one go, under 200 ms.
- **Every kept line is fed exactly once**, across restarts and crashes: before feeding a line not yet marked `fed_at`, the Jev filter looks for it in the `feed` table and only marks it if it is already there. A group is that ask's line: its text ends with ` … ` and the ask's.
- **A cast** that fired or failed (§2) is always fed, whatever `watch.json` says: `GAME#820 18:30:02 cast Steve | Steve cast "fire ball": command, running as command_2`, or `… | Steve cast "fire ball": failed — <error>`. Cooldown and duplicate casts are not fed.
- `SYS#0` is never assigned by the feed: `vfg watch` uses it for its own notices — EC2 unreachable, reconnected, lines skipped, feed restarted.
- **The writer is one Python module, `vfg_feed`**, owned by the bridge and deployed to `/opt/vfg/lib/`. Its API is `append(type, fields, text, at=None) -> seq` and `append_batch(entries) -> [seq]`, where each entry is a `(type, fields, text, at)` tuple; `at` is the moment it describes (when a line was said), defaulting to now, and is what the `HH:MM:SS` shows. It cleans the text (newlines to spaces, 500 characters), takes a file lock, appends to `feed.log` and inserts the `feed` row. Its command line is `python3 /opt/vfg/lib/vfg_feed.py post <TYPE> "<fields>" "<text>"`, which prints the seq. The Jev filter imports it, and `vfg feed post` calls it over SSH.

## 8. The `vfg` toolkit — the owner's PC

**Every agent acts through these commands, and nothing else touches EC2.** Output is plain text. Exit 0 means success. A failure exits non-zero with one line on stderr. Configuration lives in `~/.vfg/config`, as `KEY=value` lines: `VFG_SSH_HOST`, `VFG_SSH_USER`, `VFG_SSH_KEY`, and the brain's (§9); an environment variable of the same name wins.

| Command | Does |
|---|---|
| `vfg up` | Checks SSH and the `minecraft`, `vfg-bridge` and `vfg-jev` units, starts any that are down, prints their status |
| `vfg watch [--after <seq>]` | Prints the feed from the line after the last `seq` it printed (cursor in `~/.vfg/cursor`), then follows; reconnects on SSH drops; never exits on its own. `--after <seq>` starts after that seq, prints every line after it, on its first connection and on every reconnect, with no catch-up limit, and reads and writes no cursor: the brain keeps its own place |
| `vfg say "<text>" [--to <player>] [--task <name>]` | `tellraw` to everyone or one player, with the prefix `[AI] ` in aqua (`VFG_CHAT_PREFIX`), and stores the text as an `ai` line (§4), and feeds it as an `AI say <name\|->` line (§7), in the same SSH call |
| `vfg cmd "<command>"` | One server command, through the `command` action; prints Minecraft's reply |
| `vfg history [--since <iso\|-10m>] [--until <iso>] [--player <name>] [--class <c>] [--source voice\|chat\|ai] [--events] [--limit N]` | Queries the transcript history, or `events` with `--events` |
| `vfg watchers set <kind,…> [--players a,b] [--contains <regex>]` / `vfg watchers show` | Writes or prints `watch.json` |
| `vfg lookout set "<text>"` / `vfg lookout show` | Writes or prints `lookout.md` |
| `vfg brain start\|stop\|status` | Starts, stops or checks the brain (§9), a background process on the owner's PC: `start` runs `brain/run` detached, its log in `~/.vfg/brain/brain.log` and its pid in `~/.vfg/brain/brain.pid`, and when one is already running prints its pid and succeeds; `stop` sends SIGTERM to the brain alone, so in-flight calls can finish, it can stop its implementers itself (their CLIs are in its process group) and close or fail their tasks, and SIGKILL to the group after 15 s; `status` also lists the open tasks, oldest first, read from the box's `tasks` table, one `open   <name> <player\|->: <description>` line each, or `open   none`, or `open   ? (<why>)` when the read fails; its exit code is still the brain's |
| `vfg context [--since <iso\|-6h>] [--json]` / `mark <seq> …` | The shared context (§9): the feed's rows since then, oldest first, `--json` one `{"seq", "at", "line", "processed_at"}` per line, then `{"tasks": [row, …]}`, every row of the box's `tasks` table (§4) oldest first, `made` and `variables` decoded, then `{"last_seq": N}`, the feed's highest seq (0 for an empty feed), with rows or none; or marks rows processed, setting `processed_at` where it is empty, any number in one SSH call. ## 9. The brain — the owner's PC

**The brain replaces the conversation, the orchestrator agent and the dispatcher.** Its entry point is the executable `brain/run`; `vfg brain start` runs it detached. It is one async loop: it follows the feed with `vfg watch --after <seq>`, and a player's lines take turns (below), every turn its own asyncio task, so different players' lines never wait for one another. It runs two agents: the brain's loop, one `structured()` call a step, which does as tools of its own what the orchestrator call and the retry planner did; and Respond.

- **Events.** An `action_oriented` LINE is one loop. A `conversational` LINE is one Respond call, and one loop when Respond hands it up. An implementer's report is one loop. There is no other call. A GAME line, a SYS line and the brain's own `AI` lines are context only. A `context` LINE is not even that: no model is shown it (below). A LINE already in the feed when the brain reads its context (at or below the `last_seq` it gives) and more than 2 minutes old then is history and is never acted on; a LINE that arrives on `vfg watch` after that is live, whatever its time.
- **One turn per player.** A player's live lines run one at a time, in the order they came, whichever agent takes them; different players' turns run at once. At most `VFG_TURN_WAITING` (3) lines wait for a player's turn. One more is turned away: marked processed, never answered, and that player alone told which lines still wait, by `vfg say --to <player>` (`Still on: “a meteor staff”, “and a shield”, “and a bow”. I can't take any more right now — wait a bit, then ask again.`, one chat line under 200 characters). A line Respond hands up runs in the same turn. A hand-off ends the turn as soon as the implementer is started. An implementer's report waits for its task's player's turn at the front of their queue, behind only the reports already there; it is never turned away and not counted in the three, and a task with no player has a lane of its own. A turn ends when its run returns, raises or is cancelled, then waits at most `VFG_TURN_SETTLE_S` (3 s) for the `AI` rows it wrote, a whisper and a row whose write failed apart, to come back on the watch, so the player's next loop reads them; a run that raised or was cancelled skips the wait. A turn's clock starts as it begins: a loop's limits and its time to the reply count from there, Respond's call and the world read included. A stop drops everything waiting: a line dropped so is marked read and never answered, after a restart too, and a report dropped so closes its task in code.
- **A loop** is steps until one ends it. At its start it takes in what no call has read (processed marks, below), reloads the actions and reads the world once; then each step is one `structured()` call (`lib/py/vfg_llm.py`) on `VFG_BRAIN_MODEL` (`google/gemini-3.8-flash`, reasoning `low`, `VFG_BRAIN_TIMEOUT_S` 45 s, its resend and retries included), answering one `Step`, whose schema never changes and requires every property, its default included: `actions` from the menu, each written in full (§14), and `order`, `together` (all at once) or `in_turn` (one after another, stopping at the first that does not land); `read_items`, players whose items to read; `hand_offs`, new tasks, each a name, a description and the brief in parts; `follow_ups`, each a task by its name with what to change and its new description (empty: it stays), or `cancel`; `end`, one of `next`, `reply`, `silent` and `handoff`; `reply`, the chat line; `record`, the loop's one record; and `status`, a report's loop's. What code cannot carry out, or would carry out wrongly, is a validator, which `structured()` sends back once: an action not on the menu or values its action refuses, an ending with nothing to end on, a hand-off's name or a brief with a part left empty, a follow-up with no brief, a reply over 300 characters (a hard cap over the prompt's soft 200), a reply that promises work when the step ends `reply` and starts nothing, and on the last step any action or read. What would have no effect is dropped and logged instead (a status outside a report's loop, a reply or a record on `next`, a reply on `silent`, reads under an ending), and a hand-off or a follow-up under `reply` or `silent` makes the step's ending `handoff`.
- **Send if all land.** `reply`, `silent` and `handoff` mean: if every action of this step lands, send the reply, write the record, open the tasks and start their implementers, and the loop is done, with no further call. `next` means: run these, and show me the results. An action lands when it ran without an error: `vfg action run` checked its values and Minecraft did not refuse it. A step that does not land, or ends `next`, sends nothing, no reply, no record and no task, and the next step's prompt holds every earlier step and what each of its tools came to: `landed`; `changed nothing` (it ran, but its facts' `changed`, what it changed, is empty: an `edit` to values the copy already has, an `incantation_edit` to what the entry holds; not landed, so a reply written up front never claims it); `refused`, with why (refused before it ran, by the brain's check or by vfg's; a player not online; or Minecraft's error with the reference of every command it used, from `refs/`); `did not run` (vfg could not run it, the box out of reach or the action not deployed: nothing happened, and it may be run once more); `failed` (it timed out or partly happened: it may have happened); `not run` (in turn, after one that did not land); or `read`. Nothing is retried in code.
- **Reading a player's items** is a tool: the speaker's items by slot are in every step's prompt (a report's: its task's player's), and another player's come back to the next step, from a `vfg state --json --items` fetched for that read and waited for up to 15 s, its own fetch's answer and never a state from before the step's actions; a fetch that fails is a refused read. A read goes with `end` `next`.
- **The limits**: at most `VFG_LOOP_STEPS` (10) steps and `VFG_LOOP_SECONDS` (120 s) a loop. The step that starts at the 10th, or once 120 s have passed since its turn began, is the last: no action, no read, and an ending of `reply` or `handoff`, a reply in the player's terms that never mentions steps, time or limits. A loop ends with a reply, silence or a hand-off, or fails: a step whose call fails for good ends it, the line's player hears what landed and the error in one chat line of at most 200 characters, and code writes the record of what its steps ran. An answer that failed its checks twice is never put in the check's words: `<player>: sorry, I got tangled up on that one — say it again?`, or `<player>: done: <what landed> — then I got tangled up on the rest, say it again?`; any other failure keeps its short reason, `<player>: that errored out — <why>`, or `<player>: done: <what landed> — then that errored out: <why>`. An error nobody expected is said once in the same shape, unless the reply already went out; a report's task closes on the implementer's status with a record and a chat line written in code.
- **A hand-off**: code makes its name (the thing, then whose: `frost_bow_alex`; never `cast` nor a library action's bare name) free of every task, action, script folder and running copy and of `cast`, adding `_2`, `_3` …; renders the brief from its parts, under `THE PLAYER'S WORDS`, `THE WHOLE PICTURE` (how it behaves, looks, sounds and feels), `WHAT THE PLAYER TAKES FOR GRANTED`, `HOW IT IS CAST, AND FOR WHOM` and `DONE WHEN` (the checklist, one `- ` item a line); opens the task with it (§4); posts `AI task <name> | new: <description>`; and starts its implementer (§10). The turn waits for none of it to finish. A hand-off whose task would not open is never promised: the reply is a line written in code instead (`sorry, I couldn't start “<the player's words>” — say it again?`, after what landed `done: <what landed> — but I couldn't start …`), and the record says so.
- **A follow-up** names a task under TASKS; a task that does not exist is refused at the tool, and the refusal comes back as a result. The task opens again with its new brief, and its new description when the step gave one, `AI task <name> | follow-up: <brief>` is posted, and its implementer gets the brief: behind its running implementer, then resuming its session; with no session (after a restart), a new implementer starts on the description and the follow-up. **A cancel** ("never mind") is a follow-up with `cancel`, never a stop: code sends the cancel words of Prototype_Implementer_Harness, `CANCELLED: the player said never mind. Stop building and put everything back the way it was before the run this cancels, then report Cancelled: and what you put back.`, which become the task's brief; the description stays, and the row says `follow-up: never mind — put back what its last run built`.
- **Edit and stop** are actions of a step (§14), with no task: `edit` changes values of a copy under RUNNING NOW, `stop` ends one copy, each checked against `running.json` as it is when it runs, a copy that is not running refused. A stop never changes a task's status.
- **The ending, in order**, once its step landed: the hand-offs' and follow-ups' tasks and their `AI task` rows; a report's `AI result` row; the reply, through `vfg say … --task <name>` (the reported task, else the first opened, else the first followed up); a line's loop's record; then the implementers started and the follow-ups sent.
- **What a loop leaves in the context** is one short record, what was done and what failed and why (`gave KrownJM's axe Fire Aspect 5 by item modifier; /enchant refuses a level over the maximum`): `AI action - | <record>` for a line's loop (the step's, else written in code from what vfg ran; none when nothing ran and the step wrote none), the `AI result` row for a report's; its reply as the AI's `say` line; and the `AI task` rows of its hand-offs and follow-ups. Its steps, its tool calls and their results stay inside it: no row is written per action, and none for an edit or a stop.
- **A report's loop** reads the report whole, its done-when items included, with the task's name, player, words, description and latest brief. It writes the player's chat line (always one: written in code from the player's own words when the step gives none), one `result` line (`castle_steve done: castle built at spawn`) and the task's status, and may act on it, a follow-up of the same task among them when something the player asked for did not land. While a follow-up to the task runs, one the loop sent included, the task stays open with the record as its result so far.
- **Respond** is the brain's cheap mode, on `VFG_RESPOND_MODEL` (DeepSeek V4 Flash, reasoning off), reading the same context. It replies, or hands the line up to the brain and says nothing itself — never both — and never acts on the game. A Respond call that fails, or runs past `VFG_RESPOND_TIMEOUT_S` (20 s), hands the line up.
- **The shared context** is the feed (§7), `feed` in `vfg.db` (§4): the whole conversation, with the world — every online player's position, health, food, armor, XP level, game mode and effects (`vfg state --json --items`), the items by slot of the loop's player alone (Respond's: nobody's), the running copies, the saved places, the time and the weather — and TASKS, every task on the server, open and closed. The brain's loop sees RUNNING NOW and TASKS in full: every value of each copy, its limits or choices, live or restart, and who started it; each task's status, when it was last written, its description, what it made, its copies running now and its last result. Respond sees one line a copy and one line a task, `- <name> for <player|nobody>, <status>: <description>`, the status `an implementer is on it` while one runs (`TASKS: none yet` with none). A loop reads it whole once, at its start, for all its steps, and every Respond call reads it whole, but for the `context` LINEs: those stay in the feed and `vfg.db`, for a later memory, and are never shown to a model, neither in the conversation nor as new rows. Every GAME row is shown. On the AI side only the brain writes to it, through `vfg say` and `vfg feed post AI`; nothing an implementer writes is in it.
- **Processed marks.** Every loop, at its start, and every Respond call take in every row not yet processed and mark it, `vfg context mark`, so the game events since the last read are its new rows. A `context` LINE is marked as it arrives, and at a start every one still unmarked, so nothing waits on it. Nothing else is read: what arrives after a loop's start waits for the next read.
- **Caching.** A step's fixed opening (the rules, the menu, every library action in full, Minecraft's command list), then the conversation in blocks marked at stable checkpoints (every `VFG_BRAIN_CHECKPOINT`, 5, blocks; the last two for a step, the last three for Respond), then the tail, read once at the loop's start and fixed for its every step, then one block per earlier step. The last block is marked (the tail on the first step), so each step's prompt is the next step's cached prefix; at most 4 marks in all. Then the step line, its number and the time used, never cached. On the replay of the 2026-10-11 session (`integration/replay/loop/report.md`, this branch's code after its first fix round) a loop's first step read 96.4% of its prompt from the cache and a later step 96.6%; live on realmc (after its second fix round), 95% of a 32–35K-token prompt.
- **Tasks.** Only an implementer's work is a task. The brain keeps its tasks in memory, keyed by name, and writes every change of one as its whole row through `vfg task set` (§8) in the background, one task's writes in the order they were made; a write that fails is sent again after 2, 5, 15 and 30 s unless a newer change carries the row first. It reads them at a start, from `vfg context --json`, and again when the feed restarts: a row the memory lacks is added, and one the read lacks (a box provisioned again) or holds older than the memory (a write that never landed) is written back. A report merges what the implementer made into the task's `made`, keeps its `DESCRIPTION:` line as the description (§10), and reads the task's `variables` from its action, the one named as the task, else the last it made that is loaded; they are read again whenever that action's file changes. At a start, every task still open fails (`<name> failed: interrupted, the brain restarted while it ran`); at a stop, every task whose implementer it stopped (`<name> failed: stopped, the brain stopped while it ran`), and the writes still going out get 5 s. `vfg route --task` reads one row and `vfg brain status` the open ones.
- **Files**, in `$VFG_BRAIN_DIR` (default `~/.vfg/brain`): `lock`; `brain.pid`; `brain.log`, one `<ISO time> <area> <message>` per line, among them a line a step, `brain <ref> s<n> <spent> | <what it did> -> <what came of it>` (`brain <ref> s<n> FAILED (<spent>): <why>` for a call that failed), and a line a loop, `loop <ref> <player|nobody>: <n> step(s), $<cost>, <rate> cached, reply at <s> s, <s> s, ended <reply|silent|handoff|failed|cut off|broke>`, and a line for each line or report that waited for its turn, once it takes it, `turn #<seq> <player> waited <s> s for their turn` (`turn report <task> waited <s> s for their turn`); and `refs/<version>/`, the server's command tree and the wiki's command pages, fetched once per server version. A `tasks.json` an older brain left there is renamed `tasks.json.retired-<YYYYmmdd-HHMMSS>` at the start, never read and never deleted.
- **Usage**: every model call is a `usage` row of its own, written by `structured()` (§4): `brain`, one a step, `ref` `#<seq> s<n>` (a report's loop: `<task> s<n>`, the name cut to 56 characters), and `respond` (`#<seq>`), failed calls included. The brain logs what each call spent, a failed one too, and sends the queue after each step's call and each Respond call, at its start and at its stop (`vfg usage flush`, nobody waiting; never two at once, one asked for while another runs running once when it ends); `implementer` rows, one per implementer run, its `ref` the task's name, it writes with `vfg usage add`.

## 10. Implementers, actions and the scripts folder

- **An implementer is started by code from the brief of the brain's hand-off, one per task** (§9): a Claude Agent SDK query on Haiku 5.5, logged in with the owner's Claude subscription. Its brief is the hand-off's, rendered in parts under their headings, `DONE WHEN` last, then `YOUR TASK: <name>`, the name everything it makes takes (its script and its action, `vfg script new <name>`, and its copy, `as=<name>`; every `vfg action run` it sends takes `--task <name>` and every `vfg place save` `--by <name>`), `SAVED PLACES: …` (§14), read fresh, and the example scripts and presets `vfg route --task <name>` picks. A follow-up to its task resumes its session, or waits behind it while it runs, so two implementers never edit one script; it may change its task's own script in place even while copies of it run. A cancel is a follow-up whose text is the cancel words (§9): the implementer puts back what it built and reports `Cancelled:` and what it put back, a report read as done. A brief's `DONE WHEN` is the implementer's check: it checks each item before it reports, and its report says, item by item, which landed and which did not. Its last message is its report, to the brain alone; it never talks to a player. The report's last line, `DESCRIPTION: <what the thing is now, for whom, how a player uses it>`, is taken off it in code and kept as the task's description (at most 600 characters; with none, the one the brain wrote stays).
- **What a task made** is recorded by the guard from the commands it lets through (`vfg script new`, `vfg script save`, `vfg preset save`, and each copy `vfg action run … as=<copy>` starts) and the new action and preset files it lets the implementer write, each script, action and preset kept only when its file is on disk: `{"scripts", "actions", "presets", "copies"}`, given with the report and added to the task's `made` (§4). The guard refuses every `vfg task` command: only the brain writes the tasks.
- **Implementers act on the server only through actions**: `vfg action run|list|check`, its shortcuts `vfg cmd`, `vfg script set|stop` and `vfg place save`, and `vfg script new|check|list|logs`, `vfg preset save` and `vfg place list` (§8). The ladder: run an action; change a running copy; a new script and its action; a new preset.
- **The last step of any build players may want to go back to**, once it is checked, is `vfg place save <name> --at <x> <y> <z> --by <task>`, at the spot a player should arrive: the name the brief gives, else a short lowercase one (`castle`, `steve_house`).
- **Four layers, code in one**: the kit (`scripts/_lib/`, imported), presets (`scripts/_presets/<name>.py`, copied into a script), scripts (`scripts/<name>/main.py`, the code) and actions (`actions/<name>.py`, called). What implementers make goes in `made/<server>/scripts/`, `presets/` and `actions/`, under names the library does not use.
- **An action** is one pydantic class in its own file, named as the file (`gatling_gun.py`: `class GatlingGun`), with no code: its docstring's first line is its line on the menu; `script`, `runs` (`once` or `until_stopped`), `takes` (the fields the brain fills), `defaults`, `fixed`, `descriptions` (its own words for a field it inherits, whose type and limits stay) and `timeout_s`; and a field for every value the script reads, its type from `actions/_types.py`, its default, its limits (`Field(ge=, le=)`) and its description under it. `Live[T]` marks a value the script reads again while it runs. A variant subclasses an action. A preset's values are a class beside its function, `class <CamelName>(Values)`, which the action over every script that copied it inherits (`preset("<name>")`). Every value is checked on the PC; the box gets plain JSON.
- **A script** is Python 3.12, standard library only, with `kit`, `mc` and the rest of `scripts/_lib/`; line 1 its docstring, `"""<Title>: what it does."""`; line 2 `ASKS`, what players said. `v = values()` gives its copy's checked values (a `Live` one read again at most every `VFG_LIVE_POLL_S`, 0.5 s); `result(summary, **facts)` is its answer.
- **A copy** is one run of an action. On EC2 it runs as `/opt/vfg/python/bin/python3 -u <folder>/main.py`, its folder the working directory, with `PYTHONPATH=/opt/vfg/scripts/_lib`, `VFG_SCRIPT` and `VFG_INSTANCE` its name, `VFG_TASK` (the name of the task that started it, empty for the brain's own copies, or `cast` for an incantation's; `mc.task()` reads it, `""` for the last two), `VFG_RUN_DIR`; everything it makes carries the tag `vfg_<copy>`, taken away by a stop; a copy that ends by itself keeps what it made, handed over to the tag `vfg_left_<copy>`, which no stop takes (`kill @e[tag=vfg_left_<copy>]` clears it). Its files in `/opt/vfg/run/`: `<copy>.pid`, `<copy>.log`, `<copy>.json` (`{"copy", "action", "script", "source", "server", "values", "live", "runs", "task", "started"}`, `task` a task's name, null or `cast`), `<copy>.values.json` (an edit's live values), `<copy>.result.json` (`{"summary", "facts", "at"}`, the last `result()`) and `<copy>.error` (the last line of an error nothing caught, which `mc.py` writes as it cleans up). `scripts/_lib/instances.py` starts, stops and edits copies, for `vfg` and for the `stop` and `edit` scripts.
- **Incantations** are actions too: `incantation_create` (`player`, required, a name, several or `@a`; `phrase`, a word or more; `action`, from the menu; `values`, its defaults for this phrase; `cooldown_s`, default 3), `incantation_edit` (by `player` and `phrase`: `values`, `cooldown_s`, `aliases`) and `incantation_remove` (by `player` and `phrase`), over one script, `incantations`, which writes the store `/opt/vfg/incantations.json` (`{"version", "incantations": [{"id", "player", "phrase", "aliases", "action", "script", "source", "server", "values", "asked", "live", "runs", "caster_fields", "cooldown_s", "created", "by"}]}`, one entry per named player, `@a` one; `scripts/_lib/incantations.py`). vfg checks the bound action's values as a run would, makes every player field left out a caster field, makes the aliases (one `structured()` call, `VFG_INCANT_ALIAS_MODEL`, its usage row `alias` with the phrase as its ref and sent by `vfg usage flush`, and the phrase joined and split, at most 12), adds a note when the phrase is short, is everyday talk (the alias call says so), or sounds like, or starts like, another of that player's, and deploys the bound script before the store is written. `values` are every value a cast runs with; `asked`, the ones the player asked for, caster fields apart: after a `vfg action run` of the bound action that went well, a binding whose `values` differ from `asked` over the action's defaults as they are now is made again from them (decided from `$VFG_HOME/incantations.json`, no SSH while none differs). A value of the bound action may be given as a word of its own, `values.<name>=<value>`: text for a field that takes text, else read as JSON.
- **The six core actions**, each over a script of its name: `command` (up to five server commands in order, the refused list of `scripts/_lib/commands.py` applied), `teleport`, `summon_around`, `save_place`, `stop` and `edit`. Every library script has at least one action, and every script an implementer makes gets one (`vfg script new` writes both; `vfg action check` passes).

## 11. Secrets

- On EC2, `TYPESAFE_API_KEY` and `VFG_CLIENT_TOKEN` live in `/opt/vfg/.env` with mode 600. On the owner's PC they may live in the `.env` file `VFG_BOX_ENV` names (default `~/.vfg/box.env`, mode 600, outside any repo). `deploy.sh provision` and `deploy.sh env` send only the names `env.example` lists, over SSH on stdin, and make the client token on the box when none is given.
- On the owner's PC, settings live in `~/.vfg/config`. The client token also lives in each player's mod config. The OpenRouter key is `OPEN_ROUTER_API` in the environment, or alone in the file `VFG_OPENROUTER_KEY` names (default `~/.vfg/openrouter.key`, mode 600); the config holds the path, never the key, and only `structured()` reads it.
- The RCON password never leaves `server.properties` on EC2.
- No secret goes in the repo.

## 12. Startup — the brain sets everything up

1. The owner runs `vfg brain start` (`brain/run`).
2. The brain sets aside a `tasks.json` an older brain left in its folder (§9), then runs `vfg up`, then `vfg watchers set …`, then `vfg lookout set …` and `vfg jev menu set …`, its actions for Jev's state (§5); it sets the menu again whenever an action is added. It sends the usage rows queued while it was down, `vfg usage flush` (§4).
3. It reads the context with `vfg context --json`, the feed's rows and then its tasks, every row of the box's `tasks` table, fails every task still open (§9), and follows the feed with `vfg watch --after` the `last_seq` that gives, so nothing is lost across a restart and nothing older is read as new. A read that fails is tried again; the feed is never followed from 0.
4. It greets the players with `vfg say`, skipped when nobody is online.

## 14. Actions from the brain — the owner's PC

**A step of the brain's loop runs its actions** (§9), each written in full in its answer: `vfg action run <action> key=value … --for <player>` (§8), reading its one line; `together` all at once, `in_turn` one after another, stopping at the first that does not land. It carries no task: only an implementer's work is one. `--for` names the copy `<action>_<player>`, then `_2` while that one runs (`command_steve`), the player being the action's `player` value when that is one player's name, else the speaker (in a report's loop, the task's player); with neither, there is no `--for`, and `edit` and `stop` never take it. Its values are checked first, as vfg checks them. Nothing is retried in code: a command Minecraft refuses, or a value vfg refuses, goes back to the next step, Minecraft's error with the reference of every command it used (the server's command tree and the command's wiki page, from `~/.vfg/brain/refs/<version>/`), and that step fixes it; an action vfg could not run at all (the box out of reach) goes back as `did not run`. No row is written per action: the loop leaves one record (§7, §9).

- **The menu** is every action (§10), the library's and `made/<VFG_SERVER>/actions/`, each as its name and docstring's first line, reloaded when a file changes, so a new action is on it at the next loop. Every library action is in a step's opening in full (its docstring, how it runs, each field it fills), and this server's own in the tail. The running copies are RUNNING NOW, in the world: each copy with who started it and every value of its action, its value now, its limits or choices, live or restart, from `running.json`, which a background `vfg script list --json --fresh` fetches every `VFG_RUNNING_TTL_S` (30 s), and again after a step runs an until-stopped action, an edit or a stop. `edit` changes a copy's values and `stop` ends a copy, by its name there.
- **An item a player owns** is changed by its slot, which the world names (`hotbar.4 iron_sword (held)`): the speaker's items are in every step's prompt, and another player's come from a step's read. The held one, then the worn one, then the first listed; for an item the player does not have, nothing runs and the reply says so.
- **Saved places** live in Minecraft's command storage `everhear:places`, one entry per name (`^[a-z0-9_]{1,32}$`): `{pos: [x, y, z], dim: "minecraft:overworld", by: "castle_steve"}`, whole blocks, `by` the name of the task that saved it (`""` when none did; an older entry's task number still reads). Only `vfg place` and `scripts/_lib/places.py` (which the `save_place` and `teleport` scripts, and a `Place` value, use) read or write them. Every prompt — the brain's, every implementer's brief — carries them as one line: `SAVED PLACES: castle 197 68 251 overworld (castle_steve); …`, or `SAVED PLACES: none`.
- **`command` places or removes no block**: it refuses `setblock`, `fill`, `clone`, `place` and `fillbiome`, alone or after `execute … run`, and the owner's commands, one list in `scripts/_lib/commands.py`, before anything is sent. Building is a script's, through the kit, which spares protected places.
- **Settings**, from the environment, then `~/.vfg/config`: `VFG_BRAIN_DIR`, `VFG_BRAIN_MODEL` (`google/gemini-3.8-flash`), `VFG_BRAIN_REASONING` (`low`), `VFG_BRAIN_PROVIDERS` (none: OpenRouter's choice), `VFG_BRAIN_TIMEOUT_S` (45 s a step's call, its resend and retries included), `VFG_LOOP_STEPS` (10), `VFG_LOOP_SECONDS` (120), `VFG_TURN_WAITING` (3), `VFG_TURN_SETTLE_S` (3), `VFG_RESPOND_MODEL`, `VFG_RESPOND_REASONING`, `VFG_RESPOND_TIMEOUT_S` (20 s a Respond call), `VFG_BRAIN_CHECKPOINT` (5), `VFG_BRAIN_HISTORY_HOURS` (6), `VFG_DISPATCH_ACTION_TIMEOUT_S` (20; an action's `timeout_s` wins), `VFG_RUNNING_TTL_S` (30), `VFG_SERVER` (`main`), `VFG_OWNER`, and the OpenRouter key (§11). The `VFG_ORCHESTRATOR_*` and `VFG_PLAN_*` keys went with the orchestrator call and the retry planner; one left in `~/.vfg/config` is ignored.
