## 1. Where things run

- **EC2** (one Amazon Linux 2023 instance): the Minecraft Java server, vanilla 26.3 with the engine's datapack, in `/opt/mc`, systemd unit `minecraft`, its console written to `/opt/mc/console.log`; the **bridge** (`vfg-bridge`) and the **Jev filter** (`vfg-jev`) in `/opt/vfg`; the **game engine** (`vfg-engine`) in `/opt/vfg/engine/`, the library, the server's base content, in `/opt/vfg/engine/library/`, this server's own in `/opt/vfg/made/<server>/content/`, and its datapack in `/opt/mc/world/datapacks/everhear/` (below); the database `/opt/vfg/vfg.db`, the transcript history and the brain's tasks (§4); the feed `/opt/vfg/feed.log`. Open to the internet: Minecraft `25565` and the bridge's speech port `8787`. SSH only from the owner's IP. RCON `25575` is never reachable from outside — vanilla binds every interface, so the security group and a host firewall rule keep it in; nor are the test server's ports (below). Every unit runs as `ec2-user`, which owns `/opt/mc` and `/opt/vfg` (the database and its `-wal` and `-shm` files included), and `/opt/mc-test` and `/opt/vfg-test`, and has passwordless `sudo` for `systemctl`, `journalctl` and `systemd-run`, as Amazon Linux 2023 sets it up.
- **Players' PCs**: Minecraft Java 26.3 with Fabric and the **client mod**.
- **The owner's PC**: this repo; the **`vfg` toolkit**; the **brain** (§9), with its conversation agent and its router, and the **implementers** the brain starts; the **actions** `actions/`, the brain's menu of the engine's ops (§14); `made/<server>/content/` and `made/<server>/tests/`, what implementers made (§10). It reaches EC2 only over SSH; the brain also calls OpenRouter, and an implementer its model's provider (§10).
- **The test server** (below): a second Minecraft server on the box, with Carpet's fake players and the `.vfg-test-server` marker, where an implementer's test runs on an engine of its own (§10), never the live one; `VFG_TEST_BOX` (§8) names another, or none.

Every timestamp is ISO-8601 UTC with milliseconds (`2026-10-07T18:22:31.412Z`). Every id is a ULID unless stated.

**The units** start the server jar in `/opt/mc` (`minecraft`), `/opt/vfg/python/bin/python3 -m vfg_bridge` (`vfg-bridge`), `/opt/vfg/python/bin/python3 -u /opt/vfg/jev/jev_filter.py` (`vfg-jev`), the test server in `/opt/mc-test` (`minecraft-test`, below) and, after `minecraft`, `/opt/vfg/engine/.venv/bin/python -m vfg_engine` with `PYTHONPATH=/opt/vfg/engine` (`vfg-engine`): SIGTERM stops it with its state saved (exit 0); exit 1 (a crash, or Minecraft not up yet) is started again in 5 s; exit 78 (a setting it refuses) is left stopped. `ec2.sh stop` and `retire` stop `vfg-engine` first, so it saves while Minecraft still answers. The live server's heap (`MC_HEAP`, its `-Xms` and `-Xmx`, in the drop-in `minecraft.service.d/heap.conf`) is the box's memory in whole GiB, rounded up, less 4, less the test server's `MemoryMax` in whole GiB, rounded up (3), where the test server is installed (its marker and its unit; a box where it failed keeps the 4 GiB rule): 9G on an `m7i.xlarge`. `deploy.sh provision` sets up the test server before the heap and restarts the live server when it changes; the test server's setup writes it too and never restarts the live server, so there it applies at the live server's next restart.

**The test server**, for implementers' tests (`vfg test`, §8, §10), is a second Minecraft server on the same box, which nobody joins: the live server's `server.jar` (a sha256-equal copy, never a link) with Fabric Loader and Carpet, for its fake players, each pinned by hash, in `/opt/mc-test`, unit `minecraft-test`, its console `/opt/mc-test/console.log`; its game port `25566` on `127.0.0.1` and RCON `25576`, with its own random RCON password, both dropped off loopback by the nftables table `inet vfg_test`; and its vfg folder `/opt/vfg-test` (`python`, a link to `/opt/vfg/python`; `tests/`, `made/`, `run/` and `state/`, the test engine's state in `state/engine`; `protected.json`; no `.env`); a test's engine is the live box's (`/opt/vfg/engine/`: its venv, `vfg_engine/` and library, read only). A sandboxed test runs as the system user `vfgtest` (no login, no home), never as `ec2-user`, the live services' uid, whose processes' files and environments (`/proc/<pid>/cwd`, `/proc/<pid>/environ`) the same uid could read: `ec2-user` is in its group, which owns `/opt/vfg-test` (`2755`: read, not written), `run/` and `state/` (`2775`, the only folders it writes) and reads `/opt/mc-test/server.properties` (`640`) and the marker; `python`, `tests/` and `made/`, which `ec2-user` writes, stay `755`. From `vfgtest` nothing goes out but TCP to the test server's RCON on `127.0.0.1`: the table's output chain refuses the live server, the bridge, every other port and anything off loopback. Its marker, `/opt/mc-test/.vfg-test-server` (`{"made", "rcon_port", "port", "live_mc", "live_vfg", "vfg", "test_user"}`), is written only by its setup (`bridge/deploy/testserver.sh` and `testserver.py`, which `deploy.sh provision`, `deploy.sh testserver` and every `deploy.sh` run), which refuses a live folder that has one; nothing runs a test on a server without it. **Every start of the unit is a fresh world**: `reset.sh` (`ExecStartPre`) puts a copy of `world.template/` in place of `world/` (seed `20261009`, the sky stage's chunks generated and forceloaded, the world spawn on it; made once by the setup, and again with `--fresh` or a new live jar), copies the live `world/datapacks/` in, the engine's among them, and writes the token `world/vfg-fresh`. It runs at `Nice=10`, `CPUWeight=20`, `CPUQuota=200%` (two of the four vCPUs stay the live server's) and `IOWeight=20`, `-Xms256M -Xmx1536M` with two CPUs' threads, the C1 compiler only and an AOT cache of a start (`/opt/mc-test/test-server.aot`, made by its setup), `MemoryMax=2560M` and `OOMScoreAdjust=800` (the kernel kills it before the live server), reads the live folders and never writes them (`ReadOnlyPaths`), restarts always (given up after 30 starts in 5 minutes, which `vfg test` resets), and is enabled at boot; `vfg up` starts it with the others where it is installed, and `ec2.sh stop` stops it first.

**Python on the box** is 3.12, the PC's version: uv, installed into `/opt/vfg/uv/` as a step of the box's setup (`deploy.sh provision` runs `bridge/deploy/python.sh`), installs CPython 3.12 there, and `/opt/vfg/python` links to it. `/opt/vfg/python/bin/python3` runs the bridge, Jev and every `vfg` remote program; Amazon Linux's own `python3` (3.9) is left to the host's tools. The game engine alone has packages: its own venv, `/opt/vfg/engine/.venv`, on that Python, made by `engine/deploy/install.sh` with the box's uv and synced exactly to `engine/deploy/requirements.txt` (pydantic 2.14.0 and its four dependencies, wheels only, every file checked by its hash), on which it runs its content and its kit. The bridge and Jev stay standard library only.

**The game engine** (the game engine spec, `Specs/2026-10-12-Prototype_Game_Engine`; [`engine/README.md`](../engine/README.md)) is one process and one loop, `VFG_ENGINE_TICK_HZ` (10) ticks a second. Each tick reads the datapack's numbered event queue, a page of at most 12 events, and a snapshot of every online player in one RCON read (`TCP_QUICKACK` after every receive, so a reply in several packets costs no 40 ms each), runs the scenarios, the events, the abilities and the marks in that order, and sends what they queued as one batch. Players come only from the snapshot; every other entity within `VFG_ENGINE_MIRROR_RADIUS` (32) blocks of a player comes from the mirror, a second thread's pass every `VFG_ENGINE_MIRROR_S` (0.1 s), which leaves players out. It is the only writer of `/attribute`, and only by `everhear:` ids (`everhear:item/<id>`, `everhear:mark/<id>`, `everhear:ability/<id>`, `everhear:actor/<id>`); it never sets an attribute's base and never clears a potion. A content call over `VFG_ENGINE_SLOW_MS` (5) of its own time is logged, and so is one that waited over 50 ms on Minecraft (flagged slow as one over its own time is); over `VFG_ENGINE_CUT_MS` (50) of its own time it is cut, and only its instance ends. Each live read (`ctx.query`, the `ctx.world` reads) gets what is left of the call's 250 ms I/O budget as a deadline; past it, the read is given up in words (IoBudget), and the call's later reads are refused. `reload` with named files takes only files directly in a content folder (`VFG_ENGINE_CONTENT`, links and `..` resolved), as a full reload would load them; any other path is refused in words. An unreadable or unparseable protected file (`VFG_PROTECTED`) keeps the boxes last read from it, logged; they go only when the file does. A weather hold reads the weather first (two `execute if predicate` weather checks) and puts it back when the last hold goes; a read that answers neither "Test passed" nor "Test failed" is tried again next tick. A `give` that took starts its item's instance at once only where the item counts (the inventory; the main hand when no item of ours is in it); else the next snapshot does. It talks to Minecraft as every RCON client does, holding the box's RCON lock for each exchange, and refuses every command that is the owner's (`engine/vfg_engine/mc/commands.py`'s `REFUSED`: `stop`, `op`, `deop`, `ban`, `ban-ip`, `pardon`, `pardon-ip`, `whitelist`, `kick`, `save-off`), whoever sends it. It runs the classes in `VFG_ENGINE_CONTENT`, folders colon-separated, the unit's default `/opt/vfg/engine/library:/opt/vfg/made/main/content`, the library first: a class in a later folder replaces the library's of the same id (§10). Its files, in `/opt/vfg/engine/`: `vfg_engine/`, the package and its kit; `library/` and `examples/`; `.venv/`; `state.json`, every instance, grant, binding, world-setting hold and saved place (the places per world, §14), saved about once a second and on SIGTERM, from which a start rebuilds every instance and removes every `everhear:item/*` modifier nobody holds the item for (every few seconds it also removes, without loot, any entity tagged `everhear.actor` or `everhear.spawn` the mirror sees that nothing it runs owns: an actor whose chunk unloaded was taken as gone, and is swept when it loads again); `incantations.json`, the export of its bindings (§10); `engine.log`, JSON lines; `engine.sock`, its control socket, mode 600, beside `engine.sock.lock`, which holds the pid, so one engine runs a world. **The control socket** takes one request a connection: one JSON line in, `{"op", "args", "timeout_s"}` (10 s by default, `reload` 120, at most 600), handled on the engine's next tick in order with its other inputs, and one line out, the engine's reply, `{"ok", "error"?, …}`, or one the socket made itself, with `reason` (`bad_request`, `timeout` with `cancelled`, `stopping`, `failed`); a request its asker gave up on before it began is never carried out. The ops are `status`, `reload`, `classes` and `meta` (a scenario's and a mark's Args among them, and `shadows`, the library's file a class replaces, §10), `world`, `instances` (an ability lent, not granted, with `lent_by`), `grant`, `revoke`, `give`, `take`, `apply` and `clear` (a mark with its args), `start` (a scenario with its args, and `wait_s`, at most 30, for its result: a one-off's when it ends, one that goes on as soon as it reports one, `running: true` and the result) and `stop`, `spawn`, `places` and `places_import`, `bind` (to an ability, or to a scenario with its args) and `unbind`, `incantations` (each entry with its `by`), `cast`, `config_get` (with `shadows`, as `classes`) and `log` (their arguments and replies are in `engine/README.md`). `python -m vfg_engine.ctl` sends one from the box's shell: exit 0 ok, 2 refused, 3 not running, 4 no answer in time. The datapack keeps its state in Minecraft's command storage, `everhear:meta`, `everhear:events`, `everhear:out`, `everhear:mirror` and `everhear:io`, and the `everhear.*` scores ([`engine/datapack/README.md`](../engine/datapack/README.md)).

**The code** is one repo, a folder per part: `client-mod/`, `bridge/`, `jev/`, `toolkit/`, `brain/` (the conversation agent, the router, the brain's loops and the implementers), `engine/` (the game engine: its core, its kit `vfg_engine/kit/`, its Minecraft side `mc/`, the datapack, the library `library/`, the unit and its install), `actions/`, `lib/py/` (`structured()`, every model call that wants a structure back; `vfg_actions`, the one loader of the actions). What runs on EC2 is deployed to `/opt/vfg/` by `bridge/deploy/deploy.sh`: the engine, its library and its datapack go with every deploy, or alone with `deploy.sh engine`, which copies the datapack into the world and loads it when it changed. This server's content goes with `vfg engine reload` (§8). An action never leaves the PC: it is a class that names one of the engine's ops and checks its values (§14).

## 2. Speech in — client mod → bridge

`POST {VFG_BRIDGE_URL}/v1/lines`, header `Authorization: Bearer {VFG_CLIENT_TOKEN}`, body:

```json
{ "client_line_id": "uuid-v4", "player_uuid": "…", "player_name": "Steve",
  "text": "AI, build me a castle",
  "started_at": "2026-10-07T18:22:29.100Z", "ended_at": "2026-10-07T18:22:31.400Z",
  "peak_dbfs": -8.2, "mean_dbfs": -23.5 }
```

- `202 {"id": "<line id>"}` stored; `400` bad body; `401` bad token. The token is checked before the body, so an empty `{}` with a good token gets `400` — the mod's connection test relies on it. Repeating a `client_line_id` returns the first id and stores nothing. An empty `player_uuid` is stored as NULL, the same as an AI line.
- Plain HTTP is accepted for the prototype: the token only lets someone post lines.
- **Incantations** — a word or a phrase, bound for one player to one of the game engine's abilities (a cast of it) or to one of its scenarios with args set once (a start of it), fires the moment that player says it, with no model on its path (§10). The mod's keyword spotter, and Vosk beside it, hear it and post a **cast**, its own request, beside the line pipeline: neither waits on the other. One saying casts once, whichever of the two hears it first; the other posts nothing for that incantation over that stretch of audio.
  - `POST {VFG_BRIDGE_URL}/v1/casts`, the same token, body `{"client_cast_id": "uuid-v4", "player_uuid", "player_name", "phrase": "fire ball", "heard"?: "fireball", "started_at", "ended_at"}`: the incantation's own phrase (the mod maps a matched alias back to it), and the phrase's window on the mod's audio clock, the clock a line's times use. `202 {"id", "status": "fired"|"cooldown"|"duplicate"|"failed"|"stale", "error"?}` once the engine answered (below); `404` when the player has no such incantation, by its phrase or an alias; `400`, `401`; `503` when the history is busy, or the first request with its `client_cast_id` never finished. Repeating a `client_cast_id` answers what the first did.
  - A cast of an incantation whose window, widened by `VFG_CAST_SLACK_S` (0.3 s) each side, overlaps one of that player's that fired or is still `pending`, or one the spotter made whatever became of it, is `duplicate`; a cast the bridge has held `VFG_CAST_WAIT_S` (1.5 s) since its request came is `stale`, stored and never sent. The bridge keeps no cooldown and no gap between a player's casts: an incantation's cooldown is the engine's (below).
  - The mod's settings: `incantations` (on), `incantation_threshold` (0.25), `incantation_boost` (1.5), `incantation_paths` (16) and `incantation_spotter_aliases` (10: the spotter listens for each incantation's first 10 aliases of those listed), the spotter's, and `vosk` (on) and `vosk_confirm` (off), Vosk's; `heard` is the keyword the spotter matched, normalised (`fireball`), or the phrase itself when Vosk heard it (Vosk listens for the phrases only, not the aliases). Vosk's window is estimated (its partial results have no times), wider than the spotter's: from about 0.8 s before it heard the phrase to 0.15 s before. It spots only while it listens, and only that player's own incantations; no audio leaves the PC, only the phrase.
  - **A cast goes to the game engine** (§1): `{"op": "cast", "args": {"player", "phrase", "cast_id"}, "timeout_s"}` on its control socket (`VFG_ENGINE_SOCKET`), with the binding's own phrase and the cast's id, waited for at most `VFG_ENGINE_CAST_WAIT_S` (1 s) and never past `VFG_CAST_WAIT_S` since the request came; a cast the engine has not begun by then is taken off its queue, so it never fires late. That wait is outside the bridge's one cast lock, so no cast waits on another's: under the lock the cast is checked and its row stored `pending` (§4), the engine is asked, and the row takes its status; a `pending` cast decides its saying, so the same saying heard again meanwhile is `duplicate`, and a repeated `client_cast_id` waits for the first request and answers what it did (`503` only when that request never finished). Its cooldown is the engine's, counted from the cast: an ability's Config's `cooldown_s`, or a scenario binding's own `cooldown_s` (3 s unless it was bound with another). The engine's `fired`, and `charging` (its charge-up runs, and it fires when done), answer `fired`; its `cooldown` answers `cooldown`, `error` `2.3 s left of its cooldown`; `not_granted`, `unknown`, `failed`, no answer in time and no engine answer `failed`, in words.
  - `GET {VFG_BRIDGE_URL}/v1/incantations?player=Steve&after=<version>&wait=<s>`: `200 {"version", "player", "incantations": [{"phrase", "aliases", "cooldown_s"}], "server_phrases": [phrase, …]}`, the engine's bindings for that player (the name in any case), one per phrase, at its export's version; `cooldown_s` an ability's Config's (`0` while the ability is not loaded) or a scenario binding's own; and `server_phrases`, every incantation phrase on the server, whoever's (the player's own and every other player's), normalised (lowercase, accents and apostrophes dropped, every other mark a space), once each, sorted: phrases alone, never aliases. The mod's speech-to-text boosts them as hotwords (below), since players talk about each other's spells; an older bridge leaves the field out, and the mod then boosts the player's own phrases; an older mod ignores it. With `after` the current version it is held until the export's file changes or `wait` (default 25, at most 30) seconds pass, then `304`. The version is the export's, which every change bumps whoever's binding it changed, so a held request answers when any player's incantations change, not only the asking player's. The mod long-polls it while connected. Each incantation's `aliases` leave out its `everyday_aliases` (§10), everyday talk of their own that would cast on ordinary conversation; Layer 2, the drop rule and the Jev cast check still use every alias. A missing or unreadable export has none: version 0, an empty list.
  - **Layer 2 and the drop rule, on `/v1/lines`.** For a voice line from a player with incantations, of at most `VFG_INCANT_LAYER2_MAX_WORDS` words (6, normalised, fillers counted; 0 any length: a longer line is talk and casts nothing), a phoneme match of the transcript against their phrases and aliases (`VFG_INCANT_ALLOWANCE`, 0.25) fires a cast through the same path, layer `transcript`, with the line's window; a one-word phrase's phrase and aliases match only from the start of a word of the line, and one of fewer than 6 speech sounds only as it is said, its mishearings left to its aliases. Then, on a line of any length, a line that overlaps one of that player's casts and has at most one word left once the phrase is taken out (fillers not counted) is stored with `dropped = 'cast'` and never judged or fed (§5); a kept one gets `cast_id`.
  - **The Jev filter's cast check, on a stored line (§5).** `POST {bridge}/v1/jev/casts`, taken only from the box itself (`127.0.0.1`, else `403`), with the same token, body `{"line_id", "phrase", "keep"?}`: the Jev filter judged that voice line, not yet judged or dropped, a cast of `phrase`, one of its speaker's (one the engine binds for them). It goes through the same path as every cast, layer `jev`, with the line's window (its `at` and `ended_at`) and `client_cast_id` `jev:<line id>`, so asking again answers what the first did; then the line is stored with `dropped = 'cast'` whatever became of the cast, and `cast_id` that cast, unless it did not fire and the line has a fired one already. With `"keep": true` (a line of more than 6 words, the cast said inside other talk, or a short one Jev is not sure of) the line is kept instead, to be routed as ever (Jev may ask after routing it; a kept cast is not refused for a judged line), and takes the cast's id as its `cast_id` when the cast fired and it has none; and a cast whose phrase the bridge's phoneme match (`vfg_bridge/sounds.py`, allowance 0.4) places, by word between the line's `at` and `ended_at`, more than 3 s before the line ended is `stale`, a phrase not found being allowed. A Jev cast never fires late: when `/v1/lines` received its line more than `VFG_JEV_CAST_MAX_AGE_S` (2 s) before, on the bridge's monotonic clock (kept in memory from the moment it came, for a player with an incantation; a line from before the bridge last started has none, and counts as too old), it is `stale`, with the line's age as its `error`, recorded and not started. `202 {"id", "status", "error"?, "line": "dropped"|"kept"}`; `200 {"line": "dropped", "cast_id"}` when the line was dropped already, and nothing is cast; `404` no such line, or no such incantation of the speaker's; `400` not a voice line, or a bad body; `409 {"line": "judged"}` when Jev judged it already; `401`, `403`, `503`. A fired or failed one is announced as every cast is (§7).
- The mod captures only while connected to the server whose address matches its configured `server_address`; a line captured then is still delivered after the player leaves, within its 60 s. A line is speech ended when the mod's turn model hears it finished, or by **`silence_seconds` of silence** (default 3). `text` is 1–2000 characters after trimming. On failure it retries with backoff for up to 60 s, then drops the line.
- **Speech-to-text** runs on the player's PC, through sherpa-onnx 1.13.8; no audio leaves it. The mod's `model` setting: `parakeet-0.6b-v2-en`, Parakeet TDT 0.6B v2 int8, the default (`parakeet-0.6b` and `parakeet-0.6b-v2` read as it); `parakeet-110m-en`, Parakeet TDT 110M int8, its fallback, for a PC short of memory (`parakeet-110m` reads as it); `moonshine-base-en`; `moonshine-tiny-en`; any other value is the default. The 0.6B is one download of 482 MB (`asr-models/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8.tar.bz2`, its size and sha256 pinned). While it is not installed (a first start, or the first start of 0.3.5), the 110M is installed if it is not (108 MB) and listens at once, and the 0.6B downloads in the background (`vfg-stt-upgrade`), a failed download tried again after 30 s, 2 min, then every 10 min; once it is in, its recognizer is swapped into the running engine. A broken-off download is carried on by a range request; a part the server cannot continue is deleted, and the next try starts clean. A 0.6B that will not load leaves the 110M in its place for that start, with a log line and a note in Voice settings. If two loads of the 0.6B in a row begin and never finish (the game killed mid-load, as when memory runs out; the mark `<game folder>/vfg/stt-loading` holds the model and the count), the mod writes `model: parakeet-110m-en` into the config itself; a single unfinished load is tried again at the next start, and any load that finishes, or a clean quit, resets the count; picking the 0.6B again in Voice settings tries it again. The config file holds `config_version`, 2 since 0.3.5: a file without it whose `model` is `parakeet-110m-en`, 0.3.4's default, moves to `parakeet-0.6b-v2-en` once and is written back with 2, so a later pick of the 110M is kept; Moonshine never moves.
- **Hotwords**, on a Parakeet model while `hotwords` is on (the default; set in the config file only): each stretch of speech is decoded by beam search (`modified_beam_search`, 4 paths) on a stream of its own, with the hotwords as they are then: "AI" and "brain"; every name in the client's tab list, read once a second and forgotten as the player leaves the server, cut into the words the model writes (at a change from a lowercase letter to a capital and at anything not a letter, digits dropped: `KorbinJM` → `Korbin JM`, `Steve_123` → `Steve`; one with fewer than two letters left is left out), at most 200; every phrase in `server_phrases` (above), lowercase, or the player's own phrases when the bridge leaves the field out, at most 300; and the command words `unbind`, `incantation`, `incantations`, `aura`, `cooldown`, `mobs`, `spell` and `spells`. Never an alias: a hotword boosts the real word. Each is boosted 1.0 for each of its pieces the decoder takes; on the 0.6B, a name of 4 pieces or more 2.5. The mod reads `server_phrases` as strings, trimmed, the blank and repeated ones dropped; an empty list is no phrases, and a field missing or not a list is a bridge from before 0.3.5. With `hotwords` off, and on Moonshine, decoding is greedy, with no hotwords, as before 0.3.5.

## 3. Chat and game events — Minecraft server → bridge

The bridge tails `/opt/mc/console.log` and parses it.

- **Chat** `<Name> message` becomes a line with `source = chat`, in the same table as speech, and goes through Jev the same way.
- **Events**, kinds `join`, `leave`, `death`, `advancement`, `server` (start or stop), always go into `events`, and into the feed only if watched (§6).
- RCON echoes, `Played sound`, `Set spawn point` and other noise are ignored.

## 4. Transcript history — `/opt/vfg/vfg.db` (SQLite, WAL)

The bridge creates the schema. The Jev filter writes only the `jev_*` and `fed_at` columns and `usage` rows.

```sql
CREATE TABLE lines (id TEXT PRIMARY KEY, at TEXT NOT NULL, ended_at TEXT,
  player_uuid TEXT, player_name TEXT NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('voice','chat','ai')), text TEXT NOT NULL,
  peak_dbfs REAL, mean_dbfs REAL, client_line_id TEXT UNIQUE,
  jev_class TEXT CHECK (jev_class IN ('to_ai','context','not_relevant')),
  jev_confidence REAL, jev_judged_at TEXT, fed_at TEXT);
CREATE INDEX lines_at ON lines(at);
CREATE INDEX lines_player_at ON lines(player_name, at);
CREATE TABLE events (id TEXT PRIMARY KEY, at TEXT NOT NULL, kind TEXT NOT NULL,
  player_name TEXT, text TEXT NOT NULL);
CREATE INDEX events_at ON events(at);
CREATE TABLE feed (seq INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL, line TEXT NOT NULL);  -- line: the whole line, exactly as in feed.log
CREATE TABLE usage (id INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL,
  component TEXT NOT NULL CHECK (component IN ('jev','conversation','orchestrator','implementer','brain','respond','planner','alias','router')),
  model TEXT, input_tokens INTEGER, output_tokens INTEGER, cost_usd REAL, ref TEXT);
```

- **Incantations** (§2): `lines.dropped` (`'cast'`: only an incantation, never judged or fed) and `lines.cast_id` (the cast the line's speech overlapped), and the bridge's own table `casts (id, at, started_at, ended_at, player_name, phrase, heard, layer 'spotter'|'transcript'|'jev', incantation_id, action, copy, status 'fired'|'cooldown'|'duplicate'|'failed'|'stale'|'pending', error, line_id, client_cast_id UNIQUE)`: `incantation_id` `engine:<the binding's id>` (`engine:steve.fire_ball`), `action` the ability or the scenario, `copy` NULL; `pending` only between a cast's row being stored and the engine's answer (§2), never an answer to the mod, and turned `failed` (`the bridge stopped before the game engine answered`) when a stopped bridge starts again; the Jev filter reads it, and never writes it. A fired or failed cast is also an `events` row of kind `cast`.
- It is queried by date with `vfg history` (§8).
- **The AI's own messages are lines too**: every `vfg say` is stored with `source = 'ai'`, `player_name = 'AI'`, no uuid, and the text without the prefix. A whisper is stored as `(to <player>) <text>`. They give Jev the other half of the conversation, and are never judged; `vfg say` feeds each as an `AI say` line itself (§7).
- **The shared context is the `feed` table** (§9): every kept line, every fed game event and everything the brain recorded, in `seq` order, each with its `processed_at` mark: a column added after this DDL, by `ALTER TABLE` on the bridge's start, as are `usage`'s `cache_read_tokens`, `cache_write_tokens`, `ok`, `error`, `ms` and `largest_tokens`. A database built before the three classes is rebuilt on the bridge's start (and `--init-db`), once, in one transaction, every row kept: `action_oriented`, `conversational` and `direct_ask` become `to_ai`, `not_useful` becomes `not_relevant`; feed rows are never rewritten (§7). The bridge and the Jev filter are deployed together, since an older Jev filter's `action_oriented` or `conversational` fails the new CHECK, and a newer one's `to_ai` fails an older bridge's: when Jev is on the box, `bridge/deploy/deploy.sh` stops it before the schema and deploys `jev/` from the same checkout after (a Jev that does not deploy is left stopped), and `jev/deploy.sh` alone refuses a box whose bridge predates `to_ai`. One built before `planner`, `alias` or `router` gets its `usage` CHECK rebuilt the same way, every row kept. `conversation`, `orchestrator` and `planner` stay valid components only for old rows: the orchestrator call and the retry planner are folded into the brain's loop, whose steps write `brain` rows (§9).
- **`usage` is the one log of every model call.** Every `structured()` call (`lib/py/vfg_llm.py`, §1) records its own row, whatever happens: its `component` (one of `vfg_llm.Component`, the CHECK's list: `brain`, a step of a brain loop, `respond`, the conversation agent, and `router`, the router, are the brain's, `alias` the incantation alias call's; `orchestrator`, `planner` and `conversation` only old rows have), `ref` its `call_id` (at most 64 characters), its tokens and cost summed over every attempt, `ms`, and `ok` 1, or 0 with `error`, the reason, one line of at most 300 characters. A failed call is a row with what it cost; one that timed out or was cancelled with an attempt in flight, which OpenRouter bills at a price it never told, has `cost_usd` NULL, and its `error` says what the attempts that came back cost. The row is appended to `usage.pending.jsonl` on the PC, under `usage.pending.lock`, in the folder `VFG_USAGE_QUEUE` names in the environment (default `$VFG_HOME`; the replays point it at their own output, so their rows reach the box only when sent on purpose), and `vfg usage flush` (or the next `vfg usage add`) with the same `VFG_USAGE_QUEUE` sends it (§8), each row on its own: one the box's table refuses (a component its CHECK lacks, `router` before the bridge is deployed again) is skipped with a warning and not stored, and the rest are; recording never fails a call, never waits on the box and never holds up the caller's event loop. Jev's filter writes its rows itself, and the implementers theirs through `vfg usage add`; those leave `ok`, `error` and `ms` NULL. An implementer's row is one run, its requests each priced by the runner (§10), with `largest_tokens` its largest request; every other row leaves `largest_tokens` NULL.
- **The brain's tasks** (§9) are the `tasks` table, one row per implementer task, keyed by its name. The bridge creates it after this DDL, as it does `casts`, on every start and every `--init-db`, so an older history gains it and nothing else changes (`PRAGMA user_version` 4); it never writes it. Only the brain writes it, through `vfg task set` (§8):

  ```sql
  CREATE TABLE IF NOT EXISTS tasks (name TEXT PRIMARY KEY, description TEXT NOT NULL, player TEXT,
    status TEXT NOT NULL CHECK (status IN ('open','done','failed')), line TEXT, brief TEXT,
    made TEXT, variables TEXT, session TEXT, result TEXT, created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL, closed_at TEXT);
  ```

  `name` matches `^[a-z][a-z0-9_]{1,31}$` (`galick_gun_styrk`), is never the name of a library class or an action (a file `engine/library/<name>.py` or `actions/<name>.py`), nor `cast` (the bridge's task for a cast), and is kept for life. `description` is what the thing is now and for whom, `line` the player's words that started it, `brief` the latest brief its implementer got (a hand-off's, rendered in parts under headings; a follow-up's; or the cancel words, §9), `session` its implementer's session, `result` the brain's last record of it. `made` is JSON, `{"content", "bindings", "grants"}`: the classes the task wrote, the engine's ids of the bindings it made (`steve.fire_ball`) and its grants (`Steve:fireball`), each a list, or null, mirrored: each report replaces it with what the task has made now (§9); `variables` is null: a class's numbers are its Config (§10). `closed_at` is set as the status leaves `open`, and cleared when it opens again.

## 5. Jev — the Jev filter

- Takes lines with `jev_class IS NULL` and `source` other than `ai`, in `at` order, polling every 250 ms or less.
- **The cast check**, first, for every voice line from a player with an incantation (one the game engine binds for them, from its export, `VFG_ENGINE_EXPORT`, one per phrase, as the bridge offers them, §2 and §10): one Jev call, one `choice` question, `cast`, whose options are one `cast_<phrase>` per incantation (its phrase, aliases and what it does: `It casts fireball`, or `It starts meteor`, with the engine's summary of it when the export gives one) and `not_a_cast`, on a state of its own: the fixed rules, invented examples, and the speaker's lines and casts of the last minute with the AI's lines, the newest 8, the line marked `[1]`; a line of more than 6 words (a long line) is asked in its own wording, whether it has the player casting an incantation right now, inside other talk, talk about an incantation being no cast. A cast whose option Jev gave a probability (its answer's `probabilities`, not its `confidence`) of `VFG_JEV_CAST_MIN` (default 0.5; `VFG_JEV_CAST_MIN_LONG`, default 0.7, for a long line) or more goes to the bridge's cast path, `POST /v1/jev/casts` on `127.0.0.1` with `VFG_CLIENT_TOKEN` (§2). A short line whose cast is sure, `VFG_JEV_CAST_SURE` (default 0.7) or over, the bridge drops whatever becomes of the cast, `stale` included: it is never routed or fed. A long line, or a short one under the sure threshold, it keeps (`"keep": true`), and it is routed as ever ("do both if it's not sure"), so the rest of it reaches the AI when it is said to it (below), the AI seeing the cast as its GAME line (§7). Anything else — not a cast, under the threshold, no probability for the option, the call failing or refused, the bridge not answering or keeping the line — and the line goes on to the routing call as before. The short lines due a cast check are checked before any line is routed, and again after each routing call; a long line is routed first and checked after, since its check cannot change its routing; a line already older than `VFG_JEV_CAST_MAX_AGE_S` (2 s) since the filter first read it, or than that and 10 s since it was said, gets no call and is routed. It is made once a line, never while failing open, does not count towards failing open, writes a `usage` row with `ref = cast:<line id>` when answered, and one `cast-check` line to the journal. `VFG_JEV_CAST_MIN` over 1, or no `VFG_CLIENT_TOKEN`, turns it off; `VFG_JEV_CAST_MIN_LONG` over 1, for long lines alone.
- Calls Jev — `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, key `TYPESAFE_API_KEY` — once per new line it did not cast, the routing call, a voice line and typed chat alike. **A line goes to the AI only when it names the AI and is said to it, or answers a question the AI asked**, whichever player it asked. The AI's names are "AI" and "brain"; Jev judges a misheard name too ("I" where "I" makes no sense, "eye", "A", or the name run into the next word): it is not a word match. A line said to a friend or to no one is not to the AI, however much it sounds like an ask, and nor is one about the AI, which calls it "it" or "the AI". The state is the fixed rules (the setting, the AI's names and the rule, and how to read the state; they define no class), then `/opt/vfg/lookout.md` (what to look out for), then a block of invented examples, never a session's lines, under what should become of each, then `/opt/vfg/menu.md` (the brain's actions, one `name — what it does` line each, which `vfg jev menu set` writes), then history: recent lines, the AI's included, and the brain's records of its loops, the tasks it opened and followed up and their results (`AI action`, `task` and `result` feed lines), so a follow-up to an earlier ask reads as one — as much as fits in `VFG_JEV_STATE_TOKENS` (default 8,280: 8,000 before the rule, whose longer rules, examples and lookout, 837 bytes, would otherwise come out of the menu and history). The line is marked `[1]` in the history and gets two `choice` questions: is the speaker talking to the AI in it (`to_the_ai`: `says_its_name`, `says_its_name_misheard`, `answers_its_question`, `neither`), and, if it is not said to the AI, should it be remembered (`keep`: `remember_it`, `ignore_it`). The answers walk onto three classes, with `to_the_ai`'s confidence whatever the class:
  - `to_ai` — by name, its name misheard, or answering its question, whatever `keep` says: the conversation agent first (§9);
  - `context` — `neither`, and remember, or `keep` missing: kept, and shown to no model (§9);
  - `not_relevant` — `neither`, and ignore: never fed.

  A missing or malformed `to_the_ai` is Jev failing. Each line is judged once: nothing is asked again. A line not to the AI gets no answer, and its player is told nothing: one who forgets the name gets no message. The brain's conversation agent answers every `to_ai` line first, and its router places the work (§9).
- Writes the verdict to the line, and a `usage` row with `component = jev`.
- **The gather call.** A line classed `to_ai` gets one more call before it is fed, over its speaker's lines that Jev classed `context` or `not_relevant` with a confidence (never a line passed as `context` while Jev failed open or after it refused the line twice), judged after that speaker's last `to_ai` line was judged, said before the line and at most 180 s before it, not blank and not dropped — the newest 10. Judge order, not the order said, because a voice line is stored once its speech is text, after a line typed later may have been judged: each line is offered to the speaker's next line to the AI judged after it, and to no other. When there are none, no call is made. The state is built the same way, with the gather call's own rules, examples and history heading: its rules and its examples are the ones it was benched with, literal texts byte-identical to those before the AI's names and the rule and pinned by sha256 (`GATHER_RULES`, `GATHER_EXAMPLES`), since a piece said before an ask names no AI (with the routing call's, its yes on the first pieces of `integration/jev_live.py`'s asks fell from 0.88 to 0.75 on average). The ask is marked `[ask]` and those lines `[1]` … `[n]`, and each of them gets one `choice` question: is it part of the ask (`part_of_the_ask`, `not_part_of_it`); a missing answer is a no. The yes lines go with the ask as one `LINE` (§7): their texts and then the ask's, in the order said, joined with ` … `, the oldest dropped first when that is over 500 characters, under the ask's fields and time. A gathered line keeps its own class and is fed, or not, as before. A gather call that fails feeds the ask alone, and does not count towards failing open. It writes a `usage` row with `ref = gather:<ask id>`, and one `gather` line to the journal. The filter holds a group in memory until the ask is fed, so an ask caught by a crash in between is fed alone.
- **Feeds what it keeps** (`to_ai`, `context`) in batches. A `to_ai` line flushes the batch at once, with whatever context is waiting: it gets a live answer. Otherwise a batch flushes `VFG_BATCH_SECONDS` (default 5) after its first line.
- If Jev fails for 10 s it **fails open**: every line passes as `context` with no confidence, and one `SYS` line says so. No model is shown a `context` line (§9), so while Jev fails open the brain answers none of them. Another `SYS` line says when Jev is back.

## 6. Game watchers — `/opt/vfg/watch.json`

```json
{ "events": ["join","leave","death","advancement","server"], "players": [], "contains": [] }
```

- `events` are the kinds to feed. `players` limits them to those players; empty means everyone. `contains` holds extra regexes on raw console lines, fed as `GAME raw`.
- Every kind is on by default. The bridge rereads the file when it changes. The brain sets it with `vfg watchers set` as it starts.

## 7. The feed — `/opt/vfg/feed.log`

**The one stream the brain follows, and the shared context.** It is append-only, one event per line, and mirrored in the `feed` table. The bridge and the Jev filter write it through one locked writer that assigns `seq`. The owner's PC writes it only through `vfg say` and `vfg feed post`, and only the brain does.

```text
LINE#812 18:22:31 Steve voice to_ai 0.93 -8dB | AI, build me a castle
LINE#813 18:22:33 Alex chat context 0.71 - | that cave by spawn
AI#814 18:22:35 task castle_steve | new: A castle for Steve at spawn, about 40x40, stone and oak
AI#815 18:22:35 say castle_steve | on it, castle coming up
GAME#816 18:22:40 death Steve | Steve was slain by Zombie
AI#817 18:24:02 result castle_steve | castle_steve done: castle built at spawn, 40x40
SYS#818 18:25:00 | jev unavailable — passing every line as context
LINE#819 18:26:04 Alex voice to_ai 0.91 -11dB | AI, fire aspect 5 on my axe
AI#820 18:26:09 say - | your axe burns now
AI#821 18:26:09 action - | gave Alex's axe Fire Aspect 5 by item modifier; /enchant refuses a level over the maximum
```

- The grammar is `TYPE#seq HH:MM:SS fields | text`. `TYPE` is `LINE`, `GAME`, `AI` or `SYS`. The time is UTC. The fields, separated by single spaces, with `-` for anything missing:
  - `LINE`: `<player> <voice|chat> <to_ai|context> <confidence|-> <NdB|->`. The confidence, `to_the_ai`'s (§5), has two decimals and is `-` when Jev fails open; dB is the line's peak, rounded, and `-` for typed chat. A line fed before the Jev routing may end with ` was=not_relevant`, from the re-ask that is gone; the writer still accepts it, and nothing writes it now. A line fed before Addressing the AI (2026-10-13) may hold `action_oriented` or `conversational`, Jev's two classes for the AI then, since the feed is never rewritten: the brain reads either as `to_ai` (`context.parse`; a restored `feed.log` can hold them). The writer no longer accepts them: one is written anyway, with the one warning it gives for any `LINE` fields off this grammar, and nothing writes one now. The text may hold a group (§5): the lines Jev gathered into an ask, then the ask, in the order said, joined with ` … ` — `the castle by the river … the big one … AI, make it bigger`.
  - `GAME`: `<kind> <player|->`, any kind the bridge feeds.
  - `AI`: `<say|action|task|result|note> <name|->` — what the brain did, which only it writes. The second field is a task's name (`[a-z][a-z0-9_]{1,31}`, §4), or `-` where no task applies, and never a `#seq`: `say`, a chat line it sent (as the `lines` table keeps it, a whisper as `(to <player>) <text>`), under the task it is about (the reported one, else the first its loop or the router opened, else the first followed up); `action`, the record a loop leaves at each ending (§9), a report's loop's too: what was done, and what failed and why, always `action -`; `task`, a task a loop or the router opened (`new: <description>`) or followed up (`follow-up: <what to change, cut to 160>`, or `follow-up: never mind — put back what its last run built` for a cancel); `result`, a task's result, one short line (`<name> done: …`, `<name> failed: …`), which the conversation agent writes for a report (§9). The brain writes no `note` and no row per action. Nothing an implementer writes is ever fed. Older rows (one `action -` an action run, `note` rows, the `T<n>` ids of tasks before they had names) still read: only a write is checked.
  - `SYS`: no fields.
- The `ORCH` type of the orchestrator is retired.
- Text has newlines replaced by spaces and is cut at 500 characters with `…`.
- A batch is written in one go, under 200 ms.
- **Every kept line is fed exactly once**, across restarts and crashes: before feeding a line not yet marked `fed_at`, the Jev filter looks for it in the `feed` table and only marks it if it is already there. A group is that ask's line: its text ends with ` … ` and the ask's.
- **A cast** that fired or failed (§2) is always fed, whatever `watch.json` says: `GAME#820 18:30:02 cast Steve | Steve cast "fire ball": fireball, fired in the engine` (`charging in the engine` while its charge-up runs), or `… | Steve cast "fire ball": failed — <error>`. Cooldown and duplicate casts are not fed.
- `SYS#0` is never assigned by the feed: `vfg watch` uses it for its own notices — EC2 unreachable, reconnected, lines skipped, feed restarted.
- **The writer is one Python module, `vfg_feed`**, owned by the bridge and deployed to `/opt/vfg/lib/`. Its API is `append(type, fields, text, at=None) -> seq` and `append_batch(entries) -> [seq]`, where each entry is a `(type, fields, text, at)` tuple; `at` is the moment it describes (when a line was said), defaulting to now, and is what the `HH:MM:SS` shows. It cleans the text (newlines to spaces, 500 characters), takes a file lock, appends to `feed.log` and inserts the `feed` row. Its command line is `python3 /opt/vfg/lib/vfg_feed.py post <TYPE> "<fields>" "<text>"`, which prints the seq. The Jev filter imports it, and `vfg feed post` calls it over SSH.

## 8. The `vfg` toolkit — the owner's PC

**Every agent acts through these commands, and nothing else touches EC2.** Output is plain text. Exit 0 means success. A failure exits non-zero with one line on stderr: 1 refused or failed, 2 bad arguments, 3 not configured, 4 EC2 out of reach or no answer in time, 5 Minecraft not answering RCON, 6 the game engine not running, 124 `vfg action run` or `vfg cmd` when the engine took the request and did not answer in time (it may still have happened). Configuration lives in `~/.vfg/config`, as `KEY=value` lines: `VFG_SSH_HOST`, `VFG_SSH_USER`, `VFG_SSH_KEY`, and the brain's (§9); an environment variable of the same name wins.

| Command | Does |
|---|---|
| `vfg up` | Checks SSH and the `minecraft`, `vfg-bridge`, `vfg-jev` and `vfg-engine` units, and `minecraft-test` where the box has it (§1), starts any that are down, prints their status |
| `vfg watch [--after <seq>]` | Prints the feed from the line after the last `seq` it printed (cursor in `~/.vfg/cursor`), then follows; reconnects on SSH drops; never exits on its own. `--after <seq>` starts after that seq, prints every line after it, on its first connection and on every reconnect, with no catch-up limit, and reads and writes no cursor: the brain keeps its own place |
| `vfg say "<text>" [--to <player>] [--task <name>]` | `tellraw` to everyone or one player, with the prefix `[AI] ` in aqua (`VFG_CHAT_PREFIX`), and stores the text as an `ai` line (§4), and feeds it as an `AI say <name\|->` line (§7), in the same SSH call |
| `vfg cmd "<command>"` | One server command, through the library's `command` scenario (`engine_start` with `scenario=command`, waited for); prints Minecraft's replies, from the result's facts: `replies`, Minecraft's answer to each command sent, in order; `ran`, the commands that went through; `failed`, the command it stopped at (Minecraft refused it, or a block command, which it never sends), else null; `partial`, true when Minecraft did not answer. Exit 1 when Minecraft or the engine refused it (an owner's command among them), 124 when the engine took it and did not answer in time |
| `vfg history [--since <iso\|-10m>] [--until <iso>] [--player <name>] [--class <c>] [--source voice\|chat\|ai] [--events] [--limit N]` | Queries the transcript history, or `events` with `--events` |
| `vfg watchers set <kind,…> [--players a,b] [--contains <regex>]` / `vfg watchers show` | Writes or prints `watch.json` |
| `vfg lookout set "<text>"` / `vfg lookout show` | Writes or prints `lookout.md` |

## 9. The brain — the owner's PC

**The brain replaces the conversation, the orchestrator agent and the dispatcher.** Its entry point is the executable `brain/run`; `vfg brain start` runs it detached. It is one async loop: it follows the feed with `vfg watch --after <seq>`, and a player's lines take turns (below), every turn its own asyncio task, so different players' lines never wait for one another. It runs three agents, each one `structured()` call at a time on DeepSeek V4.1 Flash, the first two with no reasoning and the brain's steps at low (Prototype_Conversation_And_Router): the conversation agent (`brain/brain/respond.py`, its class `Respond`), which answers every line said to the AI at once; the router (`brain/brain/router.py`), which picks who does the work a hand-off asks for; and the brain's loops, one call a step, which do as tools of their own what the orchestrator call and the retry planner did.

- **Events.** A `to_ai` LINE (one fed before Prototype_Addressing_The_AI with Jev's two classes for the AI then, `action_oriented` or `conversational`, is read as one) is one conversation agent call, in the player's turn, and one router call when the agent hands it off: every line said to the AI goes to the conversation agent first, and none reaches a loop or an implementer but through the router. The router's choice starts a loop, adds the line to a loop, starts or follows up an implementer, or sends it nowhere. An implementer's report is one conversation agent call, never queued, and one router call when it leaves something to do. There is no other call. A GAME line, a SYS line and the brain's own `AI` lines are context only. A `context` LINE is not even that: no model is shown it (below). A LINE already in the feed when the brain reads its context (at or below the `last_seq` it gives) and more than 2 minutes old then is history and is never acted on; a LINE that arrives on `vfg watch` after that is live, whatever its time.
- **One turn per player.** A player's live lines run one at a time, in the order they came; different players' turns run at once. A turn is the conversation agent's call and the router's: it ends once the router has placed the line, so the player's next line is routed knowing where the last one went, and it never waits for a loop or an implementer, which hold no turn. At most `VFG_TURN_WAITING` (3) lines wait for a player's turn. One more is turned away: marked processed, never answered, and that player alone told which lines still wait, by `vfg say --to <player>` (`Still on: “a meteor staff”, “and a shield”, “and a bow”. I can't take any more right now — wait a bit, then ask again.`, one chat line under 200 characters). An implementer's report never waits for a turn: it goes to the conversation agent at once, beside whatever the player's turn is doing. A turn ends when its run returns, raises or is cancelled, then waits at most `VFG_TURN_SETTLE_S` (3 s) for the `AI` rows it wrote, a whisper and a row whose write failed apart, to come back on the watch, so the player's next turn reads them; a run that raised or was cancelled skips the wait, and a loop's or a report's rows are nobody's turn's and never waited for. A stop drops everything waiting: a line dropped so is marked read and never answered, after a restart too.
- **The conversation agent** takes every line said to the AI first, on `VFG_RESPOND_MODEL` (`deepseek/deepseek-v4.1-flash`, reasoning off, providers `together,coreweave,parasail`, `VFG_RESPOND_TIMEOUT_S` 20 s), reading the same context, and answers at once with one `Response`, `{reason, choice, reply}` in that order, `choice` one of `reply` (nothing to do: talk, a rule for later, a Minecraft question from what it knows, or work under way answered from WORK UNDER WAY or TASKS), `look` (a question about the live game it cannot answer for sure from what is shown, passed on to be looked up), `do` (something to be done or changed in the game, a correction, an answer to the AI's own question, or it is unsure, passed on to be done) or `quiet` (nothing to say and nothing to do), `do` the default. It is hardened against hallucinating: it answers only from what is shown — the conversation, THE WORLD NOW, WORK UNDER WAY, TASKS — and general Minecraft knowledge, and chooses `look` rather than invent a name, a number or a result. `look` and `do` both read `hand_off` true, a read-only property kept for the core and the benches. It has no actions, never acts on the game and never looks at it itself, and picks nothing; it is shown WORK UNDER WAY in brief and TASKS one line a task, so "is it done yet?" is answered from them. With `look` or `do`, the reply says back specifically what was heard — the thing, for whom, how many, where — never a bare "On it" or "Coming up" alone, and never that it is done; casual talk (`reply`, `quiet`) stays short. After the call, in code and never sent back: a sentence that names Jev or the filter is dropped (a report's reply's too); a `reply` or `quiet` whose line offers or promises something in the game becomes `do` (a promise kept whole as its line, an offer dropped; "coming up" is a status for a player with work under way, a loop thinking, an implementer running or an open task); a `quiet` with a line said anyway becomes `reply` (logged), and a `reply` with nothing said becomes `quiet`; a line beside `look` or `do` that offers, or says the thing is done, ready, gone or there, is dropped; a reply over 300 characters is cut at a word to 200, with no sentence cap in code, the prompt's guidance alone. A call that fails, or runs past its timeout, fails into `do` with no reply.
- **The router** takes every hand-off, the conversation agent's and what a report left, on `VFG_ROUTER_MODEL` (`deepseek/deepseek-v4.1-flash`, reasoning off, providers `together,coreweave,parasail`, `VFG_ROUTER_TIMEOUT_S` 30 s, 60 s when its reasoning is not off), and picks who does the work in one `Route`: `reason` first, ending with the choice and its target (`… so: loop L3`); then `to`, one of `new_loop` (a new brain loop), `loop` (with `loop`, the id of a loop WORK UNDER WAY offers, `L3`), `new_implementer` (with exactly one hand-off, the new task's name, description and brief in parts, as a step writes one), `implementer` (with a follow-up for each task the line changes, each a task under TASKS with its brief and description, or `cancel`) or `nowhere` (with a `reply`, or none: the line asks for nothing, or the thing is under way and the line only presses for it; the reply, when it has one, goes out after the agent's line, never in its place); every field the choice does not use empty. Its schema never changes and requires every property; what depends on the moment is a validator, which `structured()` sends back once: a reason whose last "so:" names another choice than `to`, a loop not offered, a hand-off missing, more than one, or refused by a step's checks (`brain/brain/checks.py`, the same words), a follow-up missing, refused by them or of a task not under TASKS, a `nowhere` reply over 300 characters, or one that promises work or, for a line, says a thing is done or fixed, and for a report's hand-off `loop` or more than one follow-up. What the choice does not use is dropped and logged. While a task's implementer is on a thing, its rules send a line that asks that thing to change, stop or be unbound to that task, or the loop already on it, or nowhere: never a second worker beside it. Its prompt is a step's opening with its own rules (`brain/prompts/router.md`, the menu, every library action in full, the command list), the conversation, and a tail never cached: this server's own actions, the world with RUNNING NOW in full and no items, TASKS in full, WORK UNDER WAY in full, and THE LINE with the conversation agent's answer and reason — and whether it passed the line on to be looked up or to be done — or THE REPORT with what it left.
- **Placing the work** is code, no model: `new_loop`, a new loop; `loop`, the line added to that loop (below), or a new loop when it can no longer take one (deleted, past its window, at the cap with no step left); `new_implementer`, the task opened, `AI task <name> | new: …` posted and its implementer started; `implementer`, each task opened again, `AI task <name> | follow-up: …` posted and its brief sent (a cancel's, the cancel words), a task gone meanwhile dropped and logged, and a new loop when none was left; `nowhere`, nothing. A router call that fails, or runs past its timeout, places the line in a new loop.
- **No hold.** The agent's line goes out the moment it answers, every time, hand-off or not: there is nothing to wait for, and `VFG_ROUTER_REASONING` no longer changes what is said. A hand-off's line goes out before the router has even run — before any task is opened or followed up — so it is never tagged `--task <name>`. The router's own line, when it has one, always goes out after the agent's, never in its place, so it is never said twice: `nowhere`'s reply, said after the agent's to correct or add to it, never to repeat it; or, when a new task would not open, a line written in code, `sorry, I couldn't start “<the player's words>” — say it again?`, after it, since nothing was started.
- **Loops** hold no turn: each is an asyncio task of its own, so loops run side by side, one player's too. The brain keeps every loop a line can still be added to, every player's, in memory only (a restart forgets them): its id `L<n>`, counted per run; its player; its lines; and its state, `thinking`, `ended` (saved, its prompt kept) or `deleted`. **A loop's budget** is `VFG_LOOP_STEPS` (10) steps for its first line (a report's loop: the report) and as many more for each line added, never past `VFG_LOOP_CAP` (20), the numbers its rules give too; a loop that reaches the cap is deleted after its ending, and the next line on that thing starts a new loop. **A line added** to a thinking loop is read before its next step, in one block: `LINE ADDED TO THIS LOOP: LINE #<seq>, <HH:MM:SS>: <player> said: <words>`, `(the conversation agent answered: “…”)` or `(the conversation agent said nothing)`, `(the router: <its reason>)`, then `ROWS SINCE THIS LOOP LAST READ:` and every row shown since, or `nothing`. When the step in flight ended the loop, its ending goes out and the loop takes one more step for the line, the ended step shown as `ENDED <end> AND SENT: …`. A thinking loop takes a line however long it has run, unless the step in flight is at the cap. **An ended loop is taken up again** by a line added within `VFG_LOOP_TAKE_UP_S` (120 s) of its creation, while it has a step left under the cap: a new step after its last, on the same prompt, every earlier step read from the cache. Past that it is gone, as if deleted. **WORK UNDER WAY** is every loop a line can be added to, oldest first: in full for the router (`- L1, for KrownJM, thinking, step 2 of 20, started 18:29:41 (52 s ago); lines: #58 “can you teleport me to Stirka” 18:29:40, #60 “teleport me to Stirkosaurus” 18:29:50 (added, not read yet)`; an ended one `ended, saved: can take a line for 68 s more; 1 of 10 steps used, …; did: <its record>; last reply: “…”`; `WORK UNDER WAY: no brain loops` with none), and in brief for the conversation agent (`- KrownJM: “can you teleport me to Stirka”, then “teleport me to Stirkosaurus” — being done now (12 s)`, or `— done a moment ago: “<its last reply>”`; `WORK UNDER WAY: nothing right now` with none). Implementers are not in it: TASKS marks the tasks one is on.
- **A loop** is steps until one ends it. At its start it reads the world once, its player's items included, and TASKS, and keeps them for every step and every take-up; what no call had read, the front turn took in for it (processed marks, below). Each step is one `structured()` call (`lib/py/vfg_llm.py`) on `VFG_BRAIN_MODEL` (`deepseek/deepseek-v4.1-flash`, reasoning `low`, which the loop replay chose over `off`, providers `together,coreweave,parasail` so a loop's steps keep one host's cache, `VFG_BRAIN_TIMEOUT_S` 120 s, or 60 s with `VFG_BRAIN_REASONING` `off`, its resend and retries included), answering one `Step`, whose schema never changes and requires every property, its default included: `actions` from the menu, each written in full (§14), and `order`, `together` (all at once) or `in_turn` (one after another, stopping at the first that does not land); `read_items`, players whose items to read; `read_configs`, game engine classes whose Config to read as written, by their names under ENGINE; `hand_offs`, new tasks, each a name, a description and the brief in parts; `follow_ups`, each a task by its name with what to change and its new description (empty: it stays), or `cancel`; `end`, one of `next`, `reply`, `silent` and `handoff`; `reply`, the chat line; and `record`, the loop's one record. The event shows the conversation agent's line (`(the conversation agent already answered the player: “On it!”; your reply follows it — never repeat it)`, or `(the conversation agent said nothing)`) and the router's reason, so the brain's reply says the result and never acknowledges again. What code cannot carry out, or would carry out wrongly, is a validator, which `structured()` sends back once: an action not on the menu or values its action refuses, an ending with nothing to end on, a hand-off's name or a brief with a part left empty, a follow-up with no brief, a Config to read that is no class's name (`^[a-z][a-z0-9_]{0,63}$`), a reply over 300 characters (a hard cap over the prompt's soft 200), a reply that promises work when the step ends `reply` and starts nothing, on the last step an ending but `reply` or `handoff`, and, while nothing of the loop has landed in the game (a report's loop counts as landed), a step that runs nothing and ends `reply` claiming it is done, or ends `silent`. What would have no effect is dropped and logged instead (the last step's actions and reads, a `next` with a reply there becoming `reply`; a reply or a record on `next`, a reply on `silent`, reads under an ending), and a hand-off or a follow-up under `reply` or `silent` makes the step's ending `handoff`.
- **Send if all land.** `reply`, `silent` and `handoff` mean: if every action of this step lands, send the reply, write the record, open the tasks and start their implementers, and the loop is done, with no further call. `next` means: run these, and show me the results. An action lands when it ran without an error: `vfg action run` checked its values, the engine did it, and Minecraft did not refuse a command a scenario sent. A step that does not land, or ends `next`, sends nothing, no reply, no record and no task, and the next step's prompt holds every earlier step and what each of its tools came to: `landed`; `changed nothing` (it ran, but its facts' `changed`, what it changed, is empty: an `engine_config` to the Config as it already is; not landed, so a reply written up front never claims it); `refused`, with why (refused before it ran, by the brain's check or by vfg's; a player not online; or the engine's error, and for a command a scenario sent Minecraft's, with the reference of every command it used (the args whose type ENGINE gives as a command), from `refs/`); `did not run` (vfg could not run it: not configured, the box out of reach, Minecraft or the game engine not running, vfg's exit 3 to 6: nothing happened, and it may be run once more); `failed` (it timed out or partly happened: it may have happened); `not run` (in turn, after one that did not land); or `read`. Nothing is retried in code.
- **Reading a player's items** is a tool: the speaker's items by slot are in every step's prompt (a report's: its task's player's), and another player's come back to the next step, from a `vfg state --json --items` fetched for that read and waited for up to 15 s, its own fetch's answer and never a state from before the step's actions; a fetch that fails is a refused read. **So is reading a Config**: each class `read_configs` names comes back to the next step as `vfg engine config get` prints it, its file and lines and the class whole (at most 8000 characters), read for that step and never kept from before; the engine not running, a class it has not, or one in neither the library nor `made/<server>/content/` (§8), is a refused read. A library class's Config reads as the library's, and the first `engine_config` of it makes this server's own copy, which runs in its place (§8). An `engine_config` (§14), values only (§8), of a class whose Config no earlier step of the loop read is refused at the tool, before it runs: the brain sends back the whole class as written, comments and all, so it must have seen it. A read goes with `end` `next`.
- **The limits**: a loop's budget (above). The step at its limit is the last: no action and no read (what it writes is dropped), and an ending of `reply` or `handoff`, a reply in the player's terms that never mentions steps, time or limits. A loop has no time limit: its steps and the step timeout bound it, and `VFG_LOOP_SECONDS` is no longer read. A loop's run ends with a reply, silence or a hand-off, or fails: a step whose call fails for good ends it, the loop's player hears what landed and the error in one chat line of at most 200 characters, and code writes the record of what its steps ran; the loop is then saved like any other, so a line added may take it up. An answer that failed its checks twice is never put in the check's words: `<player>: sorry, I got tangled up on that one — say it again?`, or `<player>: done: <what landed> — then I got tangled up on the rest, say it again?`; any other failure keeps its short reason, `<player>: that errored out — <why>`, or `<player>: done: <what landed> — then that errored out: <why>`. An error nobody expected is said once in the same shape, unless the reply already went out, and the loop is deleted.
- **A hand-off**, a step's or the router's: code makes its name (the thing, then whose: `frost_bow_alex`), which its class takes too, free of every task, action and engine class (those ENGINE lists, and the files in `engine/library/` and `made/<server>/content/`) and of `cast`, adding `_2`, `_3` …; renders the brief from its parts, under `THE PLAYER'S WORDS`, `THE WHOLE PICTURE` (how it behaves, looks, sounds and feels), `WHAT THE PLAYER TAKES FOR GRANTED`, `HOW IT IS CAST, AND FOR WHOM` and `DONE WHEN` (the checklist, one `- ` item a line); opens the task with it (§4); posts `AI task <name> | new: <description>`; and starts its implementer (§10). Nothing waits for it to finish. A hand-off whose task would not open is never promised: the reply is a line written in code instead (`sorry, I couldn't start “<the player's words>” — say it again?`, after what landed `done: <what landed> — but I couldn't start …`), and a loop's record says so.
- **A follow-up**, a step's or the router's, names a task under TASKS; a step's of a task that does not exist is refused at the tool, and the refusal comes back as a result, and the router's is sent back. The task opens again with its new brief, and its new description when one was given, `AI task <name> | follow-up: <brief>` is posted, and its implementer gets the brief: into its run as a message while the run is live, else resuming its session (§10); with no session (after a restart), a new implementer starts on the description and the follow-up. **A cancel** ("never mind") is a follow-up with `cancel`, never a stop: code sends the cancel words of Prototype_Implementer_Harness, `CANCELLED: the player said never mind. Stop building and put everything back the way it was before the run this cancels, then report Cancelled: and what you put back.`, which become the task's brief; the description stays, and the row says `follow-up: never mind — put back what its last run built`.
- **Stopping and changing** are actions of a step (§14), with no task: `engine_stop` ends a scenario, every run of it or one instance under RUNNING NOW; `engine_revoke` takes an ability away, `engine_clear` a mark and `engine_take` an item; a number is changed with `engine_config`, its Config read first. None changes a task's status.
- **The ending, in order**, once its step landed: the hand-offs' and follow-ups' tasks and their `AI task` rows; the reply, through `vfg say … --task <name>` (a report's loop's task, else the first opened, else the first followed up); the loop's record; then the implementers started and the follow-ups sent. Then, when a line was added while that step ran, the loop takes one more step; else it is saved, or deleted at the cap.
- **What a loop leaves in the context** is one short record an ending, what was done and what failed and why (`gave KrownJM's axe Fire Aspect 5 by item modifier; /enchant refuses a level over the maximum`): `AI action - | <record>`, a report's loop's too (the step's, else written in code from what vfg ran; none when nothing ran and the step wrote none); its reply as the AI's `say` line; and the `AI task` rows of its hand-offs and follow-ups. Its steps, its tool calls and their results stay inside it: no row is written per action, and none for an edit or a stop. A loop never writes a task's `AI result`.
- **A report** goes to the conversation agent at once, never queued. It reads the report whole, its done-when items included, with the task's name, player, words, description and latest brief, and answers one `ReportAnswer`: `reason`; `hand_off`, true when something the player asked for is left; `left`, what is left, the done-when items named; `status`, `done` or `failed` (`done` for a cancel that put things back); `reply`, the player's chat line; and `record`, one `result` line (`castle_steve done: castle built at spawn`). Code says the reply (one written in code from the player's own words when it gives none), posts `AI result <name> | <record>`, and closes the task on that status, or keeps it open with the record as its result so far while a follow-up to it runs, its implementer still does, or what is left is handed off. What is left goes to the router as a report's hand-off, never to a loop already running: the task's implementer again, a follow-up naming the done-when items left; a new loop, whose event is the report and what it left, which does it with actions or follows the task up and never closes it; a new implementer; or nowhere, its reply, when it has one, said after the agent's. A router call that fails follows the task up with what is left. Once that is carried out, the task closes on the agent's status, unless it was followed up here, a follow-up to it already runs, or its implementer still does. The agent failing, or an error nobody expected, closes the task on the implementer's status with a record and a chat line written in code, kept open only while a follow-up to it runs.
- **The engine's part of THE WORLD NOW** (the game engine spec): one `vfg engine overview --json`, its classes, instances, places and incantations in one SSH call, fetched at a loop's start beside `vfg state --json --items` and waited for up to 3 s (past that the last good read is shown, and the fetch finishes for the next call), each read shared while younger than 2 s, and read afresh by the next loop after an action that reached the engine. RUNNING NOW is every instance the engine runs, scenarios first: its name (what `engine_stop` takes for a scenario's), its kind and class, whose it is (`granted to Steve`, `held by Steve`, `on Steve`, a scenario's `for the world`, an actor's `in the world`) and when it ends; at most 40, the rest counted. SAVED PLACES are the engine's (§14), `castle 197 68 251 overworld (castle_steve)`. INCANTATIONS is each binding, `- "fire ball" for Steve: casts fireball`, or `starts meteor {"at":"caster"}`. ENGINE is every class by kind, scenarios first, its summary cut to 120 characters, and under a scenario and a mark its args, one `args.count: whole number 1..100, default 10: how many fall` line each. While vfg says exit 6 each part says the engine is not running; a part with no good read, or one the engine refused, reads `unknown`, with why. The prompt's rule (the spec's): before a new ability is handed to an implementer the player is asked what they want to say to cast it, unless they said; the phrase goes in the brief; and an ability is never granted and its incantation bound in one step: it is bound once it exists.
- **The shared context** is the feed (§7), `feed` in `vfg.db` (§4): the whole conversation, with the world — every online player's position, health, food, armor, XP level, game mode and effects (`vfg state --json --items`), the items by slot of the loop's player alone (the conversation agent's and the router's: nobody's), the time and the weather, RUNNING NOW, the saved places, the incantations and ENGINE — and TASKS, every task on the server, open and closed. The brain's loops and the router see TASKS in full: each task's status, when it was last written, its description, what it made, the engine's instances of the classes it made running now, and its last result. The conversation agent sees RUNNING NOW, INCANTATIONS and ENGINE from the last reads, never waited for, no saved places, and one line a task, `- <name> for <player|nobody>, <status>: <description>`, the status `an implementer is on it` while one runs (`TASKS: none yet` with none). A loop reads it whole once, at its start, for all its steps and take-ups, and every conversation agent and router call reads it whole, but for the `context` LINEs: those stay in the feed and `vfg.db`, for a later memory, and are never shown to a model, neither in the conversation nor as new rows. Every GAME row is shown. On the AI side only the brain writes to it, through `vfg say` and `vfg feed post AI`; nothing an implementer writes is in it.
- **Processed marks.** Every front turn and every report take in every row not yet processed and mark it, `vfg context mark`, so the game events since the last read are the new rows of the conversation agent's call and of a new loop it leads to. A `context` LINE is marked as it arrives, and at a start every one still unmarked, so nothing waits on it. Nothing else is read: what arrives after a loop's start waits for the next read, or reaches the loop with a line added, as the rows since it last read.
- **Caching.** A step's fixed opening (the rules, the menu, every action in full, Minecraft's command list less the commands that place or remove blocks, a scenario's to do, and the owner's, which the engine refuses), then the conversation in blocks marked at stable checkpoints (every `VFG_BRAIN_CHECKPOINT`, 5, blocks; the last two for a step and for the router, the last three for the conversation agent), then the tail, read once at the loop's start and fixed for its every step and take-up, then one block per earlier step, and one where lines were added. The last block is marked (the tail on the first step), so each step's prompt is the next step's cached prefix; at most 4 marks in all. Then the step line, `STEP <n> of at most <the loop's limit now>.`, never cached. Measured on the brain's prompt from before the game engine, the old system's actions in full: on Gemini 3.8 Flash, the brain's model before Prototype_Conversation_And_Router, on the replay of the 2026-10-11 session run on 2026-10-12 (`integration/replay/loop/report.md`, the brain loop's code after its first fix round) a loop's first step read 96.4% of its prompt from the cache and a later step 96.6%; live on realmc (after its second fix round), 95% of a 32–35K-token prompt. On DeepSeek V4.1 Flash at low, on Prototype_Conversation_And_Router's finished code, run on 2026-10-13 (`integration/replay/loop/report-deepseek-v4.1-flash-low-final.md`), a loop's first steps read 91.0% from the cache (73 steps), a later step 98.6% (4) and every call 90.3% (145).
- **Tasks.** Only an implementer's work is a task. The brain keeps its tasks in memory, keyed by name, and writes every change of one as its whole row through `vfg task set` (§8) in the background, one task's writes in the order they were made; a write that fails is sent again after 2, 5, 15 and 30 s unless a newer change carries the row first. It reads them at a start, from `vfg context --json`, and again when the feed restarts: a row the memory lacks is added, and one the read lacks (a box provisioned again) or holds older than the memory (a write that never landed) is written back. A report replaces the task's `made` with what the task has made now (`{"content", "bindings", "grants"}`, checked against the disk and the engine, each name once): a class removed, a binding undone or a grant revoked leaves it, as a deploy mirrors the folder; one with nothing known (no implementer ran) changes nothing. It keeps its `DESCRIPTION:` line as the description (§10); `variables` stays null. At a start, every task still open fails (`<name> failed: interrupted, the brain restarted while it ran`); at a stop, every task whose implementer it stopped (`<name> failed: stopped, the brain stopped while it ran`), and the writes still going out get 5 s. `vfg route --task` reads one row and `vfg brain status` the open ones.
- **Files**, in `$VFG_BRAIN_DIR` (default `~/.vfg/brain`): `lock`; `brain.pid`; `brain.log`, one `<ISO time> <area> <message>` per line, among them a line a front turn, `front #<seq> <player>: agent <handoff|reply|silent|failed> <ms> ms; router <ms> ms: <to> <loop id|task|->; said <agent|router|code|nothing>` (no router part when nothing was handed off); a line where the router placed the work, `router <ref> -> …`; a line a step, `brain <ref> s<n> <spent> | <what it did> -> <what came of it>` (`brain <ref> s<n> FAILED (<spent>): <why>` for a call that failed); a line a run of a loop (its start or a take-up), `loop <ref> <player|nobody>: <n> step(s), $<cost>, <rate> cached, reply at <s> s, <s> s, ended <reply|silent|handoff|failed|cut off|broke>; <id> <saved|deleted>, <n> of <limit> steps, lines <#seq, …|none>`; and a line for each line that waited for its turn, once it takes it, `turn #<seq> <player> waited <s> s for their turn`; and `refs/<version>/`, the server's command tree and the wiki's command pages, fetched once per server version. A `tasks.json` an older brain left there is renamed `tasks.json.retired-<YYYYmmdd-HHMMSS>` at the start, never read and never deleted.
- **Usage**: every model call is a `usage` row of its own, written by `structured()` (§4): `brain`, one a step, `ref` `#<seq> s<n>` (a report's loop: `<task> s<n>`, the name cut to 56 characters); `respond`, the conversation agent's, `#<seq>` (a report: the task's name); and `router`, `#<seq>` (a report's hand-off: the task's name); failed calls included. The brain logs what each call spent, a failed one too, and sends the queue after each step's call, each conversation agent call and each router call, at its start and at its stop (`vfg usage flush`, nobody waiting; never two at once, one asked for while another runs running once when it ends); `implementer` rows, one per implementer run, its `ref` the task's name, it writes with `vfg usage add`.

## 10. Implementers, content and the library

- **An implementer is started by code from the brief of the brain's hand-off, one per task** (§9): a run of the harness `VFG_IMPL_HARNESS` names, on DeepSeek V4.1 Flash thinking at `VFG_IMPL_EFFORT`, `high` (below). It writes engine classes and their tests, sets up what the job needs through `vfg engine`, checks it, and ends with its report. Its brief is the hand-off's, rendered in parts under their headings, `DONE WHEN` last, then `YOUR TASK: <name>`, the name everything it makes takes (its class, `made/<server>/content/<name>.py`, and another it needs `<name>_<what>`; its test, `made/<server>/tests/<name>.py`; every bind it sends, `--by <name>`), `SAVED PLACES: …` (§14), read fresh, and the EXAMPLES block (the brief, below). A follow-up to its task goes into its run as a message while the run is live, and resumes its session after it (below), so two implementers never edit one class; it carries the row's `made` (§4), from which the guard starts when this brain did not start the task, so the reports say all of it; it changes its task's own class in place, and what runs of it switches at its reload. A cancel is a follow-up whose text is the cancel words (§9): the implementer puts back what it built and reports `Cancelled:` and what it put back, a report read as done (never mind, below). A brief's `DONE WHEN` is the implementer's check: it checks each item before it reports, with its test, and its report says, item by item, which landed and which did not (below). Its last message is its report, to the brain alone; it never talks to a player. The report's last line, `DESCRIPTION: <what the thing is now, for whom, how a player uses it>`, is taken off it in code and kept as the task's description (at most 600 characters; with none, the one the brain wrote stays).
- **The ladder** (its prompt's): use what exists (start a scenario with the args the job needs, grant an ability, give an item, apply a mark, bind a phrase, or one `vfg cmd`); else one new class, from the closest, importing only `vfg_engine` and its kit, loaded with `vfg engine reload`; a variant with only other numbers is no new class but the brain's Config change, named in the report. Where and for whom are a scenario's Args, never coordinates or a name in the code; every number is in its Config.
- **What a task made** is recorded by the guard from what it lets through: each class file it writes, each binding it sends (the engine's id, `steve.fire_ball`) and each grant (`Steve:fireball`), over the task's runs; at the report they are checked against the disk and the engine (`vfg engine incantations`, `vfg engine instances --kind ability`), and what is there goes with the report into the task's `made` (§4, §9). A scenario it started, an item it gave, a mark it applied and a place a class saved are not recorded.
- **The harness** is the program around the model: it sends the prompt, runs the tool calls the model asks for, and keeps the session a follow-up resumes. The runner (`brain/brain/implementers/runner.py`) knows one only through `harness/base.py`: a `Harness` (`name`; `start(task, system, brief, guard)`; `resume(task, system, session, text, guard)`; `close()`, at shutdown) gives a `Run` (`session`; `events()`; `send(text)`, a message into the live run, false once it has ended; `stop()`, an interrupt; `close()`), whose events come in order: `Session`, its id, as soon as the harness has one, which the brain keeps in the task's row; `ToolCall`; `ToolResult`; `Text`; `Request`, one model request's tokens as the provider counted them (input not cached, read from the cache, written to it, and output), its model and when it was sent, its size the three inputs together; `Compacted`; and last `Done`: how it ended (`ok`, `error`, `turns` or `stopped`), its last message, the report, its turns, the calls the harness's own checks refused, which should be none and are logged as `denied`, and `unread`, the messages it ended without reading. The system prompt goes as a file, `$VFG_BRAIN_DIR/implementer-system-<12 hex of its sha256>.md`, given again on every resume. Every adapter calls the guard's `gate()`, its one entry point, before a tool runs, a refusal going back to the model as that tool's error with the guard's reason, and turns its harness's own permission checks off: the guard is the only gate. The tools are the harness's own. The guard refuses, on every harness, each with one line saying what to send instead: a read or a search outside `engine/` and `made/<server>/` (`Read` names a file in them, `Grep` and `Glob` a path in them, and the shell reads with `cat <file> …`, `sed -n 'A,Bp' <file>`, `grep`, `head`, `tail` and `ls` on paths in them, a glob checked match by match as bash would expand it); a write anywhere but `made/<server>/content/<id>.py` and `made/<server>/tests/<id>.py`, with `Write` and `Edit`, and a class file whose id is a library class's (`engine/library/<id>.py`: a made class of that id would run in the library's place, for everyone); any shell command but `vfg engine` (`reload`; the reads; `start`, `stop`, `grant`, `revoke`, `give`, `take`, `apply`, `clear`, `bind`, `unbind`) in the forms its prompt gives, `vfg cmd`, `vfg test`, `vfg state`, `vfg history`, `python3 -m py_compile`, `sleep` and `echo`, joined with `&&` or `;` and piped only into `head`, `tail` or `grep`; `vfg engine config set|undo` (the brain's) and `vfg engine spawn`; `@a` or `@r` for a player; a bind without `--by <its task>`; an owner's command (the engine's `REFUSED`) or a server-wide setting (`setworldspawn`, `defaultgamemode`, `difficulty`, `worldborder`) in a `vfg cmd` or in a scenario's command args; loops, variables, redirections into files, the background, `WebFetch` and `WebSearch`; and every `vfg task` command. It refuses a `vfg test` when nothing it covers (the test, the class of its name and what the task made, read as code: comments, docstrings and formatting are no change) changed since the run's last test of it, and a fifth in a run; and a `vfg cmd` that only looks (`execute if|unless` with no `run`, `data get`, `list`, `scoreboard players get`) past three a run when there is a test server (`VFG_TEST_BOX` other than `none`), and once the run's four tests are spent. A `vfg cmd` that acts always runs.
- **Claude Code** (`VFG_IMPL_HARNESS=claude-code`, the default; `harness/claude_code.py`): one Claude Agent SDK client per run, the CLI the main agent with nothing of the owner's around it (no settings, skills or MCP servers), its tools `Bash`, `Read`, `Write`, `Edit`, `Glob` and `Grep`, in `bypassPermissions` with the guard as its `PreToolUse` hook, which runs first and whose deny still blocks; as root, where the CLI refuses that mode, `dontAsk` with every use of those tools allowed. Its `Bash` lets a command run 10 minutes when the model sets no timeout (the run's limit, when that is less), and the run's limit at most (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`), so a `vfg test` that waits its turn (590 s in all, unless its own `--timeout` needs more; §8) is not cut off at the CLI's own 2 minutes. By `VFG_IMPL_PROVIDER`:
  - `deepseek` (`deepseek-flash` at `https://api.deepseek.com/anthropic`) or `openrouter` (`deepseek/deepseek-v4.1-flash` at `https://openrouter.ai/api`): DeepSeek V4.1 Flash at the provider's Claude-compatible address, through the relay (`harness/relay.py`), in the brain's own process on 127.0.0.1 at a free port, each run at an address of its own. On every POST to `…/messages` it sets the effort, `VFG_IMPL_EFFORT` (below), whatever the CLI sent: `low`, `high` or `max` as `"output_config": {"effort": <it>}` with no `thinking` field, which DeepSeek's Claude-compatible API takes and OpenRouter turns into its `reasoning.effort`; `off` as `"thinking": {"type": "disabled"}` with no `output_config`. The CLI told to disable thinking leaves the field out, untold it asks for adaptive thinking, and DeepSeek reads a request with no thinking field as thinking on. Everything else, the key among it, goes through as it came, and the answer comes back as it streams; the relay reads each request's usage from it, with the provider that served it and what it billed (OpenRouter's `usage.cost`) when the answer says, and its reasoning tokens, a part of its output (OpenRouter's `usage.output_tokens_details.thinking_tokens`, else estimated from the thinking's text at 3 characters a token), and gives the run a `Request` before the answer ends, so every request is counted. An answer that breaks off as it streams (either side's connection drops) is logged once, on the request's `relay` line, Claude Code's connection is closed so it sends the request again, and the request is still counted, marked broken: on `openrouter` from OpenRouter's record of the generation (`GET …/v1/generation?id=<its x-generation-id>`, asked with the request's own key, 20 s at most), else as far as it was read, a floor; a run's end waits for that record (20 s more), and a run stopped at its limit counts the requests it gives after the stop. On `openrouter` it also sets `provider` on every request: `order` `VFG_IMPL_OR_ORDER` (`together,digitalocean,ionstream`: Together first, for its speed, 259 tokens a second against DigitalOcean's 78, then the two that kept the cache best), `ignore` `VFG_IMPL_OR_IGNORE` (`venice,morph,relace`), and fallbacks allowed, so a run stays on one provider's cache and an outage of those never fails it. The CLI gets the relay's address as `ANTHROPIC_BASE_URL`, the provider's key as `ANTHROPIC_AUTH_TOKEN` and never the owner's login, the one model as every model it may call (`ANTHROPIC_MODEL`, the default Opus, Sonnet and Haiku models, the small fast model, the subagent model), `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, so no request writes a session's title, and its auto-compact window at the model's whole context, 1M tokens, from the price table (`CLAUDE_CODE_MAX_CONTEXT_TOKENS` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW`); the runner logs a compaction should one happen.
  - `anthropic`: Haiku 5.5 (`claude-haiku-5-5`) on the owner's Claude subscription, as before the harness, kept as a setting and not tested: the CLI's own login, never an API key (a run whose CLI would use one is stopped), at `VFG_IMPL_EFFORT` (the CLI's own effort; at `off`, its thinking disabled), its cache's life `VFG_IMPL_CACHE_TTL`; no relay, each request's tokens read from the CLI's assistant messages, one request per message id.

  A message is a second `query()` on the run's open client. The CLI runs with `--replay-user-messages`, echoing each message as it reads it, so the run knows which are unread: one sent while a tool runs is read as soon as the tool calls in flight finish, in the same turn; one that lands as the model ends its turn starts the next turn.
- **OpenCode** (`VFG_IMPL_HARNESS=opencode`; `harness/opencode.py`): one `opencode serve` (OpenCode 1.x; `VFG_OPENCODE_BIN`, else `opencode` on the PATH) per brain, driven through its HTTP API, its config, sessions and caches under `$VFG_BRAIN_DIR/opencode/`, nothing of the owner's own OpenCode read; on `deepseek` or `openrouter` only, at the provider's OpenAI-style address, the effort on every request, and on `openrouter` the same `provider` routing, in its agent's options (OpenRouter's `reasoning: {"effort": <it>}`, or DeepSeek's `thinking: {"type": "enabled"}` and `reasoning_effort`; at `off`, `reasoning: {"enabled": false}` or `thinking: {"type": "disabled"}`); its shell tool's default timeout 10 minutes (`OPENCODE_EXPERIMENTAL_BASH_DEFAULT_TIMEOUT_MS`), OpenCode having no setting for the most; our system prompt as its agent's prompt; every tool allowed in its own permissions, and the guard asked from its `tool.execute.before` plugin hook (`harness/opencode_plugin/guard.js`, JS because OpenCode's plugins are) at an address the brain serves on 127.0.0.1 with a secret, the hook throwing the guard's reason, and refusing the call when it cannot ask; each call put to the guard in Claude Code's names (a patch as a `Write` or an `Edit` of each file it touches, a web tool as `WebFetch` or `WebSearch`); its turns its model requests, the run aborted at the cap; no compaction; each session made with its title, `vfg <task>`, so no title request. A message is a prompt into the busy session, read at its next step.
- **The brief.** The system prompt is the same bytes for every implementer: its rules (`brain/prompts/implementer.md`), then `vfg prefix` (§8): `engine/WRITING.md`, `engine/KIT.md` and every library class's kind, first line, Config and Args as written. The brief is the brain's, in depth, with its `DONE WHEN` checklist (§9), then `YOUR TASK` and `SAVED PLACES` (the engine's, `vfg engine places --json`), then the EXAMPLES block, read as the run starts: at most 3 of the classes `vfg route --task <name>` picks, those that run the job first, whole, a made one followed by its test; the task's own test; every class the brief names; what the engine runs; who is online and where, the time and the weather; and every class this server's implementers made, by first line. The route, the state and the instances are read at once, for at most `VFG_ROUTE_TIMEOUT_S` and a second; what fails is said or left out, and the brief still goes. Its rules say to act on what it was given, and to read a file once.
- **The report** comes after one check, its test (below), else the engine's answer to one start, grant, give or apply, an item that check did not show being not tested; a job outside the game, or the owner's, is reported `Failed` at once. Its first word is `Done`, `Failed` or `Cancelled`; then a short paragraph; then, when the brief has a `DONE WHEN` list, one line an item, done, not done or not tested, and why; then `DESCRIPTION:`. One report covers every message its run read. A last message that is an `<analysis>` or `<summary>` of the conversation is never the report: the run's last text that started `Done`, `Failed` or `Cancelled` is, else the run is resumed once for it, else the report is `Failed`. The runner takes the task's status from the first word, else from the first line that starts with one (a report may open with what it put back), else `done`: `Done` and `Cancelled` are `done`, `Failed` is `failed`. An error, a crash or a stop by the harness is `failed` whatever the text says, and so is a warned run whose report says none of the three.
- **The test is the implementer's check**, run on the test server and never in the live world or on a real player. Anything it makes or binds gets one, `made/<server>/tests/<task>.py`, a `test(t)` with one check per `DONE WHEN` item, which `vfg test <task>` writes a skeleton of when there is none and runs with livetest (§8; `engine/README.md`, *Tests of content: livetest*; `vfg_engine/livetest.py`'s docstring is the test's guide): one engine for the test, with the library, this server's content and the task's bindings; the stage a barrier floor 81 x 81 high in the sky at 3000 296 3000, forceloaded, at night, clear, no mobs spawning, Steve the caster facing north and Alex 4 to his left, Carpet's fake players, on the test server's fresh world (§1, §8); then the engine stopped and the stage cleared. `t` is the engine's ops (`t.give`, `t.grant`, `t.apply`, `t.start`, `t.bind`, `t.cast` as the bridge sends a heard cast …), Carpet's presses (`t.use`, `t.sneak`, `t.look` …), the stage (`t.mob`, `t.blocks`, `t.ground`, `t.cmd`, which only sets it …) and the checks (`t.hurt`, `t.moved`, `t.built`, `t.said`, `t.no_errors` …), each `PASS`, `FAIL` or `CAN'T TELL` with what decided it: the report's done, not done and not tested. A test tries the thing as a player meets it: an incantation by `t.cast`, with nothing pressed after; ground, fire and blocks on what the test placed, never the stage's floor. On a `FAIL` the implementer reads what it printed, decides which is wrong, the class or the test, and fixes that one, never lowering a bar below what the brief asks and saying why it changed a test; three fixes at most, then it reports what still fails, item by item. A follow-up changes the checks for its change and runs it again. A library class used as it is, with nothing bound, keeps the engine's answer as its check, and so does any build when `vfg test` exits 3 (no test server). On 4 or 5 (the test server out of reach, down or busy, after `vfg test` itself tried the box again and restarted it) it never tests on the live server or its players, and reports each item not tested, with why (`vfg test`'s last line). In the live world the implementer neither tests nor probes: beyond what the job asked, it never moves, teleports, hurts or changes a real player, gives one an effect, or summons a mob or sets off a blast near one.
- **A follow-up while the run is live**, or starting, goes into it as a message, `MESSAGE from the brain: <text>`, through `send()`, read at the run's next safe point; nothing is interrupted. A run ends only with no message unread: on Claude Code, a run whose turn ends with one unread waits up to 5 s for the turn that reads it, then ends with it in `Done.unread`. A message the run ended without reading, and every message that went into a run stopped at its limit or crashed, goes to a resume, as a follow-up after the run would; but none after a run a cancel went into, which takes them with it. When `send()` says the run has ended, or the run is reporting, the follow-up waits for the report and then resumes the session (`FOLLOW-UP to <name>, from the brain: <text>`); follow-ups that wait behind one run go in together, so parts of one line make one run. **Every follow-up after a run resumes the task's session**, whatever its size: no fresh start and no summary. A follow-up tests only what it changed and reports only its own items; when the task's thing is not there at all (a run put back, or never finished), it builds it from the task's brief, with the change. Only a task with no session (after a restart) starts a new implementer, on what the task is and the follow-up.
- **Never mind** is a follow-up whose text is code's words (§9), `CANCELLED: the player said never mind. Stop building and put everything back the way it was before the run this cancels, then report Cancelled: and what you put back.`, known by its start, `CANCELLED:`. It goes into a live run as it is; after the run, it resumes the session; behind a run, it drops the follow-ups waiting there; and before a task's first run begins, nothing starts, and the task is reported `Cancelled: it had not started; nothing was made.` The implementer stops, puts back what the run changed, and reports. Then code puts back the rest, from the run's snapshot (`putback.py`): before `gate()` lets a call run, the snapshot keeps, at the run's first change of each, a made file's bytes or that it was not there (a `Write` or `Edit` under `made/<server>/`), a binding as the engine lists it or that there was none (`vfg engine bind|unbind`), and whether the player had an ability (`vfg engine grant|revoke`). After the report, each file not back to its bytes is written back and one the run created removed, with one `vfg engine reload` when a class file was among them (a class that goes with its file takes its instances with it); each binding the run made is unbound and each it replaced or unbound bound again exactly as it was listed, its aliases and everyday aliases as given (`vfg engine bind --aliases … --everyday …`, no alias call), its scenario's args and cooldown, and its `by`; each grant it made revoked and each it revoked granted again. A scenario it started, an item it gave, a mark it applied and a place a class saved are its own to undo. The report gains one line, `Code put back: …`, and is `failed` when it adds `It could not: …`. The snapshot is kept until the task's next run, in memory and in `$VFG_BRAIN_DIR/implementer-snapshots/<task>.json` (mode 600, the files' bytes in it), so a cancel after the run ended puts that run back, after a restart of the brain too.
- **The limits.** A run is warned once, near its limit, by a message in code's words, `LIMIT: you are about to run out of turns and time. Stop building now. Put everything back the way it was before this run, then report Failed: what you tried, why it did not work, and what might.`: at its 95th model request of 100 (`VFG_IMPL_MAX_TURNS`, less 5), counted over every turn of the run, or 60 s before its `VFG_IMPLEMENTER_MINUTES` are up (at three quarters of a limit under 4 minutes). A warned run that reports done keeps its work, unless a cancel went in; any other, code then puts back, as after a cancel. A run that reaches the limit anyway (a request past the cap, the CLI's own turn cap, or the time) is stopped, code puts back, and the runner writes the report from what the guard saw: `Failed: stopped at its limit (its 100 turns); put back to the last working version.` (`its time limit, 1200 s`), what the run had made and changed, and its last 5 tool calls with their errors.
- **Usage, priced by the runner** (`usage.py`, the table in `config.py`): each `Request` is priced at its own size and time, and no harness's running total is read, so nothing is counted twice. Per million tokens, a cache miss, a hit, a write and output: DeepSeek V4.1 Flash on DeepSeek's API (`deepseek-flash`), $0.30, $0.006, $0.30 (DeepSeek has no write price: a miss is input) and $1.20 at its peak, by the request's UTC weekday and hour, Monday to Friday 01:00–04:00 and 06:00–10:00, and half that at every other hour; on OpenRouter (`deepseek/deepseek-v4.1-flash`), the peak price at every hour; Haiku 5.5 (`claude-haiku-5-5`), $0.10, $0.01, $0.125 and $0.50, five times each for the whole of a request over 100K tokens. A model the table lacks costs $0, logged once. A request's reasoning, a part of its output, is priced once, as output. Each request is a `request` line in `brain.log`, `<task> <model> in=<not cached> cached=<n> written=<n> out=<n> size=<n> cost=<$> reasoning=<n>` (`reasoning=~<n>` when estimated from the thinking's text; 0 when it did not think), then `provider=<slug>` and `billed=<$>` when the provider said them, and `broken` for a request whose answer broke off (above). Once the run has reported, or has ended at a shutdown or in a crash, it writes one `usage` row per model, so one per run (`vfg usage add --component implementer --ref <task>`, §8): `input_tokens` every input token of its requests, cached or not, `cache_read_tokens` and `cache_write_tokens` the parts of it, `output_tokens`, `cost_usd` the sum of their prices, and `largest_tokens` its largest request. When every request of the row billed (OpenRouter's, through Claude Code's relay), `cost_usd` is what the provider billed, else the table's; the `usage` line in `brain.log` says which priced it, and the table's price beside it, and its reasoning tokens (`reasoning=`), which the row has no column for, and `broken=<n>` at its end when requests broke off (one with no bill makes the table price the row).
- **Settings**, from the environment, then `~/.vfg/config`, unless marked: `VFG_IMPL_HARNESS` (`claude-code`, or `opencode`); `VFG_IMPL_PROVIDER` (`deepseek` when `DEEPSEEK_API_KEY` is set, else `openrouter`; or `anthropic`); `VFG_IMPL_MODEL` (the provider's, above; `VFG_IMPLEMENTER_MODEL` read when it is empty); `VFG_IMPL_BASE_URL` (the provider's Claude-compatible address, above); `VFG_IMPL_EFFORT` (`high`; `off`, `low`, `high` or `max`, on every provider and harness, `medium` read as `high` and anything else an error that stops the brain; what number a word reaches is the host's: DeepSeek V4.1 Flash's own scale puts `low`, `high` and `max` at 50, 75 and 100 of 100, as DigitalOcean and Ionstream do, and Together at 25, 50 and 100, an `xhigh` reaching it as 50 too, measured through OpenRouter on 2026-10-13); `VFG_IMPL_MAX_TURNS` (100); `VFG_IMPLEMENTER_MINUTES` (20, warned at 19); `VFG_IMPL_CACHE_TTL` (`5m`, or `1h`, the `anthropic` provider's; `VFG_SUBAGENT_CACHE_TTL` read when it is empty); `VFG_OPENCODE_BIN`, from the environment only; `VFG_TEST_BOX` (`box`, the live box's own test server; `none`, none; anything else a test box's settings file), `VFG_TEST_TIMEOUT_S` (60), `VFG_TEST_QUEUE_S` (300), `VFG_TEST_BOOT_S` (120) and `VFG_TEST_SANDBOX` (`auto`), `vfg test`'s (§8); `VFG_IMPL_OR_ORDER` (`together,digitalocean,ionstream`) and `VFG_IMPL_OR_IGNORE` (`venice,morph,relace`), comma-separated, `none` for none; and the provider's key (§11).
- **Content is the classes the engine runs** (the game engine spec, [`engine/WRITING.md`](../engine/WRITING.md)): an `Item` (held), an `Ability` (granted, then cast), a `Mark` (applied, for a while), an `Actor` (a body a scenario spawns) or a `Scenario` (started, with its args); one class a file, its id the class's name in snake_case (or its own `id`), starting with a letter, every number in its `Config`, the same for everyone. It imports only `vfg_engine` and its kit, never another content class, so any one reloads on its own. Two folders, the library first: **the library**, `engine/library/<id>.py`, the server's base content and the examples implementers read, shipped with the engine to `/opt/vfg/engine/library/` by `bridge/deploy/deploy.sh`; and **this server's**, `made/<server>/content/<id>.py` on the PC (gitignored, as `made/` is), what its implementers wrote, deployed whole to `/opt/vfg/made/<server>/content/` by `vfg engine reload` and `config set|undo` (§8): packed as a folder, no caches and no dotfiles, unpacked beside it on the box and swapped in under `run/deploy.lock`, left as it is when every file is the same. **A server's class shadows the library's**: one in the later folder with the id of a library class replaces it, logged, its live instances switching as on any swap, and `classes` and `config_get` say `shadows: <the library's file>`; when its file goes, a full reload runs the library's version again. The same id twice in one folder, or one id for two kinds, is refused. Only `vfg engine config set` makes such a class (its `.library.py` kept in `.history`): the implementer guard refuses a Write or Edit that leaves a class of a library id, whatever the file is called, and a deploy refuses one that is not that copy. A copy whose code is still the library's as it was copied, its Config values aside, is rebuilt on each deploy when the library's file changed: the new file with this server's values put back (the old kept as `*.before-rebase.py`, op `rebase` in `.history/log.jsonl`); a copy changed by hand is left as it is, with a warning on each deploy and from `config get`. **The kit**, `vfg_engine.kit` ([`engine/KIT.md`](../engine/KIT.md)), is what several classes share (targets, blasts, blocks, movement, spawning, the show, input, players), each helper taking the instance and `ctx` and using only the public content API: one way to do each thing, never typed out again in a class. Nothing of a class runs until the engine's `reload`, which checks it before anything switches (it imports, one kind and its Config base, an id that starts with a letter, no `while True` or sleep, its `State()` made from its defaults, every required field, every bound, `damage(ctx)` a number at power 0, 10 and 20, an item's base able to report its triggers, an actor's entity type in 26.3, a Scenario's or Mark's Args with a default and a description for every field): a class that fails leaves the old one running, and every running instance of one that passes switches to it at once.
- **Args** are what a Scenario's start, or a Mark's application, takes: `class Args(Args)`, every field with a default, bounds and a one-line description in players' words. The types: `Player` (one online player's name), `Players` (`"@a"`, `"@r"` or names, read fresh each time), `Place` (a saved place's name, `"x y z [dim]"`, or a player's name, resolved at the start to a spot), `EntityType`, `BlockId`, `BlockMix` (`"70% stone 30% andesite"`), `ItemId`, `ReplaceRules` (`"snow > air; solid > 70% lava 30% keep"`), `Command` (never an owner's), `Seconds`, or a plain number, text or true or false with bounds. `start` and `apply` check what they are given against it and refuse in words, an arg not declared too; `classes` and `meta` show each class's args (`{name, type, default, bounds, description}`), which ENGINE lists (§9). Items and abilities take none: their numbers are their Config. A scenario reports with `self.result(summary, **facts)`, a one-shot then `self.end()`; a `start` with `wait_s` (at most 30) answers with that result once it ends, or as soon as one that goes on reports one.
- **Incantations are the game engine's bindings** (the game engine spec's *Incantations*): per player, never `@a`, a phrase bound to one of the engine's abilities (a cast of it; a bind grants nothing) or to a scenario with args set once (a start of it; an arg given as `caster`, a Player or Place arg, is filled with whoever casts it, and so is a Player arg whose default is `caster` when the binding leaves it out), with its own `cooldown_s`, 3 s unless bound with another. `engine_bind` (§14) and `vfg engine bind` (§8) make one, `engine_unbind` takes it away. vfg makes its aliases first: the code's (the phrase joined, compound words split) and one `structured()` call's (`VFG_INCANT_ALIAS_MODEL`, its usage row `alias` with the phrase as its ref, sent by `vfg usage flush`), asked for exactly 20 with each word's pronunciation; the code then drops the phrase itself, repeats, any 3 speech sounds longer than the phrase or more (an H weighed 0.25, an AH 0.5, as Layer 2 weighs one put in), and any more than 0.35 from it in sound, the weighted edit distance of their phonemes over the phrase's count (what it dropped in the line's `facts.alias_call.dropped`), then those under 4 speech sounds and past 24. It keeps as `everyday_aliases` those the alias call flags as a common phrase of their own, said meaning something else ("ice cream" and "i scream" for "ice beam"; never the code's own), a subset of `aliases`, which `GET /v1/incantations` leaves out, so the spotter never listens for them; and it adds a note when the phrase is short, is everyday talk, or sounds like, or starts like, another of that player's. The phonetic rules are the bridge's own (`bridge/vfg_bridge/sounds.py`), which vfg loads by its path. The engine keeps the bindings in its state and writes them, whole and atomically, on every change, to its export `/opt/vfg/engine/incantations.json` (`VFG_ENGINE_EXPORT`): `{"version", "incantations": [{"id", "player", "phrase", "aliases", "everyday_aliases", "ability" | "scenario" and "args", "by", "cooldown_s"}]}`, the `id` `steve.fire_ball`, `cooldown_s` an ability's Config's or a scenario binding's own; its version holds across restarts. The bridge and the Jev filter read it; only the engine writes it. Three layers cast, all through the bridge's one cast path (§2): the mod's spotter, Layer 2 on the transcript of a line of at most 6 words (`VFG_INCANT_LAYER2_MAX_WORDS`), and the Jev filter's cast check on any line the first two left (§5, `VFG_JEV_CAST_MIN` on the chosen option's probability, `VFG_JEV_CAST_MIN_LONG` on a line of more than 6 words, whose line is kept and routed; a short line's dropped only when its cast is sure, `VFG_JEV_CAST_SURE`, else kept and routed too); the bridge never fires a Jev cast whose line it received more than `VFG_JEV_CAST_MAX_AGE_S` (2 s) before: it is `stale`. The old store's bindings were moved in once, onto the classes that took their actions over, by `vfg engine migrate` (§8).

## 11. Secrets

- On EC2, `TYPESAFE_API_KEY` and `VFG_CLIENT_TOKEN` live in `/opt/vfg/.env` with mode 600. On the owner's PC they may live in the `.env` file `VFG_BOX_ENV` names (default `~/.vfg/box.env`, mode 600, outside any repo). `deploy.sh provision` and `deploy.sh env` send only the names `env.example` lists, over SSH on stdin, and make the client token on the box when none is given.
- On the owner's PC, settings live in `~/.vfg/config`. The client token also lives in each player's mod config. The OpenRouter key is `OPEN_ROUTER_API` in the environment, or alone in the file `VFG_OPENROUTER_KEY` names (default `~/.vfg/openrouter.key`, mode 600); the config holds the path, never the key, and only `structured()` and the implementers (§10) read it.
- An implementer's key is its provider's: `DEEPSEEK_API_KEY`, from the brain's environment only, for `deepseek`; the OpenRouter key, read as `structured()` reads it, for `openrouter`; none for `anthropic`, the owner's Claude login. It goes only into the harness's environment, as Claude Code's `ANTHROPIC_AUTH_TOKEN`, which the relay passes on as it came, or as OpenCode's server's, blanked in the shells its tools start; it is never printed, logged or written.
- The test server's side holds no secret (§1): `/opt/vfg-test` has no `.env` (its setup removes one, and `vfg test` refuses a vfg folder that has one), and `/opt/mc-test/server.properties` (mode 640, group `vfgtest`, the sandboxed test's user, §1) has its own random RCON password, never the live one's. A test runs with no setting whose name holds `TOKEN`, `SECRET`, `PASSWORD` or `API_KEY` in its environment, and, sandboxed, can read neither the live `/opt/mc`, the live RCON password among it, nor anything of the live `/opt/vfg` but its Python and the engine's code (§8). A file `VFG_TEST_BOX` names holds a test box's settings, the SSH key's path among them, never a key (§8).
- The RCON password never leaves `server.properties` on EC2.
- No secret goes in the repo.

## 12. Startup — the brain sets everything up

1. The owner runs `vfg brain start` (`brain/run`).
2. The brain sets aside a `tasks.json` an older brain left in its folder (§9), then runs `vfg up`, then `vfg watchers set …`, then `vfg lookout set …` and `vfg jev menu set …`, its actions for Jev's state (§5); it sets the menu again whenever an action is added. It sends the usage rows queued while it was down, `vfg usage flush` (§4).
3. It reads the context with `vfg context --json`, the feed's rows and then its tasks, every row of the box's `tasks` table, fails every task still open (§9), and follows the feed with `vfg watch --after` the `last_seq` that gives, so nothing is lost across a restart and nothing older is read as new. A read that fails is tried again; the feed is never followed from 0.
4. It greets the players with `vfg say`, skipped when nobody is online.

## 14. Actions from the brain — the owner's PC

**A step of the brain's loop runs its actions** (§9), each written in full in its answer: `vfg action run <action> key=value …` (§8), reading its one line; `together` all at once, `in_turn` one after another, stopping at the first that does not land. It carries no task: only an implementer's work is one. Its values are checked first, as vfg checks them; a scenario's or a mark's args go to the engine, which checks them against the class's Args. Nothing is retried in code: a value vfg or the engine refuses, or a command Minecraft refuses in a scenario's run, goes back to the next step, Minecraft's error with the reference of every command it used (the server's command tree and the command's wiki page, from `~/.vfg/brain/refs/<version>/`), and that step fixes it; an action vfg could not run at all (the box out of reach, the engine down) goes back as `did not run`. No row is written per action: the loop leaves one record (§7, §9).

- **The menu is the engine's ops, and there is no other way to act on the game**: the actions in `actions/` (`actions/README.md`), each as its name and docstring's first line, every one in full in a step's opening (its docstring, the op it goes to, each field it fills): `engine_start` (`scenario`, `args`) and `engine_stop` (`scenario`, every run of it, or `instance`), `engine_give` and `engine_take` (`player`, `item`), `engine_grant` and `engine_revoke` (`player`, `ability`), `engine_apply` (`player`, `mark`, `args`, `seconds`) and `engine_clear` (`player`, `mark`), `engine_bind` (`player`, `phrase`, and `ability`, or `scenario` with `args` and `cooldown_s`) and `engine_unbind` (`player`, `phrase`), and `engine_config` (`class_id`, and `config`, the class's whole new Config in Python). Each names the engine's control op in its `engine` and runs no script. What they act on is ENGINE (§9), every class with a scenario's and a mark's args, and RUNNING NOW, where a scenario that goes on is by its instance. The prompt names the library's everyday scenarios by id: `command` (raw server commands, `args.commands`), `teleport`, `save_place`, `forget_place` and `horde`. A grant lands before its bind: the grant in one step, ending `next`, the bind in the next. A change to an engine class's numbers is its Config, read (§9) and rewritten for everyone, whoever asks, values only (§8): a formula is never rewritten; a different version for one player is a new class, handed off.
- **An item a player owns** is changed by its slot, which the world names (`hotbar.4 iron_sword (held)`), with one `item modify` through the `command` scenario: the speaker's items are in every step's prompt, and another player's come from a step's read. The held one, then the worn one, then the first listed; for an item the player does not have, nothing runs and the reply says so.
- **Saved places are the engine's own**, in its state, per world (a fresh world starts with none): `{name: {dim, pos, yaw, by, at}}`, a name of lowercase letters, digits and `_` (spaces and hyphens made `_`), at most 32, `by` the task that saved it. Content reads them (`ctx.places.get(name)`, `ctx.places.all()`) and writes them (`self.save_place(name, at, by=None)`, `self.forget_place(name)`); the library's `save_place` scenario is how the brain names a place, and a class that builds saves the place it built under the name it was given. A `Place` arg takes a saved place's name. `vfg engine places` lists them and `overview` gives them to the brain; every prompt — the brain's, every implementer's brief — carries them as one line, `SAVED PLACES: castle 197 68 251 overworld (castle_steve); …`, or `SAVED PLACES: none`. The old `everhear:places` list was imported once, through `places_import` (`vfg engine migrate`, §8).
- **Building is a scenario's**: Minecraft's command list in the prompt leaves out the commands that place or remove blocks (`setblock`, `fill`, `clone`, `place`, `fillbiome`), and the owner's, which the engine refuses whoever sends them (`engine/vfg_engine/mc/commands.py`'s `REFUSED`); a class builds through the engine's block queue, which spares protected places.
- **Settings**, from the environment, then `~/.vfg/config`: `VFG_BRAIN_DIR`, `VFG_BRAIN_MODEL` (`deepseek/deepseek-v4.1-flash`), `VFG_BRAIN_REASONING` (`low`), `VFG_BRAIN_PROVIDERS` (`together,coreweave,parasail`; `none`: OpenRouter's choice), `VFG_BRAIN_TIMEOUT_S` (120 s a step's call, or 60 s with the brain's reasoning `off`, its resend and retries included; set, it wins), `VFG_LOOP_STEPS` (10 steps for a loop's first line, and as many for each line added), `VFG_LOOP_CAP` (20), `VFG_LOOP_TAKE_UP_S` (120), `VFG_TURN_WAITING` (3), `VFG_TURN_SETTLE_S` (3), `VFG_RESPOND_MODEL` (`deepseek/deepseek-v4.1-flash`), `VFG_RESPOND_REASONING` (`off`), `VFG_RESPOND_PROVIDERS` (`together,coreweave,parasail`), `VFG_RESPOND_TIMEOUT_S` (20 s a conversation agent call), `VFG_ROUTER_MODEL` (`deepseek/deepseek-v4.1-flash`), `VFG_ROUTER_REASONING` (`off`; no longer changes what is said, only `VFG_ROUTER_TIMEOUT_S`'s default), `VFG_ROUTER_PROVIDERS` (`together,coreweave,parasail`), `VFG_ROUTER_TIMEOUT_S` (30 s a router call, 60 s with its reasoning not off; set, it wins), `VFG_BRAIN_CHECKPOINT` (5), `VFG_BRAIN_HISTORY_HOURS` (6), `VFG_DISPATCH_ACTION_TIMEOUT_S` (20 s an engine op, unless its action's `timeout_s` says more: `engine_start` 45, `engine_bind` 40, `engine_config` 60; vfg's answer waited for 10 s past it), `VFG_SERVER` (`main`), `VFG_REPO`, `VFG_OWNER`, and the OpenRouter key (§11). The `VFG_ORCHESTRATOR_*` and `VFG_PLAN_*` keys went with the orchestrator call and the retry planner, and `VFG_LOOP_SECONDS` with a loop's time limit; one left in `~/.vfg/config` is ignored, `VFG_LOOP_SECONDS` logged as the settings load.
