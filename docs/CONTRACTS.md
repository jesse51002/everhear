# Everhear contracts

_The contract the parts were built to (draft, 2026-10-07; the dispatcher, §14, 2026-10-09; actions, §1, §8, §10 and §14, 2026-10-10; incantations, §2, §4, §7, §8 and §10, 2026-10-10; the brain, which replaces the conversation, the orchestrator and the dispatcher, §1, §4, §5, §7, §8, §9, §12 and §14, 2026-10-10; the Jev routing, §5 and §7, 2026-10-11; named tasks, a name and a `tasks` row for each implementer's task, and the brain's orchestrator call, §1, §4, §7, §8, §9, §10, §12, §13 and §14, 2026-10-11; the implementer harness, implementers on DeepSeek V4.1 Flash behind any harness, a message into a live run, a cancel that puts back, and usage priced by the runner, §4, §8, §10 and §11, 2026-10-11). Code comments cite it as "Contracts §N". Where the code has moved on — model choices — the code and the part's README are current._

**What every part of the prototype takes in and puts out, so each part can be built from its own spec in one prompt and still fit the others.** A part's spec may decide anything inside the part; it may not change anything here. Where a part needs this page to change, the change is made here first.

**The pattern is the one that already worked**: an SSH `tail -F` of a file on the EC2 box, RCON over SSH to act, `tellraw` to answer. One feed file carries everything the brain should hear — kept speech, watched game events — and what the brain itself did, so there is one stream, and it is the shared context.

## 1. Where things run

- **EC2** (one Amazon Linux 2023 instance): the Minecraft Java server, vanilla 26.3, in `/opt/mc`, systemd unit `minecraft`, its console written to `/opt/mc/console.log`; the **bridge** (`vfg-bridge`) and the **Jev filter** (`vfg-jev`) in `/opt/vfg`; the database `/opt/vfg/vfg.db`, the transcript history and the brain's tasks (§4); the feed `/opt/vfg/feed.log`; deployed scripts in `/opt/vfg/scripts/`, with `_lib/` (the kit, `mc.py`, `instances.py`, `places.py`, `commands.py`); each running copy's files in `/opt/vfg/run/` (§10). Open to the internet: Minecraft `25565` and the bridge's speech port `8787`. SSH only from the owner's IP. RCON `25575` is never reachable from outside — vanilla binds every interface, so the security group and a host firewall rule keep it in. Every unit runs as `ec2-user`, which owns `/opt/mc` and `/opt/vfg` (the database and its `-wal` and `-shm` files included) and has passwordless `sudo` for `systemctl` and `journalctl`, as Amazon Linux 2023 sets it up.
- **Players' PCs**: Minecraft Java 26.3 with Fabric and the **client mod**.
- **The owner's PC**: this repo; the **`vfg` toolkit**; the **brain** (§9), its **orchestrator call**, and the **implementers** it starts; the **actions** `actions/`, and `made/<server>/actions/` for what implementers made; the **scripts folder** `scripts/` (and `made/<server>/scripts/`). It reaches EC2 only over SSH; the brain also calls OpenRouter.

Every timestamp is ISO-8601 UTC with milliseconds (`2026-10-07T18:22:31.412Z`). Every id is a ULID unless stated.

**The units** start the server jar in `/opt/mc` (`minecraft`), `/opt/vfg/python/bin/python3 -m vfg_bridge` (`vfg-bridge`) and `/opt/vfg/python/bin/python3 -u /opt/vfg/jev/jev_filter.py` (`vfg-jev`).

**Python on the box** is 3.12, the PC's version: uv, installed into `/opt/vfg/uv/` as a step of the box's setup (`deploy.sh provision` runs `bridge/deploy/python.sh`), installs CPython 3.12 there, and `/opt/vfg/python` links to it. `/opt/vfg/python/bin/python3` runs the units, the scripts and every `vfg` remote program; Amazon Linux's own `python3` (3.9) is left to the host's tools.

**The code** is one repo, a folder per part: `client-mod/`, `bridge/`, `jev/`, `toolkit/`, `brain/` (the brain, its orchestrator call, Respond and the implementers), `actions/`, `lib/py/` (`structured()`, every model call that wants a structure back; `vfg_actions`, the one loader of the actions), `scripts/`. What runs on EC2 is deployed to `/opt/vfg/`; `vfg action run` deploys a copy's script and `scripts/_lib/` when the box does not have them as the PC does: each deployed folder keeps the stamp, a hash of its files, it was sent with (`.vfg-stamp`), and a run sends the stamps first. An action never leaves the PC: it is a class that names a script and checks its values (§10).

## 2. Speech in — client mod → bridge

`POST {VFG_BRIDGE_URL}/v1/lines`, header `Authorization: Bearer {VFG_CLIENT_TOKEN}`, body:

```json
{ "client_line_id": "uuid-v4", "player_uuid": "…", "player_name": "Steve",
  "text": "build me a castle",
  "started_at": "2026-10-07T18:22:29.100Z", "ended_at": "2026-10-07T18:22:31.400Z",
  "peak_dbfs": -8.2, "mean_dbfs": -23.5 }
```

- `202 {"id": "<line id>"}` stored; `400` bad body; `401` bad token. The token is checked before the body, so an empty `{}` with a good token gets `400` — the mod's connection test relies on it. Repeating a `client_line_id` returns the first id and stores nothing. An empty `player_uuid` is stored as NULL, the same as an AI line.
- Plain HTTP is accepted for the prototype: the token only lets someone post lines.
- **Incantations** — a phrase of two words or more, bound for a player to an action with its values, fires that action the moment that player says it, with no model on its path. The mod's keyword spotter hears it and posts a **cast**, its own request, beside the line pipeline: neither waits on the other.
  - `POST {VFG_BRIDGE_URL}/v1/casts`, the same token, body `{"client_cast_id": "uuid-v4", "player_uuid", "player_name", "phrase": "fire ball", "heard"?: "fireball", "started_at", "ended_at"}`: the incantation's own phrase (the mod maps a matched alias back to it), and the phrase's window on the mod's audio clock, the clock a line's times use. `202 {"id", "status": "fired"|"cooldown"|"duplicate"|"failed"|"stale", "copy"?, "error"?}` as soon as the copy is spawned; `404` when the player has no such incantation (their own or `@a`); `400`, `401`; `503` when the kit is not on the box, or is older than the bridge (no `incantations.cast_meta` or `instances.Box`), its error saying why: deploy it again with `vfg script deploy --kit`, which `bridge/deploy/deploy.sh` runs with every deploy of the bridge. Repeating a `client_cast_id` answers what the first did.
  - The bridge starts the bound action's copy on the box itself (`scripts/_lib/instances.py`, from the entry in `/opt/vfg/incantations.json`, §10), through the kit's `incantations.cast_meta(entry, player)`, with every caster field set to whoever cast; a test's cast (§10) is started the same way. With it goes `asked`, the values the binding asked for and the caster fields: those keep the bound value, and every other value is the action's as deployed now (`action_defaults.json`, §10), so a value the action gained after the binding was made has its default. A cast's copy runs with `VFG_TASK=cast` (`mc.cast()` is true) and acts as it starts: nobody presses anything after a spoken word. A cast of an incantation whose window, widened by `VFG_CAST_SLACK_S` (0.3 s) each side, overlaps one of that player's that fired is `duplicate`; within its own `cooldown_s` of its last fired cast, or within `VFG_CAST_GAP_S` (1 s) of any of that player's, it is `cooldown`. Cooldowns are on the bridge's clock.
  - The mod's settings: `incantations` (on), `incantation_threshold` (0.25) and `incantation_boost` (1.5), the spotter's; `heard` is the keyword it matched, normalised (`fireball`). It spots only while it listens, and only that player's own incantations, `@a` ones included; no audio leaves the PC, only the phrase.
  - `GET {VFG_BRIDGE_URL}/v1/incantations?player=Steve&after=<version>&wait=<s>`: `200 {"version", "player", "incantations": [{"phrase", "aliases", "cooldown_s"}]}`, the incantations that apply to that player, `@a` ones included; with `after` the current version it is held until the version changes or `wait` (default 25, at most 30) seconds pass, then `304`. The mod long-polls it while connected.
  - **Layer 2 and the drop rule, on `/v1/lines`.** For a voice line from a player with incantations, a phoneme match of the transcript against their phrases and aliases (`VFG_INCANT_ALLOWANCE`, 0.25) fires a cast through the same path, layer `transcript`, with the line's window. Then a line that overlaps one of that player's casts and has at most one word left once the phrase is taken out (fillers not counted) is stored with `dropped = 'cast'` and never judged or fed (§5); a kept one gets `cast_id`.
- The mod captures only while connected to the server whose address matches its configured `server_address`; a line captured then is still delivered after the player leaves, within its 60 s. A line is speech ended when the mod's turn model hears it finished, or by **`silence_seconds` of silence** (default 3). `text` is 1–2000 characters after trimming. On failure it retries with backoff for up to 60 s, then drops the line.

## 3. Chat and game events — Minecraft server → bridge

The bridge tails `/opt/mc/console.log` and parses it.

- **Chat** `<Name> message` becomes a line with `source = chat`, in the same table as speech, and goes through Jev the same way.
- **Events**, kinds `join`, `leave`, `death`, `advancement`, `server` (start or stop), always go into `events`, and into the feed only if watched (§6).
- RCON echoes, `Played sound`, `Set spawn point` and other noise are ignored.

## 4. Transcript history — `/opt/vfg/vfg.db` (SQLite, WAL)

The bridge creates the schema. The Jev filter writes only the `jev_*` and `fed_at` columns and `usage` rows.

```sql
CREATE TABLE lines (id TEXT PRIMARY KEY, at TEXT NOT NULL, ended_at TEXT,
  player_uuid TEXT, player_name TEXT NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('voice','chat','ai')), text TEXT NOT NULL,
  peak_dbfs REAL, mean_dbfs REAL, client_line_id TEXT UNIQUE,
  jev_class TEXT CHECK (jev_class IN ('action_oriented','conversational','context','not_relevant')),
  jev_confidence REAL, jev_judged_at TEXT, fed_at TEXT);
CREATE INDEX lines_at ON lines(at);
CREATE INDEX lines_player_at ON lines(player_name, at);
CREATE TABLE events (id TEXT PRIMARY KEY, at TEXT NOT NULL, kind TEXT NOT NULL,
  player_name TEXT, text TEXT NOT NULL);
CREATE INDEX events_at ON events(at);
CREATE TABLE feed (seq INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL, line TEXT NOT NULL);  -- line: the whole line, exactly as in feed.log
CREATE TABLE usage (id INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL,
  component TEXT NOT NULL CHECK (component IN ('jev','conversation','orchestrator','implementer','brain','respond','planner','alias')),
  model TEXT, input_tokens INTEGER, output_tokens INTEGER, cost_usd REAL, ref TEXT);
```

- **Incantations** (§2): `lines.dropped` (`'cast'`: only an incantation, never judged or fed) and `lines.cast_id` (the cast the line's speech overlapped), and the bridge's own table `casts (id, at, started_at, ended_at, player_name, phrase, heard, layer 'spotter'|'transcript', incantation_id, action, copy, status 'fired'|'cooldown'|'duplicate'|'failed'|'stale', error, line_id, client_cast_id UNIQUE)`. A fired or failed cast is also an `events` row of kind `cast`.
- It is queried by date with `vfg history` (§8).
- **The AI's own messages are lines too**: every `vfg say` is stored with `source = 'ai'`, `player_name = 'AI'`, no uuid, and the text without the prefix. A whisper is stored as `(to <player>) <text>`. They give Jev the other half of the conversation, and are never judged; `vfg say` feeds each as an `AI say` line itself (§7).
- **The shared context is the `feed` table** (§9): every kept line, every fed game event and everything the brain recorded, in `seq` order, each with its `processed_at` mark: a column added after this DDL, by `ALTER TABLE` on the bridge's start, as are `usage`'s `cache_read_tokens`, `cache_write_tokens`, `ok`, `error`, `ms` and `largest_tokens`. A database built before the four classes is rebuilt on the bridge's start: `direct_ask` becomes `action_oriented`, `not_useful` becomes `not_relevant`; one built before `planner` and `alias` gets its `usage` CHECK rebuilt the same way, every row kept. `conversation` stays a valid component only for old rows; `orchestrator` is the brain's orchestrator call's again (§9).
- **`usage` is the one log of every model call.** Every `structured()` call (`lib/py/vfg_llm.py`, §1) records its own row, whatever happens: its `component` (one of `vfg_llm.Component`, the CHECK's list: `brain`, `respond`, `orchestrator` and `planner` are the brain's, `alias` the incantation alias call's), `ref` its `call_id` (at most 64 characters), its tokens and cost summed over every attempt, `ms`, and `ok` 1, or 0 with `error`, the reason, one line of at most 300 characters. A failed call is a row with what it cost; one that timed out or was cancelled with an attempt in flight, which OpenRouter bills at a price it never told, has `cost_usd` NULL, and its `error` says what the attempts that came back cost. The row is appended to `usage.pending.jsonl` on the PC, under `usage.pending.lock`, in the folder `VFG_USAGE_QUEUE` names in the environment (default `$VFG_HOME`; the replays point it at their own output, so their rows reach the box only when sent on purpose), and `vfg usage flush` (or the next `vfg usage add`) with the same `VFG_USAGE_QUEUE` sends it (§8); recording never fails a call, never waits on the box and never holds up the caller's event loop. Jev's filter writes its rows itself, and the implementers theirs through `vfg usage add`; those leave `ok`, `error` and `ms` NULL. An implementer's row is one run, its requests each priced by the runner (§10), with `largest_tokens` its largest request; every other row leaves `largest_tokens` NULL.
- **The brain's tasks** (§9) are the `tasks` table, one row per implementer task, keyed by its name. The bridge creates it after this DDL, as it does `casts`, on every start and every `--init-db`, so an older history gains it and nothing else changes (`PRAGMA user_version` 4); it never writes it. Only the brain writes it, through `vfg task set` (§8):

  ```sql
  CREATE TABLE IF NOT EXISTS tasks (name TEXT PRIMARY KEY, description TEXT NOT NULL, player TEXT,
    status TEXT NOT NULL CHECK (status IN ('open','done','failed')), line TEXT, brief TEXT,
    made TEXT, variables TEXT, session TEXT, result TEXT, created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL, closed_at TEXT);
  ```

  `name` matches `^[a-z][a-z0-9_]{1,31}$` (`galick_gun_styrk`), is never a library action's name or `cast` (the bridge's task for an incantation's copies), and is kept for life. `description` is what the thing is now and for whom, `line` the player's words that started it, `brief` the latest brief, `session` its implementer's session, `result` the brain's last record of it. `made` is JSON, `{"scripts", "actions", "presets", "copies"}`, each a list of names; `variables` is JSON, the fields of the task's action as `vfg_actions.variables()` reads them (`{"name", "type", "default", "ge", "le", "choices", "live", "fixed", "description"}` each), or null until read. `closed_at` is set as the status leaves `open`, and cleared when it opens again.

## 5. Jev — the Jev filter

- Takes lines with `jev_class IS NULL` and `source` other than `ai`, in `at` order, polling every 250 ms or less.
- Calls Jev — `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, key `TYPESAFE_API_KEY` — once per new line, the routing call. The state is the fixed rules (the setting and how to read the state; they define no class), then `/opt/vfg/lookout.md` (what to look out for), then a block of invented examples under what should become of each, then `/opt/vfg/menu.md` (the brain's actions, one `name — what it does` line each, which `vfg jev menu set` writes), then history: recent lines, the AI's included, and the brain's records of the actions it ran and the tasks it opened (`AI` feed lines), so a follow-up to an earlier ask reads as one — as much as fits in `VFG_JEV_STATE_TOKENS` (default 8,000). The line is marked `[1]` in the history and gets two `choice` questions, D2's: what should happen with it (`d_what`: the AI must act, the AI should answer in chat, remember it, ignore it), and how the speaker would feel if the AI only replied in chat (`d_feel`: fine, let down, they wouldn't notice). The answers walk onto four classes, with `d_what`'s confidence:
  - `action_oriented` — act, and let down: the brain;
  - `conversational` — answer, or act with `d_feel` anything else or missing: Respond;
  - `context` — remember: kept, and shown to no model (§9);
  - `not_relevant` — ignore: never fed.

  A missing or malformed `d_what` is Jev failing. Each line is judged once: nothing is asked again.
- Writes the verdict to the line, and a `usage` row with `component = jev`.
- **The gather call.** A line classed `action_oriented` or `conversational` gets one more call before it is fed, over its speaker's lines that Jev classed `context` or `not_relevant` with a confidence (never a line passed as `context` while Jev failed open or after it refused the line twice), judged after that speaker's last `action_oriented` or `conversational` line was judged, said before the line and at most 180 s before it, not blank and not dropped — the newest 10. Judge order, not the order said, because a voice line is stored once its speech is text, after a line typed later may have been judged: each line is offered to the speaker's next line to the AI judged after it, and to no other. When there are none, no call is made. The state is built the same way, with the gather call's own rules and history heading, the line marked `[ask]` and those lines `[1]` … `[n]`, and each of them gets one `choice` question: is it part of the ask (`part_of_the_ask`, `not_part_of_it`); a missing answer is a no. The yes lines go with the ask as one `LINE` (§7): their texts and then the ask's, in the order said, joined with ` … `, the oldest dropped first when that is over 500 characters, under the ask's fields and time. A gathered line keeps its own class and is fed, or not, as before. A gather call that fails feeds the ask alone, and does not count towards failing open. It writes a `usage` row with `ref = gather:<ask id>`, and one `gather` line to the journal. The filter holds a group in memory until the ask is fed, so an ask caught by a crash in between is fed alone.
- **Feeds what it keeps** (`action_oriented`, `conversational`, `context`) in batches. An `action_oriented` or `conversational` line flushes the batch at once, with whatever context is waiting: both get a live answer. Otherwise a batch flushes `VFG_BATCH_SECONDS` (default 5) after its first line.
- If Jev fails for 10 s it **fails open**: every line passes as `context` with no confidence, and one `SYS` line says so. No model is shown a `context` line (§9), so while Jev fails open the brain answers none of them. Another `SYS` line says when Jev is back.

## 6. Game watchers — `/opt/vfg/watch.json`

```json
{ "events": ["join","leave","death","advancement","server"], "players": [], "contains": [] }
```

- `events` are the kinds to feed. `players` limits them to those players; empty means everyone. `contains` holds extra regexes on raw console lines, fed as `GAME raw`.
- Every kind is on by default. The bridge rereads the file when it changes. The brain sets it with `vfg watchers set` as it starts.

## 7. The feed — `/opt/vfg/feed.log`

**The one stream the brain follows, and the shared context.** It is append-only, one event per line, and mirrored in the `feed` table. The bridge and the Jev filter write it through one locked writer that assigns `seq`. The owner's PC writes it only through `vfg say` and `vfg feed post`, and only the brain does.

```text
LINE#812 18:22:31 Steve voice action_oriented 0.93 -8dB | build me a castle
LINE#813 18:22:33 Alex chat context 0.71 - | that cave by spawn
AI#814 18:22:35 task castle_steve | new: A castle for Steve at spawn, about 40x40, stone and oak
AI#815 18:22:35 say castle_steve | on it, castle coming up
GAME#816 18:22:40 death Steve | Steve was slain by Zombie
AI#817 18:24:02 result castle_steve | castle_steve done: castle built at spawn, 40x40
SYS#818 18:25:00 | jev unavailable — passing every line as context
```

- The grammar is `TYPE#seq HH:MM:SS fields | text`. `TYPE` is `LINE`, `GAME`, `AI` or `SYS`. The time is UTC. The fields, separated by single spaces, with `-` for anything missing:
  - `LINE`: `<player> <voice|chat> <action_oriented|conversational|context> <confidence|-> <NdB|->`. The confidence has two decimals and is `-` when Jev fails open; dB is the line's peak, rounded, and `-` for typed chat. A line fed before the Jev routing may end with ` was=not_relevant`, from the re-ask that is gone; the writer still accepts it, and nothing writes it now. The text may hold a group (§5): the lines Jev gathered into an ask, then the ask, in the order said, joined with ` … ` — `the castle by the river … the big one … make it bigger`.
  - `GAME`: `<kind> <player|->`, any kind the bridge feeds.
  - `AI`: `<say|action|task|result|note> <name|->` — what the brain did, which only it writes. The second field is a task's name (`[a-z][a-z0-9_]{1,31}`, §4), or `-` where no task applies, and never a copy's name or a `#seq`: `say`, a chat line it sent (as the `lines` table keeps it), under the task it is about (the first one opened or followed up on its line, or the one reported); `action`, an action it ran and how it went, always `action -`: an action never carries a task; `task`, a task the orchestrator call opened (`new: <description>`) or a follow-up it sent (`follow-up: <brief>`); `result`, a task's result, one short line (`<name> done: …`, `<name> failed: …`); `note`, anything else it records, such as a running copy it changed or stopped (`edited <copy>: k=v …`, `stopped <copy>`, `couldn't edit <copy>: <why>`), under the copy's task when that is a name, else `-`. Nothing an implementer writes is ever fed. Rows written before named tasks carry the old `T<n>` ids and still read: only a write is checked.
  - `SYS`: no fields.
- The `ORCH` type of the orchestrator is retired.
- Text has newlines replaced by spaces and is cut at 500 characters with `…`.
- A batch is written in one go, under 200 ms.
- **Every kept line is fed exactly once**, across restarts and crashes: before feeding a line not yet marked `fed_at`, the Jev filter looks for it in the `feed` table and only marks it if it is already there. A group is that ask's line: its text ends with ` … ` and the ask's.
- **A cast** that fired or failed (§2) is always fed, whatever `watch.json` says: `GAME#820 18:30:02 cast Steve | Steve cast "fire ball": command, running as command_2`, or `… | Steve cast "fire ball": failed — <error>`. Cooldown and duplicate casts are not fed.
- `SYS#0` is never assigned by the feed: `vfg watch` uses it for its own notices — EC2 unreachable, reconnected, lines skipped, feed restarted.
- **The writer is one Python module, `vfg_feed`**, owned by the bridge and deployed to `/opt/vfg/lib/`. Its API is `append(type, fields, text, at=None) -> seq` and `append_batch(entries) -> [seq]`, where each entry is a `(type, fields, text, at)` tuple; `at` is the moment it describes (when a line was said), defaulting to now, and is what the `HH:MM:SS` shows. It cleans the text (newlines to spaces, 500 characters), takes a file lock, appends to `feed.log` and inserts the `feed` row. Its command line is `python3 /opt/vfg/lib/vfg_feed.py post <TYPE> "<fields>" "<text>"`, which prints the seq. The Jev filter imports it, and `vfg feed post` calls it over SSH.

## 8. The `vfg` toolkit — the owner's PC

**Every agent acts through these commands, and nothing else touches EC2.** Output is plain text. Exit 0 means success. A failure exits non-zero with one line on stderr. Configuration lives in `~/.vfg/config`, as `KEY=value` lines: `VFG_SSH_HOST`, `VFG_SSH_USER`, `VFG_SSH_KEY`, and the brain's (§9); an environment variable of the same name wins.

| Command | Does |
|---|---|
| `vfg up` | Checks SSH and the `minecraft`, `vfg-bridge` and `vfg-jev` units, starts any that are down, prints their status |
| `vfg watch [--after <seq>]` | Prints the feed from the line after the last `seq` it printed (cursor in `~/.vfg/cursor`), then follows; reconnects on SSH drops; never exits on its own. `--after <seq>` starts after that seq, prints every line after it, on its first connection and on every reconnect, with no catch-up limit, and reads and writes no cursor: the brain keeps its own place |
| `vfg say "<text>" [--to <player>] [--task <name>]` | `tellraw` to everyone or one player, with the prefix `[AI] ` in aqua (`VFG_CHAT_PREFIX`), and stores the text as an `ai` line (§4), and feeds it as an `AI say <name\|->` line (§7), in the same SSH call |
| `vfg cmd "<command>"` | One server command, through the `command` action; prints Minecraft's reply |
| `vfg history [--since <iso\|-10m>] [--until <iso>] [--player <name>] [--class <c>] [--source voice\|chat\|ai] [--events] [--limit N]` | Queries the transcript history, or `events` with `--events` |
| `vfg watchers set <kind,…> [--players a,b] [--contains <regex>]` / `vfg watchers show` | Writes or prints `watch.json` |
| `vfg lookout set "<text>"` / `vfg lookout show` | Writes or prints `lookout.md` |
| `vfg brain start\|stop\|status` | Starts, stops or checks the brain (§9), a background process on the owner's PC: `start` runs `brain/run` detached, its log in `~/.vfg/brain/brain.log` and its pid in `~/.vfg/brain/brain.pid`, and when one is already running prints its pid and succeeds; `stop` sends SIGTERM to the brain alone, so in-flight calls can finish, it can stop its implementers itself (their CLIs are in its process group) and close or fail their tasks, and SIGKILL to the group after 15 s; `status` also lists the open tasks, oldest first, read from the box's `tasks` table, one `open   <name> <player\|->: <description>` line each, or `open   none`, or `open   ? (<why>)` when the read fails; its exit code is still the brain's |

## 9. The brain — the owner's PC

**The brain replaces the conversation, the orchestrator agent and the dispatcher.** Its entry point is the executable `brain/run`; `vfg brain start` runs it detached. It is one async loop: it follows the feed with `vfg watch --after <seq>`, and every event is its own asyncio task, so no line waits for another. What the orchestrator agent decided is now the orchestrator call, a small `structured()` call that is part of the brain (below).

- **Events.** An `action_oriented` LINE is one brain call. A `conversational` LINE is one Respond call. An implementer's report is one brain call. Each part a brain call sends to `orchestrator` is one orchestrator call more. There is no other call. A GAME line, a SYS line and the brain's own `AI` lines are context only. A `context` LINE is not even that: no model is shown it (below). A LINE already in the feed when the brain reads its context (at or below the `last_seq` it gives) and more than 2 minutes old then is history and is never acted on; a LINE that arrives on `vfg watch` after that is live, whatever its time.
- **A brain call** is one `structured()` call (`lib/py/vfg_llm.py`) on `VFG_BRAIN_MODEL` (`openai/gpt-6.1-sol`, reasoning `low`). It routes each part of the line — `action`, the action written in full, which runs at once (§14); `orchestrator`, an instruction in plain words, for anything new no action does, a change or fix of something that exists, or stopping, cancelling or undoing something running; `talk` — and writes the one chat line, the reply, in the same answer. It never names a task: the orchestrator call finds or names it. Every line it acts on gets a reply. On a report it writes the player's chat line and one `result` line (`castle_steve done: castle built at spawn`), and may send parts too, an orchestrator part to fix what the report left undone among them.
- **The orchestrator call** is one `structured()` call per orchestrator part, on `VFG_ORCHESTRATOR_MODEL` (`google/gemini-3.8-flash`, reasoning `low`, 15 s at most), one after another in the order the parts come, each told what the ones before it answered. It reads the conversation as the brain does, cached the same way, then TASKS (every task, what it made, its copies running now, its last result), RUNNING NOW (every copy, with every value of its action, its value now, its limits or choices, live or restart), the event, the brain's instruction and the line's other parts; nothing of the menu, the commands or the world. It answers one of five, which code carries out:
  - `new`: a name (the thing, then whose: `frost_bow_alex`), a description and a brief. Code makes the name free of every task, action, script folder and running copy and of `cast`, adding `_2`, `_3` …, opens the task (§4), posts `AI task <name> | new: <description>` and starts its implementer at once (§10).
  - `follow_up`: a task from TASKS, its new description and its brief. The task is open again, `AI task <name> | follow-up: <brief>` is posted, and its implementer gets the brief, resuming its session; with no session (after a restart), a new implementer starts on the description and the follow-up.
  - `edit`: a copy under RUNNING NOW and the values to change, checked against its action; code runs the `edit` action, with no task, and posts `AI note`.
  - `stop`: the copies to end; code runs the `stop` action on each, with no task, and posts `AI note` for each. A stop never changes a task's status.
  - `reply`: nothing starts; the reply is all (an ask-back, an answer, nothing by that name running).
- **Who replies.** With no orchestrator part, the brain's reply, said once the action parts are done (at once when there are none). With one, the first orchestrator call writes the line's reply, said once the action parts, that call and its edit or stop are done, never waiting for an implementer to start or for a later call; the brain's own reply is held back and said only when that call fails. A later call's reply only, its edit or stop that failed, or its failure (`say "<part>" again?`) is a line of its own after it. When an action, an edit or a stop failed, or was dropped in code, a line written in code goes out in place of the reply, so no reply claims what did not happen; a question the first call asks back is still said after it. On a report the orchestrator calls write no reply: the brain's is said once the actions are done.
- **Respond** is the brain's cheap mode, on `VFG_RESPOND_MODEL` (DeepSeek V4 Flash, reasoning off), reading the same context. It replies, or hands the line up to the brain and says nothing itself — never both — and never acts on the game.
- **The shared context** is the feed (§7), `feed` in `vfg.db` (§4): the whole conversation, with the world — every online player's position, health, food, armor, XP level, game mode, effects and items by slot (`vfg state --json --items`; Respond's without the items), the running copies, the saved places, the time and the weather — and TASKS, every task on the server, open and closed, one `- <name> for <player|nobody>, <status>: <description>` line each, the status `an implementer is on it` while one runs (`TASKS: none yet` with none). Every brain and Respond call reads it whole, but for the `context` LINEs: those stay in the feed and `vfg.db`, for a later memory, and are never shown to a model, neither in the conversation nor as new rows. Every GAME row is shown. On the AI side only the brain writes to it, through `vfg say` and `vfg feed post AI`; nothing an implementer writes is in it.
- **Processed marks.** Every call (a brain call for a line or a report, a Respond call) takes in every row not yet processed and marks it, `vfg context mark`, so the game events since the last call are its new rows. A `context` LINE is marked as it arrives, and at a start every one still unmarked, so nothing waits on it. Nothing else is read: what arrives after the last call waits for the next.
- **Caching.** The call's fixed opening, then the conversation in blocks marked at stable checkpoints (every `VFG_BRAIN_CHECKPOINT`, 5, blocks; at most 4 marks), then what changes.
- **Tasks.** Only an implementer's work is a task. The brain keeps its tasks in memory, keyed by name, and writes every change of one as its whole row through `vfg task set` (§8) in the background, one task's writes in the order they were made; a write that fails is sent again after 2, 5, 15 and 30 s unless a newer change carries the row first. It reads them at a start, from `vfg context --json`, and again when the feed restarts: a row the memory lacks is added, and one the read lacks (a box provisioned again) or holds older than the memory (a write that never landed) is written back. A report merges what the implementer made into the task's `made`, keeps its `DESCRIPTION:` line as the description (§10), and reads the task's `variables` from its action, the one named as the task, else the last it made that is loaded; they are read again whenever that action's file changes. At a start, every task still open fails (`<name> failed: interrupted, the brain restarted while it ran`); at a stop, every task whose implementer it stopped (`<name> failed: stopped, the brain stopped while it ran`), and the writes still going out get 5 s. `vfg route --task` reads one row and `vfg brain status` the open ones.
- **Files**, in `$VFG_BRAIN_DIR` (default `~/.vfg/brain`): `lock`; `brain.pid`; `brain.log`, one `<ISO time> <area> <message>` per line; and `refs/<version>/`, the server's command tree and the wiki's command pages, fetched once per server version. A `tasks.json` an older brain left there is renamed `tasks.json.retired-<YYYYmmdd-HHMMSS>` at the start, never read and never deleted.
- **Usage**: every model call is a `usage` row of its own, written by `structured()` (§4): `brain` (`ref` `#<seq>`, or the task's name for a report), `respond` (`#<seq>`), `orchestrator` (one per orchestrator part: `#<seq>`, or the task's name for a report's) and `planner` (`<ref> #<part>`, its `ref` the line's `#<seq>` or the report's task name), failed calls included. The brain logs what each call spent, a failed one too, and sends the queue after it, after an orchestrator call and after an event's planner calls, at its start and at its stop (`vfg usage flush`, nobody waiting; after calls never two at once, one asked for while another runs running once when it ends); `implementer` rows, one per implementer run, its `ref` the task's name, it writes with `vfg usage add`.

## 10. Implementers, actions and the scripts folder

- **An implementer is started by code from the brain's brief, one per task** (§9): a run of the harness `VFG_IMPL_HARNESS` names, on DeepSeek V4.1 Flash with thinking off (below). Its brief carries `YOUR TASK: <name>`, the name everything it makes takes (its script and its action, `vfg script new <name>`, and its copy, `as=<name>`; every `vfg action run` it sends takes `--task <name>` and every `vfg place save` `--by <name>`), `SAVED PLACES: …` (§14), read fresh, and what `vfg route --task <name>` picks (the brief, below). A follow-up to its task goes into its run as a message while the run is live, and resumes its session after it (below), so two implementers never edit one script; it may change its task's own script in place even while copies of it run. Its last message is its report, to the brain alone; it never talks to a player. The report's last line, `DESCRIPTION: <what the thing is now, for whom, how a player uses it>`, is taken off it in code and kept as the task's description (at most 600 characters; with none, the one the brain wrote stays).
- **What a task made** is recorded by the guard from the commands it lets through (`vfg script new`, `vfg script save`, `vfg preset save`, and each copy `vfg action run … as=<copy>` starts) and the new action and preset files it lets the implementer write, each script, action and preset kept only when its file is on disk: `{"scripts", "actions", "presets", "copies"}`, given with the report and added to the task's `made` (§4). The guard refuses every `vfg task` command: only the brain writes the tasks.
- **Implementers act on the server only through actions**: `vfg action run|list|check|show`, its shortcuts `vfg cmd`, `vfg script set|stop` and `vfg place save`, and `vfg script new|check|list|logs`, `vfg preset save`, `vfg place list` and `vfg test` (§8). The ladder: run an action; change a running copy; a new script and its action; a new preset.
- **The last step of any build players may want to go back to**, once it is checked, is `vfg place save <name> --at <x> <y> <z> --by <task>`, at the spot a player should arrive: the name the brief gives, else a short lowercase one (`castle`, `steve_house`).
- **The harness** is the program around the model: it sends the prompt, runs the tool calls the model asks for, and keeps the session a follow-up resumes. The runner (`brain/brain/implementers/runner.py`) knows one only through `harness/base.py`: a `Harness` (`name`; `start(task, system, brief, guard)`; `resume(task, system, session, text, guard)`; `close()`, at shutdown) gives a `Run` (`session`; `events()`; `send(text)`, a message into the live run, false once it has ended; `stop()`, an interrupt; `close()`), whose events come in order: `Session`, its id, as soon as the harness has one, which the brain keeps in the task's row; `ToolCall`; `ToolResult`; `Text`; `Request`, one model request's tokens as the provider counted them (input not cached, read from the cache, written to it, and output), its model and when it was sent, its size the three inputs together; `Compacted`; and last `Done`: how it ended (`ok`, `error`, `turns` or `stopped`), its last message, the report, its turns, the calls the harness's own checks refused, which should be none and are logged as `denied`, and `unread`, the messages it ended without reading. The system prompt goes as a file, `$VFG_BRAIN_DIR/implementer-system-<12 hex of its sha256>.md`, given again on every resume. Every adapter calls the guard's `gate()`, its one entry point, before a tool runs, a refusal going back to the model as that tool's error with the guard's reason, and turns its harness's own permission checks off: the guard is the only gate. The tools are the harness's own. The guard refuses, on every harness, the owner's commands and the server-wide settings, any shell command but `vfg`'s own and a few others, a write outside `made/<server>/`, an edit of a script another task's copy runs, `WebFetch` and `WebSearch`, and a read or a search outside `scripts/`, `actions/` and `made/<server>/`: `Read` names a file in them, `Grep` and `Glob` a path in them, and the shell reads with `cat <file> …`, `sed -n 'A,Bp' <file>`, `grep`, `head`, `tail` and `ls` on paths in them, a glob in a read checked match by match as bash would expand it (a bare `ls` passes; `ls -R` and `grep -r` with no path do not). It refuses a `vfg test` when nothing it covers (the test, the script and action of its name, and what the task made, read as code: comments, docstrings and formatting are no change) changed since the run's last test of it, and a fifth in a run; a `--kind` that names no template; an `incantation_create` that binds a made action that runs until stopped and whose script waits for a crouch, a click or a pad, since a cast's copy must act as it starts; and a `vfg cmd` that only looks (`execute if|unless` with no `run`, `data get`, `list`, `scoreboard players get`) once the run's four tests are spent, and past three a run when there is a test server (`VFG_TEST_BOX`). A `vfg cmd` that acts always runs.
- **Claude Code** (`VFG_IMPL_HARNESS=claude-code`, the default; `harness/claude_code.py`): one Claude Agent SDK client per run, the CLI the main agent with nothing of the owner's around it (no settings, skills or MCP servers), its tools `Bash`, `Read`, `Write`, `Edit`, `Glob` and `Grep`, in `bypassPermissions` with the guard as its `PreToolUse` hook, which runs first and whose deny still blocks; as root, where the CLI refuses that mode, `dontAsk` with every use of those tools allowed. By `VFG_IMPL_PROVIDER`:
  - `deepseek` (`deepseek-flash` at `https://api.deepseek.com/anthropic`) or `openrouter` (`deepseek/deepseek-v4.1-flash` at `https://openrouter.ai/api`): DeepSeek V4.1 Flash at the provider's Claude-compatible address, through the relay (`harness/relay.py`), in the brain's own process on 127.0.0.1 at a free port, each run at an address of its own. On every POST to `…/messages` it sets `"thinking": {"type": "disabled"}` and drops `output_config`: the CLI leaves thinking out whatever it is told, and DeepSeek reads a request without it as thinking on. Everything else, the key among it, goes through as it came, and the answer comes back as it streams; the relay reads each request's usage from it, with the provider that served it and what it billed (OpenRouter's `usage.cost`) when the answer says, and gives the run a `Request` before the answer ends, so every request is counted. On `openrouter` it also sets `provider` on every request: `order` `VFG_IMPL_OR_ORDER` (`digitalocean,ionstream,together`, the providers that kept the cache best), `ignore` `VFG_IMPL_OR_IGNORE` (`venice,morph,relace`), and fallbacks allowed, so a run stays on one provider's cache and an outage of those never fails it. The CLI gets the relay's address as `ANTHROPIC_BASE_URL`, the provider's key as `ANTHROPIC_AUTH_TOKEN` and never the owner's login, the one model as every model it may call (`ANTHROPIC_MODEL`, the default Opus, Sonnet and Haiku models, the small fast model, the subagent model), `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, so no request writes a session's title, and its auto-compact window at the model's whole context, 1M tokens, from the price table (`CLAUDE_CODE_MAX_CONTEXT_TOKENS` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW`); the runner logs a compaction should one happen.
  - `anthropic`: Haiku 5.5 (`claude-haiku-5-5`) on the owner's Claude subscription, as before the harness, kept as a setting and not tested: the CLI's own login, never an API key (a run whose CLI would use one is stopped), at `VFG_IMPL_EFFORT`, its cache's life `VFG_IMPL_CACHE_TTL`; no relay, each request's tokens read from the CLI's assistant messages, one request per message id.

  A message is a second `query()` on the run's open client. The CLI runs with `--replay-user-messages`, echoing each message as it reads it, so the run knows which are unread: one sent while a tool runs is read as soon as the tool calls in flight finish, in the same turn; one that lands as the model ends its turn starts the next turn.
- **OpenCode** (`VFG_IMPL_HARNESS=opencode`; `harness/opencode.py`): one `opencode serve` (OpenCode 1.x; `VFG_OPENCODE_BIN`, else `opencode` on the PATH) per brain, driven through its HTTP API, its config, sessions and caches under `$VFG_BRAIN_DIR/opencode/`, nothing of the owner's own OpenCode read; on `deepseek` or `openrouter` only, at the provider's OpenAI-style address, thinking off on every request, and on `openrouter` the same `provider` routing, in its agent's options; our system prompt as its agent's prompt; every tool allowed in its own permissions, and the guard asked from its `tool.execute.before` plugin hook (`harness/opencode_plugin/guard.js`, JS because OpenCode's plugins are) at an address the brain serves on 127.0.0.1 with a secret, the hook throwing the guard's reason, and refusing the call when it cannot ask; each call put to the guard in Claude Code's names (a patch as a `Write` or an `Edit` of each file it touches, a web tool as `WebFetch` or `WebSearch`); its turns its model requests, the run aborted at the cap; no compaction; each session made with its title, `vfg <task>`, so no title request. A message is a prompt into the busy session, read at its next step.
- **The brief.** The system prompt is the same bytes for every implementer: its rules (`brain/prompts/implementer.md`), then `vfg prefix` (§8), which ends with the library's actions, one menu line each. The brief is the brain's, in depth, with its `DONE WHEN` checklist (§9), then `YOUR TASK` and `SAVED PLACES`, then the EXAMPLES block, read as the run starts: at most 3 of the scripts `vfg route --task <name>` picks, those that run the job first, whole; the presets it picks; every script the brief names, and the script of every running copy it names; what runs, who is online and where, the time and the weather; what this server's implementers made, by first line; then ACTIONS: at most 7 actions in full (`vfg action show`'s text), the router's picks best first, or, when the router failed, those the job's words point to; and this server's made actions, one menu line each. Any other action in full is `vfg action show <name>`, which the guard allows. Its rules say to act on what it was given, and to read a file once. One `brief` line in `brain.log` gives each part's size.
- **The report** comes after one check, its test (below), else one action run, an item that check did not show being not tested; a job outside the game, or the owner's, is reported `Failed` at once. Its first word is `Done`, `Failed` or `Cancelled`; then a short paragraph; then, when the brief has a `DONE WHEN` list, one line an item, done, not done or not tested, and why; then `DESCRIPTION:`. One report covers every message its run read. A last message that is an `<analysis>` or `<summary>` of the conversation is never the report: the run's last text that started `Done`, `Failed` or `Cancelled` is, else the report is `Failed`. The runner takes the task's status from the first word, else from the first line that starts with one (a report may open with what it put back), else `done`: `Done` and `Cancelled` are `done`, `Failed` is `failed`. An error, a crash or a stop by the harness is `failed` whatever the text says, and so is a warned run whose report says none of the three.
- **The test is the implementer's check**, run on the test server and never in the live world or on a real player. Anything it makes or binds gets one, `made/<server>/tests/<task>.py`, from the template of the ability's kind (`vfg script new <task> --kind <kind>`, or `vfg test <task> --kind <kind>` when there is none; §8): a script, one check per `DONE WHEN` item at the template's TODOs, with the kit's test helpers, one `Test` a file, which run only under `vfg test` (`VFG_TEST=1`); `scripts/_lib/kit/test.py` is their guide, in the system prompt, and `kit/_stage/helpers.py` their code, which is not. The test server is a second Minecraft server with Carpet's fake players. Its stage is in the sky: a barrier floor at y 295, 81 x 81 around x 3000, z 3000, forceloaded, at midnight in clear weather with mobs and phantoms not spawning; the caster a fake player at full health standing on it, facing north, and Alex 4 blocks to his left. Everything 97 x 97 around it from y 280 up, the test's copies and fake players included, is cleared before the test and after it, a stop at the timeout included, and the game rules it changed are put back. A test tries the ability as a player meets it: an incantation by `t.cast`, its real trigger, with nothing pressed after (or `t.bind` binds one on the test server, for a library test), an item by `t.run` and `t.use`; ground, fire and blocks on what the test placed (`t.ground`, `t.blocks`), never on the floor. It only watches: `t.cmd` sets the stage, refusing any change to a player and stopping the test when Minecraft refuses the command, and each check is the kit's verdict (`t.hurt`, `t.moved`, `t.burning`, `t.fire_near`, `t.built`, `t.weather`, `t.said` …), never a bare `True`. When nothing fired after the trigger (no result or log line, nothing new on the stage, nobody moved, hurt or set alight), `t.unhurt`, `t.others_unhurt` and `t.no_errors` are `CAN'T TELL`. Each thing a test places prints an `AT` line, where it is from the caster: right, up and forward, forward the way he faces, north (−z); a `FAIL` says where things ended up. The test's `PASS`, `FAIL` and `CAN'T TELL` lines are the report's done, not done and not tested. On a `FAIL` the implementer reads the log lines it printed, decides which is wrong, the ability or the test, and fixes that one, never lowering a bar below what the brief asks; three fixes at most, then it reports what still fails, item by item. A change to the test is reported, item by item, with why, and an item whose check it removed is not tested. A follow-up changes the checks for its change and runs it again. A library action run as it is, with nothing bound, keeps that run's answer as its check, and so does any build when `vfg test` exits 3, 4 or 5. In the live world the implementer neither tests nor probes: beyond what the job asked, it never moves, teleports, hurts or changes a real player, gives one an effect, or summons a mob or sets off a blast near one.
- **A follow-up while the run is live**, or starting, goes into it as a message, `MESSAGE from the brain: <text>`, through `send()`, read at the run's next safe point; nothing is interrupted. A run ends only with no message unread: on Claude Code, a run whose turn ends with one unread waits up to 5 s for the turn that reads it, then ends with it in `Done.unread`. A message the run ended without reading, and every message that went into a run stopped at its limit or crashed, goes to a resume, as a follow-up after the run would; but none after a run a cancel went into, which takes them with it. When `send()` says the run has ended, or the run is reporting, the follow-up waits for the report and then resumes the session (`FOLLOW-UP to <name>, from the brain: <text>`); follow-ups that wait behind one run go in together, so parts of one line make one run. **Every follow-up after a run resumes the task's session**, whatever its size: no fresh start and no summary. A follow-up tests only what it changed and reports only its own items; when the task's thing is not there at all (a run put back, or never finished), it builds it from the task's brief, with the change. Only a task with no session (after a restart) starts a new implementer, on what the task is and the follow-up.
- **Never mind** is a follow-up whose text is code's words (§9), `CANCELLED: the player said never mind. Stop building and put everything back the way it was before the run this cancels, then report Cancelled: and what you put back.`, known by its start, `CANCELLED:`. It goes into a live run as it is; after the run, it resumes the session; behind a run, it drops the follow-ups waiting there; and before a task's first run begins, nothing starts, and the task is reported `Cancelled: it had not started; nothing was made.` The implementer stops, puts back what the run changed (an incantation it bound, edited or removed is its alone to put back), and reports. Then code puts back the rest, from the run's snapshot (`putback.py`): before `gate()` lets a call run, the snapshot keeps, at the run's first change of each, a made file's bytes or that it was not there (a `Write` or `Edit` under `made/<server>/`, `vfg script new`, `vfg script save`, `vfg preset save`); a running copy's `running.json` entry or that it was not running (`vfg script set|stop`, `vfg action run … as=`, the `edit` and `stop` actions' `copy=`); and a saved place or that there was none (`vfg place save`). After the report, a made file not back to its bytes is written back and one the run created removed, a copy it started is stopped and one it changed or stopped set back or started again, and a place it saved forgotten or saved again where it was. The report gains one line, `Code put back: …`, and is `failed` when it adds `It could not: …`. The snapshot is kept until the task's next run, in memory and in `$VFG_BRAIN_DIR/implementer-snapshots/<task>.json` (mode 600, the files' bytes in it), so a cancel after the run ended puts that run back, after a restart of the brain too.
- **The limits.** A run is warned once, near its limit, by a message in code's words, `LIMIT: you are about to run out of turns and time. Stop building now. Put everything back the way it was before this run, then report Failed: what you tried, why it did not work, and what might.`: at its 95th model request of 100 (`VFG_IMPL_MAX_TURNS`, less 5), counted over every turn of the run, or 60 s before its `VFG_IMPLEMENTER_MINUTES` are up (at three quarters of a limit under 4 minutes). A warned run that reports done keeps its work, unless a cancel went in; any other, code then puts back, as after a cancel. A run that reaches the limit anyway (a request past the cap, the CLI's own turn cap, or the time) is stopped, code puts back, and the runner writes the report from what the guard saw: `Failed: stopped at its limit (its 100 turns); put back to the last working version.` (`its time limit, 600 s`), what the run had made and changed, and its last 5 tool calls with their errors.
- **Usage, priced by the runner** (`usage.py`, the table in `config.py`): each `Request` is priced at its own size and time, and no harness's running total is read, so nothing is counted twice. Per million tokens, a cache miss, a hit, a write and output: DeepSeek V4.1 Flash on DeepSeek's API (`deepseek-flash`), $0.30, $0.006, $0.30 (DeepSeek has no write price: a miss is input) and $1.20 at its peak, by the request's UTC weekday and hour, Monday to Friday 01:00–04:00 and 06:00–10:00, and half that at every other hour; on OpenRouter (`deepseek/deepseek-v4.1-flash`), the peak price at every hour; Haiku 5.5 (`claude-haiku-5-5`), $0.10, $0.01, $0.125 and $0.50, five times each for the whole of a request over 100K tokens. A model the table lacks costs $0, logged once. Each request is a `request` line in `brain.log`, `<task> <model> in=<not cached> cached=<n> written=<n> out=<n> size=<n> cost=<$>`, then `provider=<slug>` and `billed=<$>` when the provider said them. Once the run has reported, or has ended at a shutdown or in a crash, it writes one `usage` row per model, so one per run (`vfg usage add --component implementer --ref <task>`, §8): `input_tokens` every input token of its requests, cached or not, `cache_read_tokens` and `cache_write_tokens` the parts of it, `output_tokens`, `cost_usd` the sum of their prices, and `largest_tokens` its largest request. When every request of the row billed (OpenRouter's, through Claude Code's relay), `cost_usd` is what the provider billed, else the table's; the `usage` line in `brain.log` says which priced it, and the table's price beside it.
- **Settings**, from the environment, then `~/.vfg/config`, unless marked: `VFG_IMPL_HARNESS` (`claude-code`, or `opencode`); `VFG_IMPL_PROVIDER` (`deepseek` when `DEEPSEEK_API_KEY` is set, else `openrouter`; or `anthropic`); `VFG_IMPL_MODEL` (the provider's, above; `VFG_IMPLEMENTER_MODEL` read when it is empty); `VFG_IMPL_BASE_URL` (the provider's Claude-compatible address, above); `VFG_IMPL_EFFORT` (`low`, the `anthropic` provider's only); `VFG_IMPL_MAX_TURNS` (100); `VFG_IMPLEMENTER_MINUTES` (10); `VFG_IMPL_CACHE_TTL` (`5m`, or `1h`, the `anthropic` provider's; `VFG_SUBAGENT_CACHE_TTL` read when it is empty); `VFG_OPENCODE_BIN`, from the environment only; `VFG_TEST_BOX` (none: no test server) and `VFG_TEST_TIMEOUT_S` (60), `vfg test`'s (§8); `VFG_IMPL_OR_ORDER` (`digitalocean,ionstream,together`) and `VFG_IMPL_OR_IGNORE` (`venice,morph,relace`), comma-separated, `none` for none; and the provider's key (§11).
- **Four layers, code in one**: the kit (`scripts/_lib/`, imported), presets (`scripts/_presets/<name>.py`, copied into a script), scripts (`scripts/<name>/main.py`, the code) and actions (`actions/<name>.py`, called). What implementers make goes in `made/<server>/scripts/`, `presets/` and `actions/`, under names the library does not use.
- **An action** is one pydantic class in its own file, named as the file (`gatling_gun.py`: `class GatlingGun`), with no code: its docstring's first line is its line on the menu; `script`, `runs` (`once` or `until_stopped`), `takes` (the fields the planner fills), `defaults`, `fixed`, `descriptions` (its own words for a field it inherits, whose type and limits stay) and `timeout_s`; and a field for every value the script reads, its type from `actions/_types.py`, its default, its limits (`Field(ge=, le=)`) and its description under it. `Live[T]` marks a value the script reads again while it runs. A variant subclasses an action. A preset's values are a class beside its function, `class <CamelName>(Values)`, which the action over every script that copied it inherits (`preset("<name>")`). Every value is checked on the PC; the box gets plain JSON.
- **A script** is Python 3.12, standard library only, with `kit`, `mc` and the rest of `scripts/_lib/`; line 1 its docstring, `"""<Title>: what it does."""`; line 2 `ASKS`, what players said. `v = values()` gives its copy's checked values (a `Live` one read again at most every `VFG_LIVE_POLL_S`, 0.5 s); `result(summary, **facts)` is its answer.
- **A copy** is one run of an action. On EC2 it runs as `/opt/vfg/python/bin/python3 -u <folder>/main.py`, its folder the working directory, with `PYTHONPATH=/opt/vfg/scripts/_lib`, `VFG_SCRIPT` and `VFG_INSTANCE` its name, `VFG_TASK` (the name of the task that started it, empty for the brain's own copies, or `cast` for an incantation's; `mc.task()` reads it, `""` for the last two, and `mc.cast()` is true for a cast's), `VFG_RUN_DIR`; everything it makes carries the tag `vfg_<copy>`, taken away by a stop; a copy that ends by itself keeps what it made, handed over to the tag `vfg_left_<copy>`, which no stop takes (`kill @e[tag=vfg_left_<copy>]` clears it). Its files in `/opt/vfg/run/`: `<copy>.pid`, `<copy>.log`, `<copy>.json` (`{"copy", "action", "script", "source", "server", "values", "live", "runs", "task", "started"}`, `task` a task's name, null or `cast`), `<copy>.values.json` (an edit's live values), `<copy>.result.json` (`{"summary", "facts", "at"}`, the last `result()`) and `<copy>.error` (the last line of an error nothing caught, which `mc.py` writes as it cleans up). `scripts/_lib/instances.py` starts, stops and edits copies, for `vfg` and for the `stop` and `edit` scripts. A deployed script's folder holds `action_defaults.json`, which every deploy writes and counts in the folder's stamp: for each action over the script, every field's default with the action's defaults and fixed values over them, and its live fields. `Box.start` takes from it every value a copy's values lack, and, for a cast (`asked`, §2), every value its binding did not ask for.
- **Incantations** are actions too: `incantation_create` (`player`, required, a name, several or `@a`; `phrase`, two words or more; `action`, from the menu; `values`, its defaults for this phrase; `cooldown_s`, default 3), `incantation_edit` (by `player` and `phrase`: `values`, `cooldown_s`, `aliases`) and `incantation_remove` (by `player` and `phrase`), over one script, `incantations`, which writes the store `/opt/vfg/incantations.json` (`{"version", "incantations": [{"id", "player", "phrase", "aliases", "action", "script", "source", "server", "values", "asked", "live", "runs", "caster_fields", "cooldown_s", "created", "by"}]}`, one entry per named player, `@a` one; `scripts/_lib/incantations.py`). vfg checks the bound action's values as a run would, makes every player field left out a caster field, makes the aliases (one `structured()` call, `VFG_INCANT_ALIAS_MODEL`, its usage row `alias` with the phrase as its ref and sent by `vfg usage flush`, and the phrase joined and split, at most 12), adds a note when the phrase is short or sounds like, or starts like, another of that player's, and deploys the bound script before the store is written. `values` are every value a cast runs with; `asked`, the ones the player asked for, caster fields apart: after a `vfg action run` of the bound action that went well, a binding whose `values` differ from `asked` over the action's defaults as they are now is made again from them (decided from `$VFG_HOME/incantations.json`, no SSH while none differs). A value of the bound action may be given as a word of its own, `values.<name>=<value>`: text for a field that takes text, else read as JSON.
- **The six core actions**, each over a script of its name: `command` (up to five server commands in order, the refused list of `scripts/_lib/commands.py` applied), `teleport`, `summon_around`, `save_place`, `stop` and `edit`. Every library script has at least one action, and every script an implementer makes gets one (`vfg script new` writes both; `vfg action check` passes).

## 11. Secrets

- On EC2, `TYPESAFE_API_KEY` and `VFG_CLIENT_TOKEN` live in `/opt/vfg/.env` with mode 600. On the owner's PC they may live in the `.env` file `VFG_BOX_ENV` names (default `~/.vfg/box.env`, mode 600, outside any repo). `deploy.sh provision` and `deploy.sh env` send only the names `env.example` lists, over SSH on stdin, and make the client token on the box when none is given.
- On the owner's PC, settings live in `~/.vfg/config`. The client token also lives in each player's mod config. The OpenRouter key is `OPEN_ROUTER_API` in the environment, or alone in the file `VFG_OPENROUTER_KEY` names (default `~/.vfg/openrouter.key`, mode 600); the config holds the path, never the key, and only `structured()` and the implementers (§10) read it.
- An implementer's key is its provider's: `DEEPSEEK_API_KEY`, from the brain's environment only, for `deepseek`; the OpenRouter key, read as `structured()` reads it, for `openrouter`; none for `anthropic`, the owner's Claude login. It goes only into the harness's environment, as Claude Code's `ANTHROPIC_AUTH_TOKEN`, which the relay passes on as it came, or as OpenCode's server's, blanked in the shells its tools start; it is never printed, logged or written.
- The file `VFG_TEST_BOX` names holds the test server's settings, the SSH key's path among them, never a key (§8). A test runs there with `VFG_CLIENT_TOKEN` and `TYPESAFE_API_KEY` taken out of its environment.
- The RCON password never leaves `server.properties` on EC2.
- No secret goes in the repo.

## 12. Startup — the brain sets everything up

1. The owner runs `vfg brain start` (`brain/run`).
2. The brain sets aside a `tasks.json` an older brain left in its folder (§9), then runs `vfg up`, then `vfg watchers set …`, then `vfg lookout set …` and `vfg jev menu set …`, its actions for Jev's state (§5); it sets the menu again whenever an action is added. It sends the usage rows queued while it was down, `vfg usage flush` (§4).
3. It reads the context with `vfg context --json`, the feed's rows and then its tasks, every row of the box's `tasks` table, fails every task still open (§9), and follows the feed with `vfg watch --after` the `last_seq` that gives, so nothing is lost across a restart and nothing older is read as new. A read that fails is tried again; the feed is never followed from 0.
4. It greets the players with `vfg say`, skipped when nobody is online.

## 14. Actions from the brain — the owner's PC

**The brain runs an action part at once**, written in full in its one answer: `vfg action run <action> key=value … --for <player>` (§8), reading its one line. It carries no task: only an implementer's work is one. `--for` names the copy `<action>_<player>`, then `_2` while that one runs (`command_steve`), the player being the action's `player` value when that is one player's name, else the speaker (for a report's parts, the task's player); with neither, there is no `--for`, and `edit` and `stop` never take it. A command Minecraft refuses is planned again once, with the command's reference, on `VFG_PLAN_MODEL` (DeepSeek V4 Flash, reasoning off). Each action and how it went becomes one `AI action -` line.

- **The menu** is every action (§10), the library's and `made/<VFG_SERVER>/actions/`, each as its name and docstring's first line, reloaded when a file changes, so a new action is on it at the next ask; then every running copy, one line each, from `running.json`, which a background `vfg script list --json --fresh` fetches every `VFG_RUNNING_TTL_S` (30 s), with the task that started it when that is not the copy's own name. `edit` and `stop` are on it, but the brain sends a change or a stop of a running copy to `orchestrator`, which sees every value of each copy (§9).
- **An item a player owns** is changed by its slot, which the context names (`hotbar.4 iron_sword (held)`): the held one, then the worn one, then the first listed; an ask for an item the player does not have is dropped, with why.
- **Saved places** live in Minecraft's command storage `everhear:places`, one entry per name (`^[a-z0-9_]{1,32}$`): `{pos: [x, y, z], dim: "minecraft:overworld", by: "castle_steve"}`, whole blocks, `by` the name of the task that saved it (`""` when none did; an older entry's task number still reads). Only `vfg place` and `scripts/_lib/places.py` (which the `save_place` and `teleport` scripts, and a `Place` value, use) read or write them. Every prompt — the brain's, every implementer's brief — carries them as one line: `SAVED PLACES: castle 197 68 251 overworld (castle_steve); …`, or `SAVED PLACES: none`.
- **`command` places or removes no block**: it refuses `setblock`, `fill`, `clone`, `place` and `fillbiome`, alone or after `execute … run`, and the owner's commands, one list in `scripts/_lib/commands.py`, before anything is sent. Building is a script's, through the kit, which spares protected places.
- **Settings**, from the environment, then `~/.vfg/config`: `VFG_BRAIN_DIR`, `VFG_BRAIN_MODEL`, `VFG_BRAIN_REASONING`, `VFG_RESPOND_MODEL`, `VFG_RESPOND_REASONING`, `VFG_PLAN_MODEL`, `VFG_PLAN_REASONING`, `VFG_ORCHESTRATOR_MODEL` (`google/gemini-3.8-flash`), `VFG_ORCHESTRATOR_REASONING` (`low`), `VFG_ORCHESTRATOR_PROVIDERS` (none: OpenRouter's choice), `VFG_ORCHESTRATOR_TIMEOUT_S` (15, its retries included), `VFG_BRAIN_CHECKPOINT` (5, the orchestrator call's too), `VFG_BRAIN_HISTORY_HOURS` (6), `VFG_DISPATCH_ACTION_TIMEOUT_S` (20; an action's `timeout_s` wins), `VFG_RUNNING_TTL_S` (30), `VFG_SERVER` (`main`), `VFG_OWNER`, and the OpenRouter key (§11).
